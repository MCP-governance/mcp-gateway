# 실행 경계와 증적 보강 — 2026-09-20

기준 코드: `de15131` (`main`, 종료·폐기 평면 통합 이후).
MCP 보안 관리 프레임워크 V2.0의 2.2.10, 9.5, 9.8에서 요구하는
실패 안전과 판단·집행 증적 구분을 기존 공통 실행 경로에 적용했다.

## 무엇이 달라졌는가

| 상황 | 이전 동작 | 변경 후 |
| --- | --- | --- |
| OPA가 미정의 결정값을 반환 | `decision` 키만 있으면 수용. 관찰 모드에서 허용으로 전환 가능 | 결정값·필수 필드·필드 타입·지원하는 제한조건을 검증하고 `P-CONTROL-FAIL-CLOSED`로 차단 |
| OPA 응답에 실행 기록 필드 포함 | 정책 응답을 실행 이벤트에 그대로 병합 | 허용된 정책 필드만 수용. `request_id`, `result`, `upstream_executed` 등은 거부 |
| `max_chars=0` | 조건이 거짓으로 평가되어 본문 전체 전달 | 빈 본문으로 제한. 음수·문자열·불리언 제한값과 미지원 제한은 거부 |
| 계정 정지 후 stdio 호출·대기 승인 | HTTP 인증 경로 밖에서 계정 상태 누락 | 공통 실행부에서 `active` 상태 재검증. 정지·잠금 관리자의 승인·거부도 불가 |
| 승인 처리 중 유효기간 만료 | 승인 처리 시작 때만 기한 확인 | 같은 MCP 연결의 도구 검증 후, `tools/call` 직전에 기한·승인 상태 재확인 |
| SDK가 예외를 ExceptionGroup으로 감쌈 | 실행 전 거부·출력 차단이 통신 실패로 분류될 수 있음 | 실행 전 거부와 실행 후 출력 차단을 구분해 기록 |
| 도구 실행 후 응답 유실 | DB에 `upstream_executed=false`만 남아 차단 건수에 포함 | `upstream_attempted=true`도 영속화. Console에 실행 여부 미확인 표시, 종료 판정은 T3 |

인가 판단은 기존 OPA/Rego가 계속 담당한다. 새 의존성이나 별도 정책 엔진을 추가하지 않았다.
`upstream_attempted`는 감사 체인 v4에 포함하며, v1~v3 기록과 해시는 바꾸지 않는다.

## 검증

WSL2/Linux에서 새 실습 환경을 준비한 뒤:

```bash
cd full_stack_lab
./console.sh test
```

기동된 실습 환경에서 실행 경계만 재검증:

```bash
docker compose exec -T gateway python -m app.runtime_acceptance
```

검사는 합성 계정 상태와 관찰 모드를 일시적으로 변경하고 복구한다. 전용 실습 환경에서
실행해야 하며, 승인·감사·효과 증적은 삭제하지 않는다.

2026-09-20 로컬 검증은 기존 서비스와 분리한 Compose 프로젝트·DB·볼륨에서 수행했다.

| 검사 | 결과 |
| --- | --- |
| OPA/Rego | 62/62 통과 |
| core acceptance | 90 통과, 실패 0 |
| Agent/API acceptance | 99 통과, 실패 0 |
| 실행 경계 회귀 | 44 통과, 실패 0 |
| 카탈로그 변조·OPA 중단·직접 노출 방지·스캐너 실행 | 전체 통과 |
| Python lint·Console JavaScript 문법 | 통과 |
| 무인증 API와 README 대조 | 통과 |
| Console 실행 상태 문구 | 실행·미실행·미확인·이전 기록·응답 유실 5사례 확인 |

부정 시험은 malformed OPA 응답 주입과 승인 만료·계정 정지를 재현한다. 응답 유실 시험은
**실제 합성 MCP 호출로 효과 로그를 증가시킨 다음** 응답 손실을 주입한다. 효과는 있는데
완료 응답은 없는 요청이 차단 성공으로 기록되지 않는지 확인한다. T3 판정 시험은 기존
T1 합성 케이스에 미확인 활동을 주입해 등급 하향을 검증한다. 실제 원격 제공자의 폐기
완료를 시험한 것은 아니다.

기준 코드의 함수를 별도로 실행하여 미정의 결정값이 검증을 통과하고,
`max_chars=0`에서 `ABC` 세 글자가 그대로 전달되는 것도 확인했다.

처음 재사용한 로컬 스캐너 이미지는 MCP 1.x/2.x 의존성 충돌로 Semgrep 실행에 실패했다.
현재 저장소의 이미 수정된 Dockerfile로 **검증용 워커 이미지를 새로 빌드**하여
Semgrep·Syft·Trivy·AI-Infra-Guard CLI 실행을 모두 확인했다. 워커 소스 변경은 필요 없었다.

실행 보고서는 `reports/acceptance.json`, `reports/agent-acceptance.json`,
`reports/runtime-acceptance.json`, `reports/security-regression.txt`에 남는다.

## 남아 있는 한계

- 실제 IdP, 외부 LLM·GitHub 자격증명, 조직 전체 egress 통제를 검증한 결과는 아니다.
- 승인 만료 재확인은 DB와 원격 MCP 사이의 분산 트랜잭션을 제공하지 않는다.
  이미 전달된 호출은 소급 취소하지 못하며, 계정·정책·서버 종료와 실행을 원자적으로
  직렬화하거나 진행 중인 호출을 취소하는 통제는 별도 작업이다.
- 시도 여부도 DB 기록 전에 프로세스가 중단되면 남지 않을 수 있다. Agent 경로의
  미완료 receipt와 독립 효과 로그를 함께 조사해야 한다.
- 미확인 실행을 독립 증거로 자동 정산하는 기능은 없다. 보수적으로 T3를 유지하며
  추가 조사와 명시적인 위험 수용 절차를 사용한다.
- Console 문구와 렌더링 함수는 검사했지만, 이번 변경에서 브라우저 시각 검사는 수행하지 않았다.
