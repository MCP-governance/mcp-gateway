# 통제 평면 분리 — 무엇이 엔드포인트에 깔리고 무엇이 네트워크에 깔리는가

> **v1 시기 문서.** 여기의 설계 근거(왜 그렇게 나눴는가)는 v2에도 유효하지만, 경로·포트·서비스 이름·파일 위치는 v1 기준이다. 현재 구성은 [../ai/ARCHITECTURE.md](../ai/ARCHITECTURE.md), 결정 기록은 [../ai/DECISIONS.md](../ai/DECISIONS.md).

체계를 세울 때 가장 먼저 갈라져야 하는 것은 **통제가 어디에 설치되는가**입니다.
같은 "MCP 통제"라는 말 안에 서로 다른 세 가지가 섞여 있고, 셋은 설치 주체도,
실패 방식도, 우회 방법도 다릅니다.

| 평면 | 어디에 깔리는가 | 무엇을 할 수 있는가 | 무엇을 못 하는가 |
| --- | --- | --- | --- |
| **엔드포인트 평면** | 사용자 PC·개발 워크스테이션·CI 러너 | 그 단말에 **무엇이 설정돼 있는지** 본다 | 호출을 막지 못한다 |
| **네트워크 평면** | 게이트웨이·프록시·tailnet·egress | 호출을 **실제로 막는다** | 자기를 통과하지 않는 것은 보지 못한다 |
| **관리 평면** | 서버 측 관리대장·정책·감사 | 무엇이 승인됐고 무엇이 폐기됐는지 **정한다** | 스스로는 아무것도 보지도 막지도 않는다 |

이 저장소의 v1.5까지는 네트워크 평면과 관리 평면만 있었습니다. 그래서 답할 수
없는 질문이 둘 있었습니다 — "게이트웨이를 안 거치는 경로가 있는가"와 "폐기한
서버가 사람들의 PC에서도 사라졌는가". 둘 다 엔드포인트 평면의 질문입니다.

## 1. 엔드포인트 평면 (호스트에 설치)

### 1.1 이 저장소에 구현된 것

[`../endpoint-agent/agent.py`](../endpoint-agent/agent.py) — 의존성 없는 단일 파일. 호스트 설치 절차는 [endpoint-agent/README.md](../endpoint-agent/README.md)에 있습니다.

```bash
./console.sh endpoint
```

| 하는 일 | 근거 |
| --- | --- |
| MCP 클라이언트 설정 파일을 찾아 서버 목록을 추출 | 그 단말에서 실제로 쓰는 MCP의 모집단 |
| **LISTEN 소켓과 소유 프로세스를 열거** | 설정에 적지 않고 띄운 서버. 단말 권한이라야 보인다 |
| **허용된 내부 대역에 TCP 연결 후 `initialize` 1회** | 세그먼트 너머는 게이트웨이에서 닿지 않는다 |
| **stdio MCP 프로세스 탐지** | 포트를 열지 않아 어떤 망 스캔으로도 안 보인다 |
| Registry와 대조해 `registered` / `shadow` / `retired-residue`로 분류 | 관리 평면의 정본과 현장의 차이 |
| Gateway `POST /api/endpoint/inventory` · `POST /api/endpoint/listeners`로 보고 | 판정이 화면이 아니라 데이터에서 계산되게 |

세 번째 줄이 이 평면이 존재해야 하는 이유를 가장 잘 보여줍니다. **게이트웨이
장비에서는 사원 PC의 루프백과 내부 세그먼트를 볼 수 없습니다.** 루프백은 정의상
그 단말 안에만 있고, 세그먼트는 NAT와 방화벽 뒤에 있습니다. "게이트웨이가 망을
스캔하면 되지 않나"는 그래서 답이 아닙니다 — 스캔하는 주체가 그 망 안에 있어야
하고, 그 자리에 있는 것이 엔드포인트 프로그램입니다.

**탐색 범위는 에이전트가 정하지 않습니다.** 관리 평면의 `endpoint_scan_policy`가
정하고 에이전트는 받아서 따릅니다. 사설 대역만, 최대 `/20`까지, 그리고 그 검사는
게이트웨이와 에이전트 양쪽에 있습니다. 한쪽에만 두면 그 한쪽이 틀리는 날 통제가
없습니다. 보내는 것은 MCP `initialize` 한 번뿐이고 그 밖의 요청은 만들지 않습니다.

읽는 파일: `claude_desktop_config.json`, `.mcp.json`, `mcp.json`,
`mcp_settings.json`, `cline_mcp_settings.json`, `.cursor/*.json`, `.vscode/*.json`.

**보내는 것**: 서버 이름·전송 방식·주소. stdio 명령 인자는 SHA-256 digest로 바꿔 보냅니다.
**보내지 않는 것**: `env`, `headers`, 파일 본문. 거기에 토큰이 있고 관측에는
필요 없습니다. 사람들의 API 키가 인벤토리 테이블에 쌓이면 그 테이블이 조직에서
가장 위험한 표가 됩니다.

### 1.2 장치 자격 — 사람 계정이 아니다

에이전트는 로그인하지 않습니다. 관리자가 발급한 장치 키 하나를 갖고, 그 키로 할
수 있는 일은 `scopes`에 적힌 보고뿐입니다.

| | 사람 계정 | 장치 자격 |
| --- | --- | --- |
| 발급 | 신원 관리대장 | 관리자가 엔드포인트마다 발급 |
| 할 수 있는 일 | 역할이 허용하는 전부 | `inventory` · `netscan` 보고뿐 |
| 침해됐을 때 최악 | 그 역할의 전권 | 거짓 인벤토리 한 건 |
| 폐기 | 계정 상태 변경 | `DELETE /api/endpoint/devices/{id}` |

키 하나로 남의 엔드포인트 보고를 덮어쓸 수도 없습니다. 자격이 가리키는
`endpoint_id`와 다른 보고는 403으로 거절합니다 — 그렇지 않으면 그 키는 장치
자격이 아니라 관리자 자격입니다.

### 1.3 이 에이전트가 통제하지 않는 이유

설정 파일을 고치거나 프로세스를 죽일 권한을 주면, 에이전트가 침해당했을 때
조직의 모든 개발 환경을 조작할 수 있는 경로가 됩니다. 관측만 하는 프로세스는
침해당해도 거짓 인벤토리를 올리는 것이 최대치이고, 그 거짓은 판정을 **보수적인
쪽으로만** 밉니다. 없는 잔존이 보고되면 종료 판정이 내려가지, 올라가지 않습니다.

그래서 이 평면이 Gateway에 보내는 본문은 **관측 보고이지 지시가 아닙니다.**
보고 내용으로 Registry를 바꾸거나 서버를 활성화하는 경로는 코드에 없습니다.

### 1.4 실제 조직 배치에서 엔드포인트단에 필요한 것

이 실습이 구현한 것은 인벤토리 하나입니다. 실제 배치에서 같은 평면에 놓이는
것들을 함께 적어 둡니다. **아래는 이 저장소에 구현돼 있지 않습니다.**

| 통제 | 무엇을 해결하는가 | 왜 엔드포인트단인가 |
| --- | --- | --- |
| 클라이언트 설정 무결성 | 승인된 MCP 구성만 허용 | 설정 파일은 단말에만 있다 |
| 로컬 stdio 서버 실행 통제 (allowlist / 코드서명) | 임의 `npx` 실행 차단 | 프로세스 기동은 단말에서 일어난다 (v1.7은 **탐지**까지) |
| 로컬 자격 저장소 감시 | 토큰 잔류 탐지 | OS 키체인은 네트워크에서 안 보인다 |
| 에이전트 런타임 후킹 | 모델이 만든 도구 호출을 강제 경로로 유도 | 클라이언트 프로세스 안에서만 가능 |
| EDR/MDM 연계 | 미등록 MCP 실행 알림 | 기존 단말 관리 체계 재사용 |
| 프록시 설정 강제 | 모든 MCP 트래픽을 게이트웨이로 | 단말 네트워크 설정이 강제 경로의 전제 |

마지막 항목이 두 평면을 잇는 지점입니다. **네트워크 평면의 강제 경로는
엔드포인트 평면이 프록시를 강제해야 성립합니다.** 그 강제가 없으면 게이트웨이는
"쓰기로 한 사람만 쓰는 관문"입니다.

## 2. 네트워크 평면 (망에 설치)

### 2.1 이 저장소에 구현된 것

| 구성요소 | 위치 | 역할 |
| --- | --- | --- |
| Security Gateway | `gateway/` · `127.0.0.1:8080` | 단일 정책 집행점(PEP). 모든 ingress가 `execute_call()`로 수렴 |
| OPA / Rego | `opa/` · 내부 `policy` 망 | 정책 결정점(PDP) |
| upstream 격리 | `compose.yaml`의 `tools` 망 | MCP 서버에 host port 없음 |
| loopback 게시 | `compose.yaml`, `compose.corporate-lab.yaml` | 8000/8080/16686/8088이 이 호스트 밖으로 나가지 않음 |
| 다른 게시 주소 거절 | `console.sh` | 예전 `BIND_ADDR`/`AIG_BIND_ADDR`에 127.0.0.1 외 주소가 있으면 기동 거부 |

### 2.2 네트워크단에 필요하지만 미구현인 것

[NETWORK.md](NETWORK.md)가 설계 기준을 담고 있습니다. 요약하면,

| 통제 | 상태 | 문서 |
| --- | --- | --- |
| tailnet ACL (주소가 아니라 태그로) | 미구현 | NETWORK.md §3.1 |
| `tailscale serve` (Funnel 금지) | 미구현 | NETWORK.md §3.2 |
| 조직 OIDC reverse proxy | 미구현 | README 13절 결정 |
| egress 허용목록 (MCP 서버 외 차단) | 미구현 | — |
| DNS 싱크홀 (미등록 MCP 도메인) | 미구현 | — |
| TLS 종료·mTLS | 미구현 | README 13절 |

### 2.3 egress와 DNS를 여기 적어 두는 이유

엔드포인트 평면이 섀도 MCP를 **발견**하면, 그것을 **차단**하는 것은 네트워크
평면입니다. 발견과 차단을 한 평면에서 하려 들면 둘 다 약해집니다. 엔드포인트가
차단까지 하면 1.2의 권한 문제가 생기고, 네트워크가 발견까지 하려면 모든 트래픽을
복호화해야 합니다.

현재 구현된 흐름은 발견까지입니다.

```
엔드포인트 에이전트 → 섀도 MCP 발견(설정 + 망 리스너) → Gateway 인벤토리
  → 그 사람의 호출에 MCP-SHADOW-001/002(Alert)로 증적 강화
  → A.I.G 동적 점검을 그 리스너에 직접 걸어 무엇인지 확인
  → (미구현) egress 허용목록에 반영해 실제 차단
```

네 번째 줄까지가 이 저장소이고, 마지막 줄은 조직의 네트워크 장비 몫입니다.

egress 판단 자체는 관리 평면에 들어왔습니다. `opa/data.json`의 `egress.allowed_hosts`가
등록 서버의 목적지를 제한하고 `MCP-EGRESS-001`이 그 밖의 목적지를 실행 전에
차단합니다. 다만 이것은 **게이트웨이를 지나는 호출**에만 걸립니다. 지나지 않는
호출을 막는 것은 여전히 네트워크 장비의 일입니다.

## 3. 관리 평면 (서버 측 정본)

| 정본 | 위치 | 무엇을 정하는가 |
| --- | --- | --- |
| Registry | `mcp_servers` / `mcp_tools` | 승인된 서버·도구·계약·행위 |
| 정책 관리대장 | `opa/policy_ledger.json` | Risk → Control → Policy → 버전 → 상태 |
| 예외 관리대장 | `opa/exceptions.json` | 완화의 범위·기간·보완통제 |
| 신원 관리대장 | `principals` | 역할·계정 상태 |
| 데이터 등급 관리대장 | `documents` | 분류와 그 출처 |
| **종료 케이스** | `termination_cases` | 이 이용 관계가 전주기의 어디에 있는가 |
| **회수 대상 / 증거** | `revocation_targets` / `termination_evidence` | 무엇을 회수해야 하고 무엇을 확인했는가 |

관리 평면은 스스로 아무것도 막지 않습니다. 네트워크 평면이 읽어서 막고,
엔드포인트 평면이 대조해서 보고합니다.

## 4. 세 평면이 한 번에 필요한 사례: 종료 판정

논문의 네 기준(C1~C4)이 어느 평면에서 채워지는지가 이 분리의 가장 좋은 예입니다.

| 기준 | 누가 채우는가 | 이 저장소의 구현 |
| --- | --- | --- |
| **C1 모집단** | 관리 평면 + **엔드포인트 평면** + 제공자 | 게이트웨이 원장의 호출 주체 + 엔드포인트 설정 잔존 + 제공자 고지(없으면 T3) |
| **C2 수행 권한** | 관리 평면 + 제공자 | 회수 대상의 `holder`와 제공자 증명 |
| **C3 연속성** | **네트워크 평면** | 차단 시각 이후 실행된 호출 수 = `decisions` 실측 |
| **C4 증거 접근** | 관리 평면 | 대상·시점을 특정하는 증거 대장 |

C3은 네트워크 평면만 답할 수 있습니다. "폐기 이후 이 서버로 실행된 호출이
0건"이라는 사실은 제공자의 응답이 아니라 **이 조직의 강제 경로가 만든 기록**입니다.
C1의 일부는 엔드포인트 평면만 답할 수 있습니다. 게이트웨이는 자기를 통과한
호출만 알기 때문입니다.

**그리고 C1의 나머지는 어느 평면도 답할 수 없습니다.** 원격 제공자가 하위
시스템에 대해 보유한 위임 자격은 제공자가 고지하지 않으면 존재 여부조차 알 수
없습니다. 그 경우 판정은 T3이고, 이 엔진은 T1을 주지 않습니다.

## 5. 배치 결정표

새 통제를 붙일 때 어느 평면인지 고르는 기준입니다.

| 질문 | 답 | 평면 |
| --- | --- | --- |
| 단말에만 존재하는 상태를 봐야 하는가? | 예 | 엔드포인트 |
| 호출을 실제로 멈춰야 하는가? | 예 | 네트워크 |
| 사람이 승인·기한·범위를 정하는가? | 예 | 관리 |
| 침해됐을 때 최악이 "거짓 보고"인가 "임의 실행"인가? | 임의 실행 | 엔드포인트에 두지 않는다 |
| 이 통제가 없으면 다른 통제의 전제가 무너지는가? | 예 | 네트워크 (강제 경로) |

## 6. 지금 구성의 한계

- ~~엔드포인트 에이전트는 관리자 계정으로 로그인합니다.~~ **v1.7에서 해결.**
  장치 자격으로 바뀌었고 그 자격은 `scopes`에 적힌 보고 외에 아무것도 할 수
  없습니다. 다만 키는 여전히 **공유 비밀**입니다. 운영에서는 디바이스 인증서나
  워크로드 신원(mTLS, SPIFFE)이어야 하고, 그러면 단말에서 키 파일이 유출돼도
  다른 장비에서 쓸 수 없습니다.
- 망 탐색은 **그 단말이 닿을 수 있는 범위**까지만 봅니다. 단말이 속하지 않은
  세그먼트의 MCP는 그 세그먼트에 에이전트가 있어야 보입니다. 커버리지의 분모를
  모른다는 아래 한계가 여기에도 그대로 적용됩니다.
- `initialize`에 답하지 않는 MCP 구현(인증을 먼저 요구하는 서버)은 `confirmed`로
  올라오지 않습니다. 프로세스 표지가 있으면 `suspected`, 없으면 보이지 않습니다.
  미탐이 남는 자리이고, 오탐을 줄이려고 고른 대가입니다.
- 커버리지의 **분모를 모릅니다.** 조직 전체 자산 목록이 없으므로 "몇 퍼센트를
  본다"에 답하지 않고 `known_endpoints`로만 말합니다.
- 설정 파일 대조는 **이름과 주소 기준**입니다. 같은 서버를 다른 주소로 적어 두면
  섀도로 분류됩니다. 오탐이 미탐보다 낫다는 선택이지만, 오탐이 많으면 아무도 이
  목록을 보지 않게 되므로 조직 배치 전에 정규화 규칙을 조정해야 합니다.
- 네트워크 평면의 차단(egress·DNS)은 미구현입니다. 발견까지가 이 저장소입니다.
