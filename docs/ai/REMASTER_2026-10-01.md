## 확인된 실패와 정정

클린 보드의 phase3은 실제 단말 설정 잔존을 T2로 올바르게 판정하면서 기존 종료 시험 2건이
실패했다. 판정 조건을 완화하지 않았다. 관리형 설정 생성기에 검토된 서버 제외 기능을 추가하고,
4개 실제 워크스테이션에서 설정 회수 → 실제 단말 보고 → 잔존 소멸을 검증하도록 고쳤다.
phase4 전체 검증은 통과했다. 실패 보고서도 클린 보드 reports에 보존한다.

1. **반복 OAuth**: 설치 CLI가 읽는 설정은 `mcp_oauth_credentials_store`다. 구버전 이름
   `mcp_oauth_credentials_store_mode`를 써 인증 결과가 encrypted store에 들어갔고, 파일 저장소만
   찾는 이관 코드와 불일치했다. 파일 모드로 수정한 후 5개 OAuth 자격을 정상 이관했다.
   GitHub 자격은 기존 연결에서 이관했고 Context7의 공개 도구는 익명으로 실제 응답했다.
2. **신청 흐름 누락**: 관리자 registry 직접 등록으로 임시 경로를 만들었다. 정상 도입 신청 기록은 없었다.
   이후 `pj1-log-*` 7개 경로를 해제했다. 승인 기록을 소급 생성하지 않는다.
   **정정(D-59, 2026-10-01 13시 실측)**: 해제한 것은 `pj1-log-*`뿐이었다. 02:47 KST에 같은 방식(신청 기록 없음)으로
   `context7`·`figma`·`supabase`·`notion`·`zapier`를 다시 직접 등록해 READY/ERROR로 남겨 두었고, 이 문서는 그것을
   적지 않았다. 이 커밋의 방어는 `intake_id`·`allowed_principals`가 있을 때만 걸려 이 등록들은 모든 직원에게 열려
   있었다. D-59에서 신청 기록 없는 Console 등록은 실행되지 않게 했고, 실기기 등록은 도입 신청으로 다시 했다.
3. **원격 신청 모델 결함**: 현재 도입 모델은 GitHub 구현 저장소를 필수로 요구한다.
   공급자 호스팅 SaaS MCP는 구현 소스가 공개되지 않을 수 있다. 문서 저장소 검사로 서비스 구현을
   검증했다고 할 수 없다. 원격 endpoint·도구 계약·자격 범위·퇴출 조건을 검토하는 신청 유형이 필요하다.
4. **감사 공백**: `/mcp/<미등록 id>/`는 초기화 단계에서 HTTP 404를 반환한다.
   `tools/call`까지 도달하지 않아 기존 decisions에 기록되지 않았다. 실제 연결 거부를 별도
   `event_kind=mcp-connection`으로 기록하도록 수정한다. 도구 실행 건수로 꾸미지 않는다.
5. **시험 범위**: `pj1-log-*`는 우리 Gateway의 임시 등록 id다. 공급자 MCP 구현은 수정하지 않았다.
   공급자별 읽기 도구 하나씩만 노출했다. Notion·Zapier는 도구 접근/작업 목록 메타데이터 조회이며,
   문서 검색·Zapier 작업 실행·Supabase 쓰기·Figma 편집을 검증한 것이 아니다.

이 수치는 해당 제한된 시험의 증거다. 전체 MCP 통합, 전 단말 통제, MCP Top 10 전수 대응,
타사 제품보다 우수하다는 근거로 사용하지 않는다.

PJ1 임시 봉쇄는 uid 1000의 IPv4/IPv6 TCP 출력에 적용했다. Gateway와 SSH 응답을 제외한
7개 공급자 직접 TCP 연결은 실패했고 Gateway 연결은 성공했다. root, 다른 사용자, 다른 기기,
UDP 및 재부팅 후 지속성은 이 확인 범위 밖이다. 정식 단말 집행과 별도로 기록한다.
