# 설계 결정 번호 251~300

## D-251 풀 연결 재획득은 명시적으로 검사하고 외부 작업의 직렬화는 유지한다 (2026-10-25, R-06)

- 이유: 연결을 점유한 채 풀을 다시 기다리면 작은 풀이나 동시 요청에서 진행이 막힌다. 반대로 연결만 합치면 정지 요청이 미커밋 상태로 가려지거나 완료 행을 잠가 정지 확인을 막는다.
- 결정: db 헬퍼는 선택 connection으로 기존 연결을 재사용한다. 기존 트랜잭션 안의 transaction context는 psycopg savepoint다. 로컬 계약·제어 정책 조회와 도입 승인·검토는 받은 연결을 쓴다. 등록 HTTP는 승인 커밋 후 실행하며 등록 오류는 승인 상태를 유지한다. 프로세스 잠금은 등록까지 유지한다. 자기 승인 거부 이벤트는 호출자의 롤백과 독립적으로 append한다.
- 운영 감시는 같은 키의 session advisory 잠금을 잡고 즉시 커밋한 뒤 주기 작업을 수행한다. 오류·취소 시 해제하며 해제 실패 시 연결을 닫는다. 잠금용 연결은 계속 점유한다.
- 검사기 tests/nested_tx_check.py는 명명된 함수·상대 import·위치/키워드 연결 인자를 AST로 추적한다. 자기 시험·미허용 재획득·낡은 ALLOW가 실패하면 코드 1이다. CI static에 연결했다. 동적 호출·속성·클로저의 한계는 보고서에 둔다.
- 보존: 토큰 잠금 안 중지 UPDATE의 독립 커밋, 사용자 중지, LiteLLM·운영 감시의 세션 잠금, 거부 감사, OIDC 회전, SIEM ACK 전 행 잠금은 같은 파일의 ALLOW 사유로 관리한다. IdP의 서명 폐기 기록은 asyncio.to_thread 완료를 기다린 후 기존 순서로 DB를 갱신·커밋한다.
- 검증(2026-10-26, Linux Python 3.13 + gateway 요구 패키지): pyflakes 0건, `nested_tx_check.py` 자기 시험 13건·위반 0·낡은 예외 0·허용 7, `nested_tx_refactor_check.py` 12건 통과, `run_local_suite.py` 통과 117·생략 17·실패 5(실패 5건은 main에서도 같은 실패, 회귀 0). PostgreSQL 경합은 CI `pg-suite`(0-2)에서 확인한다. 배포·실기기 미실행.
- 대안: 짧은 트랜잭션에서 xact 잠금을 풀면 다른 프로세스의 작업이 겹친다. SIEM 임대는 소유자·만료 열과 경합 검증이 필요해 스키마를 바꾸지 않았다. CI의 DB 경합·오류 복구에서 직렬화나 실패 차단이 깨지면 이 결정을 재검토한다.

## D-252 고정 독립 검토의 낡음은 PR 실패 대신 검토 갱신 대기로 남긴다 (2026-10-26)

- **이유:** `threat_trace_mapping_check.py`는 독립 검토의 고정 파일 해시·심볼/행·근거와 현재 코드를 대조한다. 참조 파일이 바뀌는 코드 PR마다 실패하므로 코드 회귀와 검토 기록의 낡음을 PR 관문에서 같은 실패로 다루면 0단계 병합을 막는다. 낡음을 통과로 표시하거나 해시만 자동 갱신하면 독립 검토의 의미가 사라진다.
- **결정:** EXTERNAL·KNOWN과 별도인 REVIEW_PENDING에 대상 파일과 갱신 사유를 명시한다. 시험은 계속 실제 실행하고 정상 완료된 assertion 불일치만 `검토 갱신 대기`로 보고한다. 이는 통과가 아니며 별도 집계하고 종료 코드 1을 만들지 않는다. 정상 통과하면 통과다. 실행/시험 예외, 0개 실행, 시간 초과, 비정상 종료는 계속 실패다. 대상은 inventory에서 local-suite를 유지한다. 제품 판정·정책 시험에 이 예외를 확장하지 않는다.
- **대안:** ① 기존 PR 실패 관문 유지는 참조 코드 변경마다 병합을 막으므로 기각. ② 시험 생략·삭제·일괄 통과 처리는 낡음과 도구 장애를 숨기므로 기각. ③ 파일 해시만 자동 갱신하는 방식은 재검토 근거가 없어 기각.
- **재검토 조건:** 0단계 코드 병합 뒤 별도 독립 에이전트가 병합 기준판의 변경 코드·시험·근거를 재검토한다. 이전 기록을 보존하고 새 기준판·검토자·시각·참조별 평가 및 대체 관계를 남긴 뒤 해시를 다시 고정한다. 그 결과를 리더가 반영하고 이 시험의 정상 통과를 확인한다. 재검토 완료 여부와 REVIEW_PENDING 지정 유지/해제는 그때 함께 확인한다.

## D-253 관리 계정의 Codex는 Codex 자체 샌드박스 대신 MINT AppArmor 경계로 실행한다 (2026-10-26)

- **이유:** 관리형 진입점의 Codex에서 셸 명령이 `Failed to create unified exec process: Permission denied (os error 13)`로 실패했다(팀원 보고, PJ1 재현). Codex는 셸 샌드박스를 만들 때 자기 바이너리를 `codex-linux-sandbox`로 다시 실행하는데 관리 프로필이 그 실행을 막았고(audit `denied_mask="x"`), 자기 재실행을 허용해도 다음 단계에서 bubblewrap(사용자 네임스페이스)을 요구했다.
- **결정:** 관리 계정 전용 Codex 실행기에만 고정 옵션 `-c sandbox_mode="danger-full-access"`를 넣는다. 명령 실행 경계는 기존 AppArmor 하네스→도구 프로필(실행 허용 목록, 파일 규칙, 브로커 접근 거부, nftables 송신 제한)이 맡는다. 공용 `/etc/codex` 설정·승인 정책·Claude 실행기·비관리 계정은 바꾸지 않는다. 하네스 본체 규칙은 `mr` 그대로다.
- **대안:** ① 자기 재실행(`mrix`)+bwrap·사용자 네임스페이스 허용 — 커널 공격면 확대(dev73에서 기각), PJ1에서 Ubuntu 기본 네임스페이스 제한에도 걸림. ② 공용 `/etc/codex`에 샌드박스 해제 — 같은 PC 일반 계정까지 바뀌어 기각.
- **반영:** 실행기는 키트 설치 때 만들어지므로 기존 PC는 새 키트 재설치가 필요하다. 이 고정 옵션은 D-238 통제 해시에 들어가지 않는다.
- **검증:** 실행기 렌더링 시험(관리 Codex에만 옵션, Claude·공용 설정 없음, 본체 `mr`). 실기기 확인은 배포 뒤 PJ1 재설치와 관리형 진입점 셸 실행으로 한다.
- **PR49 후속 보강(2026-10-26):** 관리형 Codex·Claude 실행기는 실제·유효 UID와 실행기 진입 시의 정확한 `mcpgw-<계정>-<하네스>-entry (enforce)` 라벨을 확인하고, 읽기 실패·불일치면 실행 전에 종료한다. 하네스 프로필로의 전환은 그 뒤 본체를 실행할 때 일어나므로 하네스 라벨을 미리 요구하지 않는다. Codex의 `-a/--ask-for-approval never`(붙임·등호·짧은 옵션 묶음 포함), `--dangerously-bypass-approvals-and-sandbox`, `--yolo`는 기존 인자 가드에서 거부한다. 홈·임시 경로의 쓰기 범위 축소는 후속 검토로 남긴다. 시험 결과와 미검증 범위는 루트 `REPORT-H49.md`에 기록한다.

## D-254 콘솔 인증서는 이름별로 선택하고 하네스 IP 신뢰 경로를 유지한다 (2026-10-26)

- **결정:** `FIELD_CONSOLE_TLS=none|tailscale|file`을 field와 운영 배포가 공유한다. 이름 기반 콘솔은 같은 Caddy의 443에서 SNI로 분기하며 기존 콘솔 스니펫을 재사용한다. IP·SNI 없는 연결의 사설 CA, 키트의 `IDP_ISSUER`와 MCP 공개 URL은 유지한다. 선택한 방식의 Compose 오버레이만 추가한다.
- **이유:** 브라우저의 실행 파일 다운로드에 신뢰할 수 있는 HTTPS를 제공하면서 기존 키트의 CA 핀과 장치 자격 경로를 바꾸지 않는다. Caddy 2.11.4의 내장 Tailscale 인증서 관리자를 사용하므로 새 의존성은 없다.
- **경계:** field 게시 IP는 기존 자동 검색 값만 쓴다. 소켓은 tailscale 방식의 root Caddy에만 읽기 전용으로 연결한다. 소켓의 API 권한 자체가 읽기 전용이 되는 것은 아니다. file 방식은 두 PEM 파일만 마운트하고 키의 그룹·기타 사용자 권한을 거부한다.
- **대안:** HTTP 8000의 일괄 리디렉션은 기존 주소와 내부 Git 접근의 동작을 바꾸므로 채택하지 않았다. HTTP 콘솔을 유지하며 안내 출력은 선택한 HTTPS로 바꾼다. 운영 배포에는 HTTP 포트를 추가하지 않는다. 하네스까지 DNS 이름으로 옮기는 것은 기존 키트·CA 경계를 바꾸므로 범위에서 제외한다.
- **검증 한계:** 정적·오프라인 검사와 일회용 컨테이너 검사를 분리한다. Docker 없는 환경의 결과는 Caddy 문법·Compose 렌더링·실제 인증서 발급 증거가 아니다. 재현 명령과 실행 결과는 루트 `REPORT-HTTPS.md`에 기록한다. HTTP 폐쇄가 운영 요구가 되면 구형 주소 사용 확인 뒤 리디렉션을 별도로 검토한다.

## D-255 Tailscale 소켓은 인증서 전용 컨테이너만 쓰고 Caddy는 비root로 돈다 (2026-10-26)

- **결정:** D-254의 "root Caddy에 소켓 연결"을 바꾼다. 소켓은 네트워크 없는 `console-cert` 컨테이너(읽기 전용 루트, 능력 전부 제거)만 마운트해 하루 한 번 `tailscale cert`를 받고, 새 쌍을 세대 디렉터리에 쓴 뒤 `current` 링크를 원자적으로 바꾼다. Caddy는 UID 10001·그룹 0으로 돌며 링크가 바뀌면 USR1로 다시 읽는다. 능력은 `NET_BIND_SERVICE`만 남긴다(이미지 바이너리의 파일 능력 때문에 없으면 실행 거부). HTTPS를 켜면 HTTP 8000은 이름 기반 주소로 301 리디렉트하고, none 방식에서만 콘솔을 그대로 준다. deploy는 `MINT_BIND`가 이 기기의 실제 Tailscale IPv4인지 확인한다.
- **이유:** 보안 검토에서 root Caddy+소켓(높음)과 평문 8000 잔존(중간)이 지적됐다. 소켓 API는 읽기 전용이 아니므로 외부 요청을 받는 프로세스와 분리한다.
- **반영:** 기존 root 소유 CA 볼륨은 시작 전 일회성 root 컨테이너가 소유권만 넘긴다(CHOWN·DAC_READ_SEARCH 능력만. 재배포 때 비root 소유 0700 디렉터리를 지나야 한다). 발급 실패 시 이전 쌍을 유지하고 컨테이너가 재시작된다.
- **검증:** `console_https_check.py --docker` 13개(인증서 게시·실패 시 이전 쌍 유지, 비root 기동, 리디렉트 4경로, 링크 교체 후 재적재·재시작 0회, 세 방식 Caddy 문법·Compose 렌더링).

## D-256 Windows 키트는 상태를 현재 언어로 표시하고 부분 관측은 실패 종료로 보지 않는다 (2026-10-26)

- 근거: 소유자 요청 P2-7/P3-8, PR #59 위의 Windows 키트 진단 수정.
- 결정: enum과 저장된 진단값은 표시할 때 번역한다. 트레이의 언어를 터미널에도 전달한다. active 상태에 남은 probe 대기 결과를 비워 기존 자동 점검으로 다시 측정하며 설치기의 probe 삭제와 상태 창 열기를 유지한다. OS 알림 영역 설정은 바꾸지 않는다.
- 관측 경계: agent --once는 partial을 0으로 종료하지만 게이트웨이에는 partial/incomplete_snapshot을 그대로 보고한다. 서비스도 partial 상태로 기록하고 실제 실패, 인가 실패, 시간 초과, 잘못된 출력은 오류로 남긴다. 판정과 관측 완전성은 바꾸지 않는다.
- 표시 이름: managed_policy의 서버 목록과 device_manifests의 응답에는 구조화된 표시 이름이 없다. harness_guidance 안의 정제된 Markdown 이름을 역파싱하지 않고 소유자 대안에 따라 ID를 그대로 표시한다. 게이트웨이 응답과 정책 해시는 변경하지 않는다.
- 검증: Windows 전체와 관련 오프라인 회귀 89건 중 87 통과, 환경 제약 2 생략. 실제 설치/모델/MCP 검수는 미실행. [검증 보고](../../research/llm-wiki/status/reports/2026-10-26-windows-tray-ux.md).

## D-257 Unix 키트는 등록·정책 수신 뒤 기존 설치를 교체한다 (2026-10-26)

- **이유:** Windows 실측 P0-2와 같은 선철거 순서가 Linux bootstrap과 macOS 설치기에도 있었다. Linux 제거 진입점은 config.json이 없는 상태 폴더를 놓쳤다.
- **결정:** managed-linux.enroll은 등록·정책 확인만 수행하고 결과는 root 프로세스 메모리로 전달한다. bootstrap은 그 뒤 이전 모드를 제거하고 파일·하네스를 배치한다. macOS도 계정·UID 소유를 확인한 뒤 먼저 등록한다. 관측용 install.py는 임시 설정의 1회 보고가 성공해야 기존 프로그램·설정을 교체한다(--no-verify 명시 사용 제외).
- **복구:** Linux는 상태 폴더·서비스 흔적을 인정하고 제거 실패를 전파한다. 설정이 없을 때 소유 불명 설정을 삭제하지 않는다. 런처 원본의 소유 정보나 로그인 셸 원복 정보가 없으면 보존하고 실패한다. macOS는 소유 기록이 없으면 계정·홈을 삭제하지 않고 알려진 서비스·방화벽 anchor·설정 백업만 정리한다. config.json 소실 시 PF 활성화 참조 번호는 복구할 수 없다.
- **진단:** 설치 단계·하위 stderr를 append하고 알려진 비밀값과 인증·토큰·비밀번호 줄을 제거한다. 명령 인자와 응답 본문을 예외 메시지로 출력하지 않는다.
- **Codex 설정:** 관리형 설치기는 사용자 마커를 편집하지 않는다. 다만 CA 키트에 함께 배포하는 `field/pc/mcpgw_pc.py`에는 범위 삭제 정규식이 있어 수정했다. 정확한 마커 줄 한 쌍과 기록한 렌더링을 비교하며, 구간에 직원 표가 끼거나 마커 중복·역순·미완성·여러 줄 문자열이면 원본 바이트를 별도 백업하고 실패한다. 정상 구간 밖의 CRLF·직원 표를 보존한다. 새 렌더링 기록이 없는 구판은 저장한 설정으로 재생성 가능한 블록만 인정한다.

- **한계:** 바로가기에 AppUserModelID를 넣지 않아 작업 표시줄 고정은 실행 파일 기준이다. 실측은 pj3 기존 설치에 바뀐 파일을 직접 넣어 확인했고, 새 키트 다운로드→원클릭 설치 전 과정은 기기 배포 뒤 확인한다. [작업 보고](../../research/llm-wiki/status/reports/2026-10-27-windows-gui-launcher.md).

## D-263 승인된 소스를 장치 자격으로 받아 Linux PC에서 고정 레시피로 빌드하고 이미지 ID로 격리 실행한다 (2026-10-27)

- **문제:** D-262 뒤 직원은 Gitea에 직접 닿을 수 없고, 기존 PC 실행 매니페스트는 내부 미러 이미지만 받아 승인된 저장소 MCP를 PC에 설치할 수 없었다. 계약 관찰에 빌드가 필요한데 내부 사본은 최종 승인 뒤에만 만들어지는 순환도 있었다.
- **결정:** 서명 매니페스트에 선택 `source`(커밋·소스 트리 sha256·레시피 ID/sha256·Dockerfile)를 넣고 `image`와 정확히 하나만 허용한다. 관리자는 저장소의 검증 완료와 고정 레시피를 확인해 소스 빌드를 지정하고 내부 사본을 먼저 대조·게시한다. 이것은 계약 승인이 아니다. 게이트웨이는 승인 기록을 잠근 상태에서 소스·레시피를 다시 대조한다. `GET /api/endpoint/local-sources/{server_id}`는 enforcement 장치 자격과 기존 `authorized` 검사를 요구한다. 관찰 전에는 지정 관찰 장치만, 관찰 후에는 사용 대상인 직원의 장치만 받는다. 받은 뒤 승인·정책 세대를 재확인하고 다운로드를 append-only 감사 경로에 기록한다.
- **Linux:** 기존 작업·사전 준비가 같은 함수로 다운로드→트리 해시 대조→`filter="data"` 압축 해제→고정 레시피 빌드를 수행한다. 최상위 폴더 하나를 제거하고 압축·해제 크기와 파일 수를 제한한다. 태그 `mcpgw-src/<server>:<manifest 앞 12자>`와 전체 매니페스트 라벨을 확인하고 `sha256:<64hex>` 이미지 ID만 실행한다. 준비 스레드와 작업 스레드의 빌드는 잠금으로 직렬화한다. 상태 파일에 서버·상태·이유를 담고 상태 화면의 `p`는 기존 로컬 소켓에서 등록 UID/root를 확인해 다시 준비하도록 알린다. 이 응답에는 토큰이 없다.
- **배치:** 게이트웨이는 이미 내부 Git 관리 자격과 ops 망을 갖고 있다. 망·자격은 추가하지 않고 base/field/deploy compose의 게이트웨이에 레시피 읽기 전용 마운트만 추가한다. 실행 격리·장치 정책·직원 자격 경계·사람의 계약 승인·원장 불변식은 유지한다. 레시피는 동일 파일을 콘솔과 게이트웨이에 배포해야 한다.
- **경계:** Windows 파일은 변경하지 않았다. 보안 업데이트 전 Python은 필터 없는 압축 해제로 후퇴하지 않는다. 실행의 네트워크 차단과 빌드 중 패키지 수신은 별개이며 전이 의존성의 고정·재현성, 침해된 root/엔진, 원격 빌더의 취소 후 잔여 작업은 보증하지 않는다. 소스의 최초 관찰에만 30분 준비 기한과 콘솔 프록시 대기 여유를 주며 일반 호출·실행 기한은 늘리지 않는다. 빌드가 사용자 로그인 기한을 넘기면 로그인 갱신 뒤 미리보기를 다시 연다.
- **시험:** `full_stack_lab/tests/local_source_check.py`(정상·매니페스트 반례·다운로드 중 철회/교체·크기 상한·다이제스트 불일치 시 빌드 금지·태그/라벨/ID·캐시·기한/취소·사전 준비·상태 화면·UID 제한), 기존 DEV-73 실행기·키트 회귀와 `open_endpoints.py`. 로컬 정적/대역 시험만 수행하며 실제 Linux 엔진·Gitea·PostgreSQL 경합·하네스는 미실행이다. 상세와 원자 요구사항은 [작업 보고](../../../research/llm-wiki/status/reports/2026-10-27-kit-source-linux.md)에 둔다.

## D-271 설치 결과는 등록 응답 대신 서비스의 최신 관리 상태를 표시한다 (2026-10-28)

- 원인: pj2 첫 설치의 등록 응답은 대기였으나 서비스의 첫 정상 보고가 간편 모드를 자동 활성화했다. Linux bootstrap은 연결 확인에 최신 상태를 쓰면서 JSON은 등록 응답 그대로 내보냈다. Windows도 등록 응답을 썼고, macOS는 상태와 관계없이 대기라고 출력했다.

- 적용: Linux 관리형 설치 결과와 bootstrap 완료 JSON·화면이 같은 서비스 상태를 쓴다. bootstrap 연결 확인은 추가로 60초를 기다리지 않는다. Windows 설치 JSON·격리 모드 안내·설치 마법사의 완료 문구, macOS JSON·완료 문구에도 같은 상태값을 반영한다. 새 의존성과 등록 API 변경은 없다.
- 시험: 수정 전 `kit_simple_mode_check.py`에서 기대 `active`에 등록 시점의 `pending-organization-activation`이 반환되는 실패를 재현했다. 수정 후 활성·대기·격리·철회·확인 불가, 자동 활성화, 낡거나 손상된 스냅숏을 단위 시험으로 고정했다. Windows는 등록 응답이 대기여도 최신 보고가 활성이면 JSON이 활성인 것을 실제 설치 함수와 OS/API 대역으로 검사했다. macOS 완료 문구도 반환 상태와 대조했다.
- 한계·대안: 등록 응답만 신뢰하는 방식은 자동 활성화 이후의 상태를 설명하지 못해 버렸다. 최대 60초 뒤에도 보고가 없으면 실패한 설치나 활성으로 추정하지 않으며 상태 확인이 필요하다. 실기기 재설치·GUI·하네스 확인은 이번 범위 밖이다.

## D-272 등록 파일을 소모한 키트 재실행은 기존 설치 안내만 한다 (2026-10-28)

- 원인: 등록 토큰을 한 번 사용하고 `enrollment.json`을 지우는 것은 의도된 경계지만, Linux bootstrap은 같은 폴더의 재실행을 파일 없음 오류로 끝냈다. macOS도 등록 파일을 먼저 읽는 구조다.

- 보안·범위: 소비한 토큰 복원·보관·재사용, 등록 API 재호출, 기존 설치 제거·활성화는 하지 않는다. Linux는 `mcpgw-status --check`, macOS는 기존 서비스 상태 텍스트를 읽는 `cat` 명령을 안내한다. Windows 원클릭은 매번 포함된 페이로드에서 등록 파일을 준비하고 기존 등록 거부 시 「이미 연결되어 있습니다」를 반환하므로 같은 파일 부재 경로가 없어 변경하지 않는다.
- 시험: 수정 전 기존 설치가 있어도 종료 코드 1인 반례를 재현했다. 수정 후 Linux 직원·격리 계정, 다른 직원·부분 설치의 음성 조건, macOS 기존 설치를 임시 상태 폴더로 검사하고 등록·제거 함수 미호출 및 등록 파일 부재 유지를 확인했다. 실제 설치 상태·서비스 연결 여부의 증거는 별도다.

## D-291 키트가 장치 자격으로 승인된 MCP 목록과 소스를 받는다 (2026-10-28)

- 한계: 실제 장치·Gitea 연동은 기기 이미지에서 확인해야 한다(psycopg·fastapi 필요 시험).

- 결정: 배포되는 키트·시험의 시험 장비 실주소를 문서용 대역(RFC 5737 `192.0.2.x`)으로 바꾸고, 옛 검증 기록 문서·증거 JSON·`docs/design/NETWORK.md`는 `<솔루션 주소>` 같은 자리표시로 바꿨다. `full_stack_lab/tests`의 주소 기본값은 환경 변수(`TEST_GATEWAY_URL` 등)로만 받는다.
- 검사: `deploy/check.py`가 키트·배포 대상·옛 검증 문서에서 사설(10/8, 172.16/12, 192.168/16)·Tailscale(100.64/10) 대역 실주소 리터럴을 실패로 센다. 네트워크 대역 표기(예: `10.0.0.0/20`)와 문서용 대역은 허용한다.

## D-293 키트 화면: 블록 글자 배너와 카드형 GUI (2026-10-28)

- 결정: 터미널 키트 화면은 MINT 블록 글자 배너(256색·트루컬러에서 청록→초록 줄 그라데이션, `NO_COLOR`·비 UTF-8·비대화형은 `#` 단색)와 번호 시작 안내(로그인·상태 확인·승인된 MCP)를 앞세우고 장치·게이트웨이·최근 보고·승인된 MCP를 라벨·값으로만 보인다. Windows 설치 마법사·트레이 창은 왼쪽 메뉴(상태·승인된 MCP·로그인/계정·설정)와 오른쪽 둥근 흰 카드 격자, 청록 포인트로 바꾸고 프로세스를 DPI 인식으로 올린다. 문구는 기존 `T` 번역 표에 두고 설명 문단을 쓰지 않는다. 새 런타임·의존성은 없다(WinForms).

## D-294 Windows 승인 서버는 표시 이름으로 보이고 PC 격리 실행 서버는 정책에서 뺀다 (2026-10-28)

- 원인: Windows 트레이의 「승인 서버」가 서버 id를 보였고, Windows에는 PC 격리 로컬 실행기가 없는데 `deployment=local` 서버(예: 메모리 MCP)가 승인 목록에 올라 호출하면 `MCP-CATALOG-001`로 실패했다(실제 Windows VM 확인).
- 결정: `managed_policy`는 Windows 장치에서 `deployment=local` 서버를 `servers`·managed-mcp 파일에서 제외한다(Linux·macOS 동일). 정책에 `server_names`(id→표시 이름)를 더하되 `control_hash`·옛 판본 해시 계산에서는 뺀다. 이름이 바뀌어도 장치가 통제 변경으로 격리되지 않게 하기 위해서다. Windows 서비스는 상태 파일에 `server_names`를 쓰고 트레이·`windows_status.py`는 이름을 우선 보이며 옛 상태 파일은 id로 내려간다.

## D-295 키트 설치·상태 화면의 직원 경로 점검 수정 (2026-10-28)

- 원인: PJ1·pj2 실기기에서 직원 경로를 그대로 밟아 보니 (1) 틀린 비밀번호·주소에서 설치가 곧바로 끝나고 「연결 등록·정책 수신에 실패」로 보였으며 로그인이 「구성요소 확인」 단계 안에 있었고, (2) Ctrl-C·입력 끝(EOF)·`mcpgw-status --sources` 취소·비대화형 실행이 파이썬 트레이스백을 냈고, (3) 로그인 화면의 「1 로그인 · 2 상태 확인 · 3 승인된 MCP」는 고를 수 없었고, (4) 설치 끝과 `--remove`가 JSON 한 줄을 그대로 찍었고, (5) 계정 중지·잠금이 모두 「계정 잠김·승인 확인 필요」로만 보였고, (6) 제거 뒤 `/usr/local/lib/mcpgw-managed`에 키트 사본이 남았고, (7) 브라우저가 같은 이름 파일에 「(1)」을 붙이면 콘솔 명령이 예전 키트를 풀었다.
- 결정: 로그인을 패키지 설치보다 앞에 두고 아이디·비밀번호·주소·네트워크 실수는 이유를 보이며 3회까지 다시 묻는다(스킴 없는 주소는 https://로 보정). 중지·잠금·승인 대기·시도 제한은 게이트웨이 문구를 그대로 보이고 바로 끝낸다. Ctrl-C는 한 줄 안내(종료 130), 터미널이 아닌 실행은 화면 없이 「터미널 입력 필요」. 번호 메뉴 줄은 뺀다. 모델 로그인이 만료된 하네스 응답은 「로그인 필요」로 표시한다. JSON 결과는 표준 출력이 터미널이 아닐 때만 낸다. 마지막 연결을 제거하면 키트 사본도 지운다. 콘솔 Linux 명령은 `~/Downloads`의 가장 최근 `mcp-managed-kit-linux*.zip`을 푼다.
- 한계: Linux(pj1·pj2)에서 확인했다. Windows·macOS 설치 마법사의 같은 재시도 규칙은 이번 범위가 아니다(macOS는 같은 bootstrap을 공유). 장치 제거 때 게이트웨이의 장치 기록을 닫는 호출은 없다.
