# 설계 결정 번호 201~250

## D-201 서버별 동의 요청·일괄 결정과 도구별 감사 기록을 함께 유지한다 (2026-10-23, W15-CONSENT-UX)

- 결정: 첫 동의 부족 차단에서 같은 직원의 서버 이용 승인·도구 심사·PAC 노출 권한에 속하는 동의 필요 도구를 현재 호출 등급으로 함께 대기시킨다. 정상 동의·명시적 거부는 보존하며 묵시적 동의는 만들지 않는다.
- 콘솔은 서버별 대기 묶음과 모두 허용·모두 거부를 제공한다. 결정은 화면에서 확인한 ID 집합으로 한정하고 본인·서버·현재 상태가 모두 일치해야 처리한다. 일괄 결정과 도구별 감사 사건은 하나의 트랜잭션이다.
- 심사 조건 변경·등급 상승·만료·철회는 다시 동의해야 한다. 도구·등급·조건 해시 단위 저장 및 전송 직전 공유 잠금 재검증은 유지한다. 서버 전체에 무기한·미래 도구 포괄 동의를 부여하지 않는다.
- 이유: PJ1 Claude 실사용에서 filesystem 도구 6개를 처음 사용할 때 각각 중단됐다. UI 상호작용을 합치되 정책·데이터 권한은 그대로 둔다. 신규 라이브러리 없이 기존 psycopg 트랜잭션·PAC·심사 범위를 재사용한다.
- 근거·시험·한계: [분석](../../research/llm-wiki/analysis/consent-per-server-1023/README.md), [보고](../../research/llm-wiki/status/reports/2026-10-23-consent-per-server.md). 오프라인 대역 시험이며 실제 DB·MCP·PJ1·브라우저 검수는 미실행이다. 커밋·기기 접속 없음.

## D-202 출력 자격 증명 보류는 구조화된 `키=값`에만 적용하고 문서 속 예시는 문자열 단위로 가린다 (2026-10-23)

  Gitleaks·개인정보 잔여 검사, 실패 시 보류는 그대로다.
- **시험**: `full_stack_lab/tests/output_credential_span_check.py`(게이트웨이 이미지, 2건). 기존 `mcp_result_contract_check`·

## D-203 로컬 MCP 호출은 컨테이너를 한 번만 띄운다 — 호출의 initialize·tools/list는 승인 계약으로 답한다 (2026-10-23)

- **문제**: 게이트웨이가 로컬 MCP 호출마다 initialize·tools/list·tools/call을 각각 PC 작업으로 보내 컨테이너가 세 번 떴다
  (각 3~4초). 호출 전체 시간 안에서 마지막 작업이 남은 시간 없이 시작돼 바로 만료되거나(`TimeoutError`), PC 러너가
  `/control`의 기한 경과로 컨테이너 전에 실패했다(PJ1 sequentialthinking·read_multiple_files).
- **결정**: 호출(전송 신원이 있는 세션)에서는 `LocalClient`가 initialize를 고정 프로토콜(`registry.pinned_protocol`)로,
  tools/list를 `mcp_tools`의 승인 설명·입력/출력 스키마로 답한다. 실제 대조는 PC 러너의 tools/call 작업이 컨테이너 안에서
  initialize·tools/list를 하고 승인 해시(설명·입력·출력 스키마)와 프로토콜을 비교한 뒤에만 호출하므로 통제가 줄지 않는다.
  승인 전 관찰·등록(`discovery`)은 지금처럼 실제 서버에 묻는다.
- **시험**: `local_jobs_pg_check.py`에 "호출은 initialize·tools/list 작업을 만들지 않는다" 추가(운영 DB를 비우는 시험이라
  기기에서는 돌리지 않음). 오프라인 `dev73_*`·`local_runner_usability_check` 통과. 실증은 PJ1 실제 호출.

## D-204 인자 이름 `to`만으로 메일 수신자로 보지 않는다 (2026-10-23)

- **문제**: PAC 매개변수 사실(`pac.facts`)이 `to`·`cc`·`bcc`·`recipient` 이름의 모든 문자열을 수신자 대상으로 보고 조직 메일 도메인
  목록과 대조했다. memory MCP의 `create_relations`(`{"from": "MCP Python SDK", "to": "stdio"}`)가 PAC-10으로 막혔다.
- **결정**: 값이 주소 형태(`@` 포함)이거나 분류기가 이 호출에서 메일 목적지(`Destination.kind == "email"`)를 찾은 경우만 수신자다.
  파일 경로가 "이 서버의 검토된 추출기가 경로로 분류한 것만 대상"인 것과 같은 원칙이다. 주소 형태 값은 지금처럼 도메인 검사를 받는다.
- **한계**: 주소가 아닌 수신자 식별자(채팅 채널 등)를 받는 도구는 분류기가 메일로 읽지 않으면 수신자 범위 검사 대상이 아니다.
  이전에는 그런 값이 도메인 목록을 통과할 수 없어 항상 막혔다. 목적지·외부 전송 통제는 그대로 적용된다.
- **시험**: PJ1 실사용(memory `create_relations`), 게이트웨이 이미지 `pac_boundary_check`·`adversarial_check`.

## D-205 엔드포인트 관찰기는 승인된 로컬 MCP 컨테이너의 프로세스를 미등록 MCP로 보고하지 않는다 (2026-10-23)

- **문제**: 키트의 로컬 실행기가 관리 계정 UID로 띄운 승인 MCP 컨테이너의 프로세스(`node … mcp-server-…`)를 같은 PC의
  `agent.stdio_processes`가 "설정에 없이 실행된 stdio MCP"로 보고해, 승인된 로컬 MCP를 부를 때마다 `MCP-SHADOW-002` 경보가 붙었다(PJ1).
- **결정**: 프로세스의 cgroup에서 컨테이너 ID를 읽어 엔진(`docker`/`podman inspect`)의 `mcpgw.local=1` 라벨이 있으면 제외한다.
  라벨 컨테이너는 root나 엔진 권한 그룹만 만들 수 있고, 그 권한이면 이미 PC에서 무엇이든 할 수 있으므로 우회 경로를 넓히지 않는다.
  컨테이너 밖이거나 라벨이 없는 프로세스는 지금처럼 보고한다.
- **시험**: `endpoint_collector_check.py`(라벨 컨테이너 프로세스 제외, 다른 UID 제외, 명령행 해시). 실증은 PJ1.
## D-206 공식 MCP의 PC 격리 실행 기본값을 승인 화면이 미리 채운다 (2026-10-23)

- **문제**: 도입 신청한 stdio 공식 MCP를 승인하려면 관리자가 「PC 격리 실행」 창에 이미지·실행 인자·폴더·환경 변수를 손으로 넣어야 했다.
  10-23 실사용에서 memory는 호출마다 새 컨테이너라 `/tmp` 저장이 사라져 그래프가 비었고, 영구 폴더와 `MEMORY_FILE_PATH`를 넣어 다시 승인했다.
  환경 변수 입력란은 화면에 아예 없어(`env: {}` 고정) 화면만으로는 그 설정을 할 수도 없었다.
- **결정**: `intake_proposal.LOCAL_RUN_PRESETS`(한 곳의 작은 표)가 공식 저장소(`modelcontextprotocol/servers`)의 알려진 경로만 제안한다.
  filesystem `/workspace/mcp-docs`·`mcp-docs:ro`, memory `mcp-memory:rw`+`MEMORY_FILE_PATH=/workspace/mcp-memory/memory.json`,
  git `--repository /workspace/mcp-repo`·`mcp-repo:ro`, sequentialthinking·time은 마운트·환경 없음. 승인 미리보기가 `local_run_preset`으로 돌려주고,
  `askLocalRun`은 저장된 값이 없을 때만 미리 채운다(환경 변수 입력란 추가). 값은 라벨과 입력란에 그대로 보이며 관리자가 바꾼다.
  다른 저장소의 같은 경로·모르는 경로는 빈 제안이다.
- **불변**: 제안은 화면 초기값일 뿐이다. 저장은 기존 `LocalRunSpec`·`local_jobs.manifest_errors`·허용 이미지 저장소·digest 고정·서명 흐름을 그대로 거친다.
  쓰기 가능(rw) 기본값은 저장형 memory 하나뿐이다(시험이 고정).
- **근거와 한계**: 공식 README 5개의 판본·행은 `research/llm-wiki/analysis/local-run-presets-1023/`. 폴더 이름(`mcp-docs`·`mcp-repo`·`mcp-memory`)은 PC 홈의 관례 이름이라
  실제 문서·저장소 폴더 이름이 다르면 관리자가 고친다. README의 memory 예시 파일은 `.jsonl`이고 표는 PJ1에서 통과한 `memory.json`을 쓴다.
  git은 읽기 전용 마운트라 쓰기 도구(add·commit)는 실패하고, 읽기 전용에서의 `git status`·소유자 불일치 동작은 기기에서 확인한다.
- **시험**: `local_run_presets_check.py`(선택·빈 제안·표의 모든 값이 기존 요청 모델과 매니페스트 검사를 통과), `console-state` 노드 시험, 기존 승인·실행기 시험.

## D-207 루트 전용 공식 이미지(git·time)는 기본값에서 빼고 상태만 보인다 (2026-10-23)

- **문제**: D-206 표가 git·time도 제안했지만, 10-23 PJ1(Ubuntu, Docker 29.8.1, 사용자 재매핑 없음) 실측에서 `mcp/git`·`mcp/time`은 러너 옵션
  (`--user 1001:1001 --read-only --tmpfs /tmp --cap-drop=ALL --network=none`)으로 `exec /app/.venv/bin/mcp-server-{git,time}: permission denied`로 끝났다. 승인해도 실패한다.
- **원인(실측)**: 두 이미지의 `/app/.venv/bin/python`은 `/root/.local/share/uv/python/cpython-3.10.18-…/bin/python3.10`으로 가는 링크이고 `/root`가 `drwx------ root`다(USER 미지정=root).
  비루트 UID는 `/root`를 지날 수 없다. 캐시·HOME·tmpfs 문제가 아니므로 환경 변수(HOME 계열은 러너가 금지)나 tmpfs로 풀 수 없다.
  시스템 python3.12로 우회해도 패키지가 cp310 확장 모듈(`pydantic_core`)이라 로드되지 않고, 매니페스트는 entrypoint를 바꿀 수 없다. filesystem·memory·sequentialthinking은 node 이미지라 영향이 없다.
- **결정**: 컨테이너를 root로 돌리거나 capability를 더하지 않는다(재매핑 없는 호스트에서 탈출 시 호스트 root). `LOCAL_RUN_PRESETS`에서 `src/git`·`src/time`을 빼고
  `ROOT_ONLY_IMAGES`로 모아, 승인 미리보기가 `local_run_status`(「관리 계정으로 실행할 수 없는 이미지」)를 돌려준다. 「PC 격리 실행」 창은 이 문구를 경고 칩으로 보이고
  이미지 입력란을 비워 둔다(설명 문단 없음). 관리자가 비루트로 다시 만든 사내 미러 이미지를 직접 넣는 길은 그대로 열려 있다.
- **불변**: `LocalRunSpec`·`manifest_errors`·러너의 `--user`·`--cap-drop=ALL`·허용 환경 변수는 바꾸지 않았다.
- **한계와 후속**: 진단 실험(컨테이너 안에서만 `/root`를 711, uv 디렉터리를 go+rX로 연 뒤 UID 1001로 `mcp-server-time` 실행)에서는 `initialize`가 통과해
  `/root` 통과 권한만 고친 사내 재빌드 이미지는 비루트로 동작할 것으로 보이나, 재빌드 이미지는 만들지 않았고 digest·서명 흐름 검증도 하지 않았다.
  같은 uv 방식으로 빌드된 다른 공식 파이썬 이미지(예: fetch)도 같을 가능성이 있으나 이미지를 받지 않아 확인하지 못했다. D-206의 git·time 항목을 정정한다.
- **시험**: `local_run_presets_check.py`(두 경로는 빈 제안+상태 문구, 나머지는 빈 문자열, 표와 겹치지 않음, 배선), 기존 승인·러너 시험.
## D-208 LiteLLM 승인·철회를 선택 애드온으로 전파하고 재조회한 관리 상태를 사건 원장에 남긴다 (2026-10-23)

- **결정**: MINT 등록 완료·등록 해제·공급망 중지·종료/폐기에서 서버별 영속 대기열을 갱신한다. 5초 상태 대조가 누락과 기한 만료를 보완한다. LiteLLM 1.105.0 관리 API로 서버·키/팀 승인 도구를 반영하고, 철회 시 서버·BYOK/OAuth 저장 자격·열거한 사용자의 워커별 세션을 정리한다. HTTP 성공 응답과 독립된 GET 상태를 확인한 뒤에만 완료한다.
- **이유**: 기존 호출 판정 애드온만으로는 관리 화면의 승인 상태와 폐기 전파를 일치시키지 못한다. 기존 MCP/ACL/자격 저장 기능은 LiteLLM API를 사용하고 새 MCP 서버나 권한 엔진은 만들지 않는다. 공식 v1.105 태그, 릴리스 commit 80b9556dd312d18c535ae06884faa97d1fdb8f46과 읽은 심볼·행·라이선스·확보 한계를 분석에 남겼다.
- **경계**: 기본 꺼짐이며 새 동기화 경로는 직원 MINT 토큰이나 upstream 비밀을 LiteLLM에 보내지 않는다. 관리 키는 파일/환경 변수 참조로 매 요청 다시 읽는다. 사용자·키 해시·팀을 명시적으로 연결하고 현재 키 소유자와 팀 구성원을 재조회한다. require_key_mcp_access_defined=true가 확인되지 않으면 신규 경로를 만들지 않는다. 다른 표식의 서버는 인수하지 않으며 자격·신원 설정을 낮춰 호환시키지 않는다.
- **증거·실패**: approval_events에 litellm-sync/G5 사건만 추가한다. litellm_sync_jobs는 원장이 아닌 수정 가능한 작업 상태다. 실패는 최대 300초 간격으로 재시도하고 화면에 동기화 실패를 표시한다. 자격 삭제 전 소유자 목록을 확보하지 못한 경우 모집단 확인불가를 보존하며 재시도 뒤 빈 목록만으로 완료하지 않는다. 기존 판정 행과 종료 등급 조합은 수정하지 않는다.
- **대안·되돌릴 조건**: 응답 코드만 보고 완료하거나 직원 토큰·공유 자격을 복제하는 방법은 증거와 자격 경계를 충족하지 않아 제외했다. LiteLLM API/ACL 계약이 달라지면 URL 설정을 비워 애드온을 중지하고 새 판본에서 계약·시험을 다시 검토한다. 꺼짐은 이미 남은 외부 경로를 삭제하는 조치가 아니므로 철회가 필요하면 켜진 상태에서 재조회까지 마친다.
- **검증/한계**: 신규 HTTP 대역 21건과 기존 운영23/SBOM8·화면 상태15/UI6 통과. 실제 LiteLLM1.105·PostgreSQL·PJ1·브라우저는 미실행. 기존 애드온 회귀와 pyflakes는 로컬 의존성 부족으로 미실행이다. 현재 신규 등록은 자격 없는 HTTP에 한정하며 로컬 stdio·인증 설정 복제·공급자 토큰 원격 폐기·SSE/stateless·미열거 워커는 입증하지 않는다. ## D-217 같은 직원·같은 PC의 재설치는 직전 활성 장치를 대체하고 활성화를 이어받는다 (2026-10-23)

- 배경(PJ1 10-23 16:20): 키트 업데이트는 새 zip의 `install.sh` 재실행인데, 매번 새 장치 ID가 `pending`으로 시작해 관리자가 다시 활성화해야 했다. PJ1에는 active 기록이 10개(8개는 보고 끊김)였다.
  재설치 정리(D-192)가 이전 기록을 찾지 못한 원인은 `platform` 비교였다. 관측기의 enroll 보고가 `platform`을 `Linux 6.8…`로 덮어써 `'linux'`와 같지 않았다.
  그 밖에 하네스(`claude mcp list`)에는 대기 중에도 401 「인증이 만료되었거나 유효하지 않습니다」만 보였고, 직원이 볼 상태 확인 수단과 키트 판본(`/api/health`의 `pc_kit_sha256` null)이 없었으며, 대기 중 로컬 실행기가 2초마다 `HTTPError`를, 결속 검사가 거짓 `profiles-not-enforcing`을 남겼다.
- 결정 1(이어받기): `endpoint_plane.consume_enrollment`는 같은 직원 계정·같은 관리 계정 이름·같은 PC의 이전 장치(`status=active`)를 찾는다. `platform` 열은 비교하지 않고 `managed_platform`(detail)만 쓴다.
  같은 PC는 둘 다 `machine_id`(Linux `/etc/machine-id`에 고정 문구를 붙인 SHA-256, 원본은 보내지 않음)가 있으면 그 값으로, 없으면(이전 키트·macOS) 호스트 이름으로 본다. Windows는 계정 SID도 같아야 한다.
  가장 최근 이전 장치가 `managed_state=active`이고 승인자가 있고 그 장치 범위의 `local_run_stops`가 없으면, 새 장치를 `active`로 만들고 승인자·승인 시각을 물려받아 `activated` 이벤트(`inherited_from`)를 남긴다.
  격리된 장치, 활성화 전 장치, 등록 해제(`revoked`) 장치, 로컬 실행이 중지된 장치는 이어받지 않고 `pending`으로 시작한다(재설치로 보류를 풀 수 없다). 다른 PC·다른 직원은 지금처럼 `pending`이다.
  어느 경우든 이전 기록은 `revoke_device(…, "reinstall")`로 폐기해 토큰을 함께 철회하고 `detail.superseded_by`에 새 장치를 남긴다.
- 보안 경계: 신원은 그대로 transport 토큰에서만 정해진다. 이어받은 장치도 첫 보고가 정책·집행 점검에 맞아야 하고(보고가 없으면 토큰 발급 불가, 어긋나면 격리) 기존의 관리자 승인에 기대지 새 승인을 만들지 않는다. 같은 호스트 이름의 다른 PC 복제는 `machine_id`가 달라 이어받지 못한다.
- 결정 2(대기 사유): 헤더 도우미는 서비스가 알려 준 상태에 따라 고정 거부값 `Bearer endpoint-not-active.pending|.quarantined`를 출력한다(서비스가 없으면 기존 값). `agent_contract.authenticate`가 이 값을 서명 검증 전에 401로 거절하며 사유 문장(「이 PC는 관리자 활성화를 기다리는 중입니다…」)을 응답 `detail`에 실어, 하네스가 보여 주는 401 줄에 대기 사유가 나온다. 자격으로는 어디에서도 통하지 않는다.
- 결정 3(상태 명령): Linux 서비스가 `/usr/local/lib/mcpgw-managed/status-<계정>.json|txt`(root 소유, 0644, 요약만)를 매 주기에 쓰고, `mcpgw-status`(= `managed-linux.py status`)가 장치 상태(활성/활성화 대기/중지)·게이트웨이 연결·마지막 보고·승인 서버 수·키트 판본을 한국어로 보인다. 180초 넘게 갱신이 없으면 「확인 안 됨」이다. 프로필 안의 계정은 Python을 못 돌려 `cat …/status-<계정>.txt`를 쓴다.
- 결정 4(판본): 키트 판본은 설치되는 프로그램 7개(`PROGRAM_FILES`)의 줄바꿈 정규화 SHA-256이다. `/api/health`의 `pc_kit_sha256`이 게이트웨이에 마운트한 키트 폴더(`compose.field.yaml`의 `../endpoint-agent:/endpoint-kit:ro`)에서 호출마다 계산하고, 상태 명령이 설치본의 앞 12자리를 보인다.
- 결정 5(로그): 로컬 실행기는 게이트웨이가 401·403·409로 거절하면 `{"local_runner":"waiting","status":…}`를 한 번 남기고 간격을 2초에서 30초까지 늘리며, 풀리면 `ready`를 한 번 남긴다. 결속 검사의 `enforcing_profiles/kernel_ready(username, harnesses, mode)`는 설치 단계(`warn`은 기존 프로필, `enforce`는 결속 프로필)와 D-216의 하네스 목록에 맞는 프로필만 요구한다.
- 시험: `full_stack_lab/tests/kit_continuity_check.py` 21건(수정 전 코드에서 19건 실패, 2건은 Linux 전용), 기존 `header_broker_label_check.py`의 설치기 복사 단언을 `PROGRAM_FILES`로 바꿨다. DB는 대역이라 집행·실기기 증거가 아니다.
- 한계: macOS는 `machine_id`를 보내지 않아 호스트 이름으로만 같은 PC를 본다. Windows·macOS 키트에는 같은 이름의 상태 명령이 없다(Windows는 트레이 표시). 하네스가 401 본문을 항상 보여 주는지는 PJ1에서 확인해야 한다. 이미 설치된 장치는 키트를 한 번 다시 설치해야 `machine_id`·상태 명령이 생기고, 그 재설치는 호스트 이름으로 이어받는다.

## D-219 관리형 Claude Code는 계정 동기화 플러그인과 웹 도구도 닫는다 (2026-10-23)

- 배경(PJ1 10-23, Claude Code 2.1.288, 관리 계정): 관리형 프로필(`disableClaudeAiConnectors`·`allowManagedMcpServersOnly`)이 있는데도 `claude plugin list`에 계정에서 동기화된 `productivity@synced`·`engineering@synced`·`pdf-viewer@synced`가 `loaded`였고, `claude -p`의 WebSearch가 열려 실제 검색 결과를 돌려줬다(WebFetch는 모델 프록시가 `proxy refused`로 막음). 커넥터 서버만 닫고 계정 쪽 두 경로를 닫지 않았다.
- 결정: 관리형 `managed-settings.json`(`endpoint_plane.managed_policy`, 키트 `mcpgw_pc.py managed`)에 다음을 더한다.
  - `syncClaudeAiPlugins: false`, `syncClaudeAiSkills: false` — 계정에 켠 플러그인·스킬의 내려받기와 이미 받은 것의 로드를 멈춘다. 공식 문서상 `false`만 효력이 있고(`true`는 미설정과 같음) 사용자·로컬·관리형 범위에서 읽는다. 관리형 범위에서는 받아 둔 것을 `~/.claude/plugins/.trash/`로 옮긴다. 플러그인 쪽은 v2.1.273 이상(PJ1은 2.1.288), 스킬 쪽 최소 판본은 문서에 없다.
  - `permissions.deny: ["WebFetch", "WebSearch"]` — 프록시가 막는 WebFetch도 설정으로 막고, 프록시로 막지 못한 WebSearch를 닫는다.
  - `allowManagedPermissionRulesOnly: true` — 사용자·프로젝트·로컬·`--settings`의 allow/ask/deny와 `--allowedTools`를 무시해 직원이 deny를 다시 열지 못한다. 문서는 이 키가 MCP 허용 목록을 잠그지 않는다고 따로 밝히므로 `allowManagedMcpServersOnly`는 그대로 둔다.
  - `permissions.allow: ["mcp__<서버>", …]`(Gateway에 라우팅된 서버만) — 위 키로 `--allowedTools`가 무시되면 `claude -p`가 Gateway 도구를 부를 수 없게 되므로, Codex의 `default_tools_approval_mode = "approve"`와 같이 하네스 승인은 미리 주고 판정은 Gateway가 한다. 서버 목록이 바뀌면 설정 해시가 바뀌어 단말이 다시 받는다.
- 출처: https://code.claude.com/docs/en/settings-reference.md (`syncClaudeAiPlugins`·`syncClaudeAiSkills`·`allowManagedPermissionRulesOnly`·`permissions.deny` 항목), https://code.claude.com/docs/en/managed-mcp.md (`allowManagedMcpServersOnly` 구분, `allowAllClaudeAiMcps`, `serverUrl` 규칙). 2026-10-23 WebFetch로 대조.
- 시험: `tests/command_surfaces_check.py`의 `check_connector_surfaces`를 키트 managed·`managed_policy`(Linux·Windows)에 적용(수정 전 KeyError로 실패). 워크스테이션 이미지 템플릿은 이미 WebFetch/WebSearch를 거부한다.
- 한계: 설정 파일이 맞다는 시험이며 실제 차단은 PJ1에서 `claude plugin list`(synced 없음)·`claude -p` WebSearch(거부)로 확인해야 한다. Desktop·웹·다른 클라이언트는 이 설정 밖이다. 이미 받아 둔 동기화 플러그인은 설정이 내려간 뒤 다음 Claude Code 시작 때 휴지통으로 옮겨진다.

## D-220 관리 단말은 자기 하네스의 커넥터·기능을 장치 자격으로 보고하고, 그 보고는 소유자의 관리 단말 상태로 판정한다 (2026-10-23)

- 배경: 인벤토리 보고(`mcpgw_pc.py report`)는 직원 토큰을 쓰는 비관리 설치에서만 돌았다. 관리 계정(`managed-<직원>`)은 키트를 쓰지 않아 PJ1의 `harness_items`가 0행이었고, `integrations.snapshot`은 하네스 보고 항목마다 `endpoint_item_state(None, …)`를 호출해 어떤 항목도 `endpoint_enforced`가 될 수 없었다(보고가 직원 토큰으로 오므로 맞는 보수적 선택이었다).
- 결정 1(수집): `endpoint-agent/managed-linux.py serve`에 스레드를 더해 60초 뒤부터 6시간마다 수집·보고한다(실패는 15분 뒤 재시도, heartbeat와 무관). 관리 계정의 `claude`·`codex` 실행기(`/usr/local/lib/mcpgw-enforcement/mcpgw-<계정>/`)를 `setpriv`로 그 계정 권한에서 돌린다(`subprocess(user=)`는 Python 3.8에 없다). 읽는 것: `claude mcp list`(Gateway 서버 제외), `claude plugin list`(`productivity@synced` 같은 동기화 플러그인, kind `plugin`·대상 `stdio`·`Status: ✔ loaded`면 active), `codex mcp list --json`, app-server `app/installed`·`config/read`·`configRequirements/read`, `codex features list`. 이름과 목적지 호스트(`origin`)만 보낸다. 한 하네스의 읽기가 실패하면 그 하네스는 보고에서 뺀다 — Gateway는 보고한 하네스의 항목을 전부 `absent`로 되돌리므로 실패가 「없음」처럼 보이면 안 된다. macOS·Windows 관리형은 이번에 포함하지 않는다.
- 결정 2(경로): `POST /api/endpoint/harness-inventory`(`Depends(endpoint_device("inventory"))`, 직원 토큰 아님). 항목은 장치 소유자(`owner_token`) 명의, 작업 위치는 `device:<endpoint_id>`로 저장한다. 키트 보고의 `workstation` 형식(`^[a-z0-9]…`)에는 `:`가 없어 직원이 자기 키트 보고로 관리 단말의 보고를 덮어쓰거나 흉내 낼 수 없다. `connectors.ingest`가 두 경로의 저장을 공유한다(키트 응답 형식 불변). 소유자가 없는 장치의 보고는 409.
- 결정 3(상태): `integrations.harness_item_state` — 장치 보고는 그 장치의 상태로 `endpoint_item_state`를 계산한다(점검 정상이면 `endpoint_enforced`, 같은 PC의 다른 관리자 계정이 있으면 `bypass_possible`). 이는 관리 계정의 커널 규칙(UID nft는 Gateway 호스트와 모델 프록시만 허용)이 벤더 목적지 연결을 막는다는 D-62의 조건에 기댄 것이지, 하네스가 그 항목을 로드하지 않는다는 뜻이 아니다. 키트 보고(장치 없음)는 지금처럼 집행 증거가 아니다. 목록의 `managed_by`는 `endpoint_enforced`면 `endpoint`, 발견 위치는 「엔드포인트 보고」.
- 결정 4(웹 검색): Codex 웹 검색은 사용자 `config.toml`이 아니라 유효값으로 판정한다. `config/read`의 `web_search`(없으면 기본 cached)를 `configRequirements/read`의 `allowedWebSearchModes`로 제한한다(허용 목록에 그 모드가 없으면 `disabled`, 없으면 목록의 첫 값). PJ1은 `web_search: "disabled"`·`allowedWebSearchModes: ["disabled"]`인데 키트 수집기는 파일에 키가 없다는 이유로 `cached`를 보고했다(k1.log). 키트(`mcpgw_pc.py`)와 관리 단말 수집기가 같은 규칙을 쓰며 `connector_control_check.py`가 두 구현의 일치를 본다. `app-server` 응답이 없는 판본은 예전처럼 `config.toml`을 읽는다.
- 시험: `tests/connector_control_check.py` 11건(PJ1 실제 출력 사용). 수정 전 코드에서 장치 보고 상태·웹 검색 유효값·수집기 시험이 모두 실패.
- 한계: root 서비스가 관리 계정으로 `claude mcp list`를 돌릴 때 AppArmor 프로필·헤더 브로커 결속 모드에서 실제로 기대한 출력이 나오는지는 PJ1 확인 전이다(실패하면 보고하지 않고 15분마다 재시도하며 로그에 `harness_inventory: failed`만 남는다). `claude mcp list`는 서버마다 연결을 확인하므로 120초 한도에서 시간 초과될 수 있다. 장치 보고 항목의 「사용 엔드포인트」 수는 같은 직원의 키트 보고와 별개 행으로 센다.

## D-221 비활성 항목과 「마지막 보고에서 사라짐」을 나누고, 콘솔 하네스 커넥터 표에 통제 상태를 표시한다 (2026-10-23)

- 배경: 하네스가 `enabled: false`로 보고한 앱(PJ1의 Slack·Notion 등 9개)과 보고에서 빠진 항목이 모두 「마지막 보고에서 사라짐」으로 표시됐다. 콘솔 하네스 커넥터 표는 승인 칩만 있어 「승인」이 하네스에 효과가 있는 것처럼 읽혔고, 항목이 실제로 어디까지 막혀 있는지(엔드포인트에서 차단·차단 미검증)는 다른 탭에서만 보였다.
- 결정: `harness_item_state` — `status == 'absent'`(보고에서 빠짐)이면 `observed_only`·「마지막 보고에서 사라짐」, 하네스가 직접 꺼짐으로 보고했으면(`active=false`, 그 밖의 status) 장치 보고는 계산된 상태를 유지하고 근거를 「하네스에서 비활성 · …」, 장치 없는 키트 보고는 `observed_only`·「하네스에서 비활성 보고」로 한다.
  콘솔 벤더 커넥터 표와 상세에 「통제」 열/항목을 더한다. 같은 항목을 보고한 엔드포인트들의 상태 중 가장 약한 것을 라벨로 보인다(`console-state.mjs connectorControl`): 엔드포인트에서 차단 / 벤더 콘솔 차단 / 차단 미검증. 승인 칩은 「승인 · 기록만」(윤곽 칩)으로 바꿔 장부 기록이며 하네스 설정이 바뀌지 않음을 설명문 없이 라벨로만 구분한다. 한국어·영어 사전 모두 추가.
- 시험: `connector_control_check.py ItemState`, `console-state.test.mjs`(connectorControl), `i18n.test.mjs`.
- 한계: 라벨은 보고·점검에 기댄 표시이며 단말 밖 경로(Desktop·웹)의 차단을 뜻하지 않는다.

## D-222 후속(설계만): 관리자가 특정 벤더 커넥터를 허용하는 경로 (2026-10-23)

- 현재: 승인은 장부 기록이고 관리형 프로필을 넓히지 않는다(D-53). 그래서 승인해도 Claude Code의 관리 계정에서는 그 커넥터가 계속 닫혀 있다. 이는 설계된 동작이지만, 「승인했는데 안 된다」는 요구를 풀 수 있는 공식 경로가 있다.
- 경로 A — `managedMcpServers`(Claude Code 2.1.259 이상, 관리형 설정): 승인한 벤더의 원격 서버(`type: http`, `https` URL, `command`·`env`·`headersHelper` 없음)를 관리형 설정에 직접 넣는다. 직원이 OAuth로 각자 로그인하고(`headers`에 비밀을 넣지 않는다), `managed-mcp.json`이 있어도 로드되며 `allowedMcpServers` 항목이 필요 없고 `deniedMcpServers`는 여전히 적용된다. claude.ai 계정 커넥터를 다시 여는 `allowAllClaudeAiMcps`가 필요 없어 권장 방향이다.
- 경로 B — `allowAllClaudeAiMcps: true` + `allowManagedMcpServersOnly: true` + `allowedMcpServers`에 Gateway URL과 승인한 벤더의 `serverUrl`(예: `https://mcp.example.com/*`, 호스트 전체를 쓸 때만 와일드카드, 포트 규칙 주의): 계정 커넥터를 불러오되 허용 목록에 있는 것만 연다. 허용 목록 판정은 2.1.273 이상이며, 한 곳이라도 목록을 빠뜨리거나 `allowManagedMcpServersOnly`가 빠지면 계정의 모든 커넥터가 열리는 D-53의 위험이 그대로 돌아온다. `serverName`은 보안 통제가 아니다(문서 경고).
- 공통으로 필요한 변경과 위험: ① 벤더 호스트로의 연결을 관리 계정의 UID nft 허용 목록에 더해야 한다(지금은 Gateway와 모델 프록시뿐) — 이 순간부터 그 항목은 Gateway 판정 밖의 직접 경로이므로 상태는 `endpoint_enforced`가 아니라 「벤더 통제」·「관찰만」이어야 하고 `vendor_enforced`는 벤더 콘솔 확인 기록이 있을 때만이다. ② 승인에 데이터 범위·목적·만료를 결속하고 만료되면 설정에서 빼야 한다(`CONNECTOR_REVIEW_DAYS`는 검토 기한이지 사용 유예가 아니다). ③ 정식 경로(도입 신청 → Gateway 등록)가 있는 서버는 그쪽을 쓴다 — 직접 경로는 PII 검사·계약 대조·감사 원장을 우회한다. ④ Codex는 `features.apps = false`가 앱 전체를 닫고 앱 단위 허용 키가 requirements에 있는지 미확인이다. ⑤ 정책 해시가 바뀌므로 승인·철회가 단말 정책 갱신(heartbeat 60초)으로 이어지고, 철회 시 열린 세션은 다음 시작까지 남을 수 있다.
- 구현하지 않았다. 구현 시 소유자 결정이 필요한 것: 어떤 벤더를 직접 경로로 열 수 있는가(데이터 등급), 직접 경로의 감사·상태 표시 방식.

## D-223 로컬 MCP 러너는 첫 PC에 없는 승인 폴더를 관리 계정 홈 안에 만든다 (2026-10-23)

- 배경: pj2 순수 첫 설치 실측에서 승인된 로컬 filesystem 호출이 「허용하지 않는 마운트 경로」로 실패했다(원장 1073). 승인 매니페스트의 마운트 폴더(`mcp-docs`)가 새 관리 계정 홈에 아직 없었다. PJ1은 누군가 폴더를 미리 만들어 둬서 드러나지 않았다.
- 결정: `PinnedMounts`는 실행 계정(uid, gid)을 받으면, 관리 계정 홈 **아래** 승인 경로의 없는 폴더만 고정된 부모 FD 기준으로 `mkdir(0700)` 후 그 계정 소유로 바꾼다. 홈 자체·홈 밖 경로는 만들지 않고, 이미 있는 링크·파일은 기존대로 `O_NOFOLLOW` 열기에서 거부된다.
- 한계: 직원 본인 계정(sudo 그룹이라 별도 관리 계정을 쓰는 경우)은 관리 계정 홈에 직접 파일을 넣을 수 없다. 문서를 넣는 정상 경로는 후속으로 정한다.
- 시험: `local_run_manifest_check.py`(Linux) 폴더 생성·링크 거부, WSL 단독 확인.

## D-224 별도 관리 계정을 쓰는 직원은 자기 홈 폴더에 문서를 넣고, 로컬 MCP는 그 폴더를 읽기 전용으로 본다 (2026-10-23)

- 배경: 관리자 권한이 있는 직원(pj2처럼 sudo 그룹)은 하네스가 별도 관리 계정(`managed-<직원>`)으로 돈다. 로컬 MCP의 마운트 폴더는 관리 계정 홈(0750, 직원 접근 불가)에 있어 직원이 문서를 넣을 수 없었다(D-223 이후 빈 폴더만 보임).
- 결정: 키트 설정의 `owner_uid`(직원)가 있으면 러너는 **읽기 전용(ro)** 마운트를 직원 홈의 같은 상대 경로(예: `~/mcp-docs`)에서 가져온다. 없으면 직원 소유 0755로 만든다(컨테이너의 관리 계정 UID가 읽을 수 있게). **쓰기(rw)** 마운트(memory 저장 등)는 지금처럼 관리 계정 홈에 0700으로 둔다 — 에이전트가 쓰는 곳에 직원 쪽 프로세스가 끼어들지 않게.
  링크·하드링크·특수 파일 거부, 고정 FD 바인드, 실행 직전 재확인은 그대로다. 직원이 600으로 둔 파일은 컨테이너가 읽지 못한다(그 파일만 읽기 오류).
- 같은 계정(직원=관리 계정)인 경우는 바뀌지 않는다.
- 시험: `local_run_manifest_check.py`(ro는 직원 홈 0755, rw는 관리 계정 홈), WSL 단독 확인, pj2 실측.

## D-225 키트는 sudo 설치 한 번에 필수 구성요소와 컨테이너 엔진까지 갖춘다 (2026-10-23)

- 배경: 소유자 10-23 지시("처음에 sudo로 설치할 때 종속성과 세팅을 다 넣는다"). 키트는 gcc·nftables·AppArmor 도구만 설치하고, 로컬 MCP가 쓰는 컨테이너 엔진·openssl은 첫 사용 때 없으면 그제야 실패했다(엔진 없음은 첫 호출 오류, 이미지 수신은 첫 호출 한도 180초에 걸림).
- 결정 1(한 번에 조회·설치): `bootstrap.ensure_packages`는 `REQUIRED`(gcc·nft·apparmor_parser·curl·openssl)를 `shutil.which`로 한 번 조회해 없는 것만 모아 패키지 관리자를 한 번 갱신(apt-get update)하고 한 번에 설치한다. 모두 있으면 아무 명령도 실행하지 않는다. 이전에는 `missing`과 `still`을 같은 질의로 두 번 만들었다.
  openssl은 로컬 매니페스트 서명 검증(`local-runner.signed`)이, curl은 하네스·점검 도구가 쓴다.
- 결정 2(엔진: 설치한다, 실패해도 멈추지 않는다): 엔진이 없으면(`/usr/bin/podman`·`/usr/bin/docker`, 러너가 보는 경로와 같다) 배포판 패키지로 설치한다 — apt `docker.io`, dnf `podman`, pacman `docker`.
  근거: 소유자가 설치 때 다 넣기를 원하고, 첫 호출에서 설치하면 시간 제한에 걸리며, 엔진이 필요한 로컬 MCP는 엔진 없이 쓸 수 없다. 엔진은 원격 MCP에 필요 없으므로 설치 실패는 「로컬 MCP는 엔진 설치 뒤 사용할 수 있습니다: sudo apt-get install docker.io」로 알리고 나머지 설치는 계속한다(필수 구성요소 실패는 기존대로 설치를 멈춘다).
  docker면 `systemctl enable --now docker`까지 한다(podman은 데몬이 없고 러너가 podman을 먼저 쓴다). 이미 설치돼 있으나 꺼진 docker도 켠다. 실패하면 한 줄로 켜는 명령을 안내한다.
- 하지 않는 것(보안 약화 금지): Docker 공식 저장소·키 추가(외부 신뢰 확장), `daemon.json`·userns-remap 변경(기존 컨테이너 저장소가 가려진다 — 러너가 측정해 「탈출 시 호스트 root」 위험 수용을 표시하는 D-192 구조 그대로), 어떤 계정도 docker 그룹에 넣기(관리 계정이 docker 그룹이면 설치기가 거부하는 규칙 불변).
- 결정 3(파이썬): 설치 전에 설치기 인터프리터와 서비스가 쓰는 `/usr/bin/python3`가 3.10 이상인지 확인한다(`check_python`). 문서의 「Python 3.10 이상」을 실제 검사로 만들었고, 미달이면 계정·패키지를 건드리기 전에 한 줄로 멈춘다.
- 결정 4(소요 시간): 단계 안내(`step`)가 단계별 소요를 모아 설치 끝에 한 줄로 낸다. 「설치 소요(로그인 제외): 필수 구성요소 설치 41초 · 관리형 연결 설치 9초 · 합계 52초」. 1초 미만 단계는 빼고, 직원이 로그인하는 시간은 넣지 않는다. 디버그 출력은 아니다.
- 한계: `/usr/bin` 밖의 엔진(snap docker 등)은 러너가 쓰지 못해 「엔진 없음」으로 보고 `docker.io`를 더 설치한다. dnf의 `podman`은 root 서비스의 `--userns=auto`를 쓰므로 `/etc/subuid`에 containers 범위가 있어야 하고(Fedora 기본) 실측하지 않았다. 실제 apt·dnf·pacman 설치와 `systemctl enable --now docker`는 대역으로만 시험했다.
- 시험: `full_stack_lab/tests/kit_install_upfront_check.py` `Packages`(한 번의 갱신·두 번의 설치, 완비 PC는 무명령, 정지된 docker 켜기, 엔진 실패 계속, 필수 실패 중단, 관리자별 이름, 파이썬 판본, 소요 시간). 수정 전 코드에서는 이 파일 29건 중 28건 실패.

## D-226 승인된 로컬 MCP의 폴더와 이미지를 첫 호출 전에 준비한다 (2026-10-23)

- 배경: PJ1에서 첫 이미지 pull이 5~15분이라 첫 호출이 180초 한도에 걸렸고(D-200), pj2 첫 설치에서는 마운트 폴더가 없어 첫 호출이 실패했다(D-223). 폴더·이미지 준비는 설치 쪽 일이다.
- 결정 1(목록): 장치는 새 경로 `GET /api/endpoint/local-manifests`(장치 자격, `enforcement` 범위)로 이 장치가 준비해도 되는 승인 서버를 받는다. 게이트웨이는 직원이 쓸 수 있는 서버(`pac.servers_for`) 중 **작업 실행과 같은 `local_jobs.authorized`** 검사(`tools/call` 기준)를 통과한 서버만 서명 매니페스트와 함께 낸다. 철회·만료·정지·정지된 사용자·미관찰 승인은 나오지 않는다. 활성이 아닌 장치는 409이다.
- 결정 2(검증): 장치는 작업 때와 같은 함수 `verify_manifest`(고정 승인 키 서명 + digest + 서버 id)로 확인하고, 서명 승인 기한이 지났으면 준비하지 않는다. 확인 전에는 폴더도 이미지도 만들지 않는다(위조 매니페스트 시험).
- 결정 3(준비): 폴더는 작업 때와 같은 `PinnedMounts`로 만든다(`ensure_mounts`): ro는 직원 홈 0755, rw는 관리 계정 홈 0700, 링크·하드링크·특수 파일 거부, 고정 FD(D-223·D-224 불변). 이미지는 작업과 같은 `engine_configuration`(허용 저장소·digest 고정·엔진 판본 측정·추가 볼륨 거부)을 `seconds=PREFETCH_SECONDS`(1800)로 불러 받는다. 첫 호출 한도(`PREPARE_SECONDS` 180)는 그대로다.
- 결정 4(실행 방식): 서비스가 별도 스레드(`local.prepare`)로 60초마다 목록을 받아 새(서버, 매니페스트 해시)만 준비한다. 작업 수령 루프와 섞이지 않아 이미지를 받는 동안에도 호출이 막히지 않고, 설치는 기다리지 않는다. 활성화 전(401·403·409)은 오류가 아니라 기다림이라 15초마다 다시 보고, 목록 경로를 모르는 이전 게이트웨이(404·405)는 조용히 60초 간격이다. 서버별 실패는 같은 사유를 한 번만 기록하고 300초 뒤 다시 한다. 철회된 서버는 기억에서 지운다. 준비한 서버는 다시 열지 않는다(엔진에서 이미지를 지웠다면 첫 호출이 같은 함수로 다시 받는다).
- 결정 5(보이기): 서비스가 상태 요약에 `local`(준비/전체·사유·문서 폴더)을 싣고 `mcpgw-status`가 두 줄을 보인다 — 「로컬 MCP 준비: 1/2 (이미지 받는 중: memory)」, 「직원 문서 폴더: /home/<직원>/mcp-docs」. 승인된 로컬 서버가 없거나 목록을 아직 못 받았으면 `—`. 설치 끝에는 「활성화 뒤 백그라운드로 진행, 진행과 문서 폴더 위치는 mcpgw-status」 한 줄을 낸다. 문서 폴더 경로는 승인 매니페스트의 ro 마운트에서만 알 수 있어 설치 순간에는 모른다.
- 한계: ① 게이트웨이 배포가 있어야 목록이 나온다(없으면 첫 호출 때 받는 기존 경로가 그대로다). ② 활성화 전 장치는 준비하지 않는다 — 활성화되기 전에 폴더·이미지를 내려받게 하지 않으려는 선택이며 활성화 뒤 15초 안에 시작한다. ③ 새 승인을 만드는 순간의 관찰 호출(승인 전)은 그 서버가 아직 목록에 없어 여전히 그 자리에서 이미지를 받는다. ④ 직원이 모드 600으로 둔 파일은 컨테이너가 읽지 못한다(D-224). ⑤ 폴더 안 파일이 1만 개를 넘거나 링크가 있으면 준비가 그 사유로 실패한다(작업과 같은 검사).

## D-227 설치·러너 중복 정리와 측정해 하지 않은 것 (2026-10-23)

- 정리(동작 불변): ① 엔진 명령줄(`[binary,'--remote=false']`/`--host unix:///…`)을 세 곳(`detect_engine`·`engine_configuration`·`recover`)이 따로 만들던 것을 `engine_argv` 하나로, 엔진 판본 질의 두 곳을 `client_version` 하나로. ② 작업 실행의 매니페스트 해시·서명 확인을 `verify_manifest`로 빼 미리 준비와 같은 함수를 쓴다. ③ 직원 홈 조회(`pwd.getpwuid(owner_uid)`)를 `employee_documents`로. ④ `managed-linux install`이 `machine_id()`를 두 번 불러 `/etc/machine-id`를 두 번 읽던 것을 한 번으로. ⑤ `ensure_packages`의 같은 도구 질의 두 번을 한 번으로.

- 죽은 코드: 키트 5개 파일의 최상위 함수·상수를 저장소 전체 참조 수로 훑었으나 참조 0인 것은 없었다(`pyflakes` 통과).
- 시험: 기존 키트·러너 시험 전부 기대값 변경 없이 통과(`loopback_owner_replies_test`는 `check_python` 대역 한 줄만 추가).

## D-228 설치 전에 열린 터미널에서도 관리 하네스가 뜨도록 직원 홈 런처를 관리 런처로 바꾼다 (2026-10-23)

- 배경: pj2 실측에서 설치 전부터 열려 있던 터미널의 `claude`가 직원 계정의 비관리 `~/.local/bin/claude`를 실행해, 모델 로그인이 관리 계정이 아니라 직원 계정에 들어갔다. 키트의 셸 함수는 설치 뒤 연 셸에만 적용되고, 세션 PATH(~/.profile)는 `~/.local/bin`을 `/usr/local/bin`보다 앞에 둔다.
- 결정: 별도 관리 계정을 쓰는 직원(설정에 `owner_uid`)이면 `managed-linux.py`가 설치 때 직원 홈의 `~/.local/bin`·`~/bin`·`~/.npm-global/bin`에 있는 `claude`·`codex` 런처(링크·파일)를 기록해 두고, `exec /usr/local/bin/<이름> "$@"` 한 줄짜리 관리 런처(직원 소유 0755)로 바꾼다. 서비스는 5분마다 다시 확인해 업데이트가 런처를 되돌렸으면 다시 바꾸고, 제거(원복) 때 원래 링크·파일을 되살린다.

- 안전: 모든 파일 연산은 직원 홈에서 시작해 `O_NOFOLLOW` 디렉터리 FD와 `O_EXCL|O_NOFOLLOW` 생성으로 한다(경로 중간 링크·경쟁 생성 거부). 관리자 권한 직원이라 보안 경계가 아니라 사용 경로 정리다.
- 시험: `kit_install_upfront_check.py` `HomeLaunchers`(Linux: 교체·재확인 무변경·업데이트 뒤 복구·원복), pj2 실측.

## D-230 삭제된 계정은 관리자가 복구하고, 재가입 안내와 PC 연결·도구 목록 화면을 바로잡는다 (2026-10-23, 노션 버그 리포트 3건)

- 배경: 팀원이 콘솔에서 사용자를 삭제하자 그 사람은 로그인에서 「삭제된 계정」, 재가입에서 「이미 사용 중인 아이디」로 막혀 되돌릴 길이 없었다. 삭제(`DELETE /api/accounts/{id}`)는 `principals.status='deleted'`로 바꾸고(행·비밀번호 해시·아이디는 남음), 발급 토큰·콘솔 세션·SSO 세션·MCP 세션·상류 풀을 폐기하고, 로컬 실행에 사용자 단위 정지 표식을 남긴다. 이용 관계(`종료·폐기`)와 감사 원장은 건드리지 않는다. 아이디는 `principals`에 계속 있어 재가입이 막히고, 관리 목록은 삭제 행을 숨겨 복구 수단이 없었다.
- 결정 1(복구): `GET /api/accounts/deleted`와 `POST /api/accounts/{user_id}/restore`를 `Depends(admin_caller)`로 추가한다. 복구는 ① 그 사람의 활성 엔드포인트를 모두 해제하고(`revoke_device`: 장치 토큰·MCP 세션·풀 폐기) ② 한 트랜잭션에서 상태를 `active`로 바꾸고, 부여된 동의를 `REVOKED`로 철회하며(동의마다 `user-consent` 사건), `account-restore` 사건을 `approval_events`에 더하고 ③ 삭제 때 둔 로컬 실행 정지를 푼다. 복구 사건의 범위에 삭제 시각·처리자(`deleted_at`·`deleted_by`)와 해제한 엔드포인트·철회한 동의 수를 싣고, 복구는 새 사건만 추가한다(원장 행·판정 기록을 고치는 코드 없음). 해제·철회를 상태 변경보다 먼저 하므로 중간 실패는 삭제 상태(차단)로 남는다. 비밀번호는 그대로라 복구 뒤 기존 비밀번호로 로그인하며, 토큰·엔드포인트·동의는 되살리지 않아 다시 연결하고 동의해야 한다. 이용 중지(`user_server_suspensions`)는 건드리지 않는다.
- 종료 판정과의 관계: [TERMINATION_MODEL](TERMINATION_MODEL.md)은 서버·이용 관계의 종료를 판정하며 계정 삭제는 입력이 아니다. 삭제 중 막힌 접근의 회수 증거는 그때 기록된 `principals.status`와 함께 남고 복구가 바꾸지 않는다. 복구된 사람은 다시 모집단에 들어가므로 이미 종료된 서버·관계는 그대로 종료 상태다(복구가 서버를 되살리지 않음).
- 결정 2(안내): 로그인 거부 사유를 「삭제된 계정입니다. 관리자에게 복구를 요청하세요.」로, 삭제된 아이디로 가입하면 「삭제된 아이디입니다. 관리자에게 복구를 요청하세요.」로 바꾼다. 재가입으로 같은 아이디를 새로 만들지는 않는다(이전 소유 기록과 섞이지 않게).
- 결정 3(콘솔): 사용자·엔드포인트에 「삭제된 사용자」 탭(이름·이메일·역할·부서·삭제 시각·처리자)과 「복구」 버튼을 둔다. 감사 사건 이름 「계정 복구」를 추가했다. 삭제 자체는 사건을 남기지 않는 기존 동작 그대로다(처리자·시각은 `principals.status_changed_by/at`에 있다가 복구 사건 범위로 옮겨 적힌다).

## D-234 승인한 MCP의 기본 사용 대상은 전체 직원이고, 승인 화면에서 신청자만·지정 직원으로 좁힌다 (2026-10-25)

- 배경: PJ1에서 MINT 계정 aaaa의 하네스에 MCP가 하나도 없었다. 원클릭 승인이 사용 대상을 신청자 한 명(`allowed_principals=[신청자]`)으로 고정해, 승인된 11개 모두 `user`만 쓸 수 있었다. 다른 직원은 장치가 활성이어도 관리형 설정에 서버가 0개로 내려간다. 소유자 결정: 기본은 전체 직원, 승인 화면에서 좁힐 수 있게.
- 결정:
  - 사용 대상 `"*"`는 「활성 직원 전체」다. 승인 봉투(envelope)는 그대로라 검토한 도구·읽기/쓰기 분류·인자 제한·기한은 계속 묶인다(`pac.scope`의 봉투 판정은 사람 목록만 넓어진다). 모든 판정 경로가 `registry.permits(allowed, token)` 하나로 묻는다(게이트웨이 판정·tools/list·동의·관리형 설정·통제 범위·LiteLLM 동기화).
  - 원클릭 승인 `audience`: `all`(기본)·`requester`·`selected`(+로그인 아이디 목록, 활성 계정만). 원격은 검토 계약에, 저장소 도입은 신청 증거(`audience_principals`)에 남겨 등록이 그대로 쓴다. 2차 승인은 1차와 같은 대상이어야 한다. 콘솔 승인 화면에 「사용 대상」 선택과 「지정 직원」 입력, 원장 화면에 「전체 직원」 표시.
  - 이미 승인된 서버의 사용 대상 변경: `POST /api/registry/servers/{id}/audience`(관리자, 원장 `server-audience` 사건, 이전 값 보존).
  - 운영자 자격 파일(`upstream`)의 `allowed_principals`도 `"*"`를 받아, 서버 보유 자격을 승인 대상 전체와 공유할 수 있다.
- 같이 고친 것: 활성화 대기·격리 장치에는 「관리자 활성화를 기다리는 중이라 MCP를 아직 쓸 수 없다」는 안내를, 쓸 수 있는 서버가 없는 직원에게는 「도입 신청·사용 대상 추가 요청」 안내를 관리형 메모리로 내려, 모델이 사용자 설정 파일을 뒤지거나 셸에서 하네스를 실행하려 하지 않게 한다. 같은 PC·같은 관리 계정에 다른 직원의 키트가 설치되면 이전 직원의 장치 기록은 이어받지 않고 해제한다.
- 시험: `audience_all_check.py`, 원클릭·동의·LiteLLM·tools/list 관련 시험의 대역 갱신(`permits`), `harness_detect_check`(빈 경우 안내), `kit_continuity_check`(다른 직원 장치 해제 중복 없음).

## D-235 GitHub는 직원이 각자 계정을 연결해서 쓰고, 공유 토큰은 지정한 사람 전용으로 둔다 (2026-10-25)

- 배경: 소유자 결정 「GitHub는 직원별로 각자 계정을 연결하는 방식으로 바꿔. 공유 토큰은 다시 user 전용으로 되돌려.」 D-234로 승인 대상이 전체 직원이 되면서 운영자 자격 파일의 한 행(`allowed_principals=["*"]`)이 모든 직원의 GitHub 호출에 같은 계정으로 나갔다. 자격이 없는 직원의 호출은 익명으로 나가 401이 `MCP-UPSTREAM-001`의 「오류」로 돌아왔다. `credential_headers`는 endpoint당 한 행만 받았다(「ambiguous resource binding」).
- 불변식과의 관계: 「직원 토큰을 upstream으로 넘기지 않는다」의 직원 토큰은 MINT 로그인 토큰이다. 직원이 GitHub에서 직접 만든 자격은 그 직원의 호출에만 쓰는 서버 보유 자격이며, MINT 토큰은 여전히 어느 헤더에도 들어가지 않는다.
- 결정:
  1. **저장**: `user_upstream_credentials`(직원 토큰×endpoint)에 AES-GCM 암호문. 주체·endpoint를 연결 데이터로 묶어 다른 행으로 복사해도 풀리지 않는다. 키는 `console.sh`가 `.env`에 한 번 만드는 `USER_CREDENTIAL_KEY`(32바이트)이고 gateway·gateway-sse·agent-service에 환경 변수로 간다. 키가 없거나 바뀌면 연결은 「연결 안 됨」으로 읽혀 차단된다(실패는 차단). 평문은 로그·원장·응답·호출 기록에 남기지 않는다.
  2. **선택 순서**(`upstream.credential_choice`): ① 이 직원이 이 endpoint에 연결한 자격 ② 운영자 파일에서 이 직원에게 묶인 행(정확한 이름이 `"*"`보다 우선, 같은 endpoint 여러 행 허용, 같은 순위가 둘이면 거부) ③ 없음. 연결한 자격이 만료됐으면 운영자 행으로 물러서지 않고 거부한다. 연결한 값은 등록된 endpoint(https)에만 가며 `refresh_connected`가 호출마다 DB에서 읽어 프로세스 안 사본을 갱신하고 `close_pool`이 지운다. 연결·해제는 `release_pool`로 다른 프로세스의 따뜻한 세션도 닫는다.
  3. **직원별 자격 필요 표시**: 서버 endpoint의 호스트가 `api.githubcopilot.com`이면 직원별 자격이 필요한 서버다(`user_credentials.SERVICES`; 등록에 `credential_scope = "shared"`를 두면 끈다). 새 등록 절차를 늘리지 않아 이미 등록된 서버도 바로 적용된다. 필요한데 ③이면 `execute_call`이 예약·검사 전에 `MCP-CREDENTIAL-001`로 차단하고(상위 서비스 호출 없음, `upstream_attempted=false`) 「GitHub 계정 연결이 없거나 만료되어 호출하지 않았습니다. MINT 콘솔 『내 연결』에서 GitHub 계정을 연결하세요.」를 하네스에 보낸다. 종료 중인 서버는 `MCP-DECOMM-001`이 이유로 남도록 이 검사를 건너뛴다. 정책은 `policy_ledger.json`에 게이트웨이 집행으로 등재(priority 2015).
  4. **연결 방법**(콘솔 「내 연결」, 모든 역할): (a) 개인 액세스 토큰 붙여넣기 — 저장 전에 `GET https://api.github.com/user`로 로그인 이름과 만료(`github-authentication-token-expiration`)를 확인하고 실패하면 저장하지 않으며 토큰을 오류에 되풀이하지 않는다. 화면에는 계정·방식·연결 시각·만료·마지막 사용만 보인다. (b) `GITHUB_OAUTH_CLIENT_ID`가 있으면 GitHub 장치 인증(RFC 8628: `POST github.com/login/device/code`, `…/login/oauth/access_token`, client secret 없음)으로 연결. 코드 입력 창을 열어 두고 서버가 간격(`slow_down` 반영)을 지켜 확인하며 상태는 대기·연결됨·만료·거부·실패다. 진행 중 흐름은 agent-service 프로세스 메모리에 있다(재시작하면 다시 시작). 연결 해제는 즉시 삭제.
  5. **수명주기**: 계정 삭제와 중지·잠금은 그 직원의 연결을 모두 지운다. 서버별 이용 중지(`user_server_suspensions`)는 재개할 수 있으므로 지우지 않고 호출만 `P-SUSPEND-001`이 막는다. 이용 관계 종료(`decommission`)는 그 endpoint의 직원 연결을 `server-held-credential`(보유자 조직, 확인 방법 `credential-store`) 회수 대상으로 올리고, 종료 시작 시 삭제한 뒤 다시 읽어 없음을 `credential-check` 증거로 남겨야 「회수됨」이 된다(삭제 실패면 미회수로 남아 `credentials` 수집이 다시 시도한다). 회수 증거는 조직이 보관한 사본의 삭제이며 GitHub 쪽 토큰 폐기는 계정 소유자의 몫이라 제공자 쪽 대상(고지 없음)은 그대로 판단 불가로 남는다.
  6. **원장**: `approval_events`에 `upstream-credential-connect`·`upstream-credential-disconnect`(주체·서비스·계정 이름·방식·기한·사유, 값 없음). 사용은 호출 기록 `decisions.client.upstream_credential`(`employee`/`operator`/`none`)과 `last_used_at`(5분 단위)로 남긴다.
  7. 운영자 공유 자격은 지정한 사람 전용(`allowed_principals=["user"]`)으로 되돌렸고 계약 확인(주체 없는 조회)은 이 행을 계속 쓴다.
- 한계: 장치 인증으로 받은 OAuth App 토큰이 `api.githubcopilot.com/mcp`에서 받아들여지는지는 실제 OAuth App과 계정으로 확인하지 않았다(이 작업은 실제 토큰·앱 사용 금지). 조직이 GitHub에서 OAuth App을 등록하고 장치 흐름을 켜야(Enable Device Flow) client id를 넣을 수 있으며, 조직의 OAuth App 접근 제한이 있으면 조직 소유자가 승인해야 한다. 토큰 붙여넣기 방식은 GitHub의 토큰 형식·권한을 그대로 따른다. 연결 자격이 없는 상태의 계약 확인(`refresh_catalog`)은 운영자 행이 있어야 인증된다. 장치 흐름 상태가 프로세스 메모리라 agent-service를 여러 프로세스로 늘리면 폴링이 다른 프로세스에 가 만료로 읽힌다(고정 세션 또는 DB 보관 필요).

## D-242 판본은 유의적 버전, 정본은 최상위 `VERSION` 하나, 첫 판본은 0.9.0 (2026-10-25)

- 배경: 판본 번호 없이 기능 단위로 기기에 배포했고, 이미지 태그(`gateway` 무태그·`workstation:3.0`·`runtime-worker:1.0`), FastAPI `version`(1.1.0·2.0.0), 브랜치 이름(v3.1) 같은 내부 세대 표기가 섞여 있었다. 고객 서버 배포·업그레이드·롤백에는 하나의 판본이 필요하다.
- 결정:
  1. [유의적 버전](https://semver.org/lang/ko/)을 쓴다. 정본은 저장소 최상위 `VERSION` 한 줄이고, 사용자에게 보이는 변경은 `CHANGELOG.md`(Keep a Changelog)의 「미배포」에 쌓았다가 판본을 올릴 때 옮긴다. 태그 `vX.Y.Z`는 `VERSION`이 그 값인 커밋에만 붙인다. 1.0.0 전에는 부 판본이 바뀔 때 호환되지 않는 변경이 있을 수 있고 「업그레이드 주의」에 적는다.
  2. 첫 판본은 **0.9.0**. 근거: 도입 심사·호출 전 판정·원장·종료 판정·키트(Linux 실기기, Windows 설치·활성화)가 한 기기에서 실사용 중이라 기능은 1.0 범위에 가깝지만, 최종 검수 0건, macOS 실기기 미검증, 고객 서버 설치는 CI 일회용 스택에서만 실증, 이전 판본에서 올라오는 이행 경로 미검증이라 1.0.0(안정 약속)은 이르다. 0.1.0은 실제 성숙도보다 낮게 알린다.
  3. 태그 위치는 `VERSION`·`CHANGELOG.md`·`deploy/`가 들어간 이 브랜치의 main 병합 커밋을 권고한다(지금 main `7687a9e`에는 `VERSION`이 없어 판본 표시와 태그가 어긋난다). 다음 S1(간편 모드 기본·자동 활성화)은 동작 기본값이 바뀌므로 0.10.0으로 낸다.
  4. 판본 표시(설계, 코드는 후속): 빌드 인자로 `MCP_BUILD_REVISION=<VERSION>+g<커밋 12자>`를 넣는다 — `deploy/mint.sh`는 이미 이렇게 해서 `/api/health`·`/api/readiness`의 `build.revision`에 판본이 보인다. 후속으로 ① 게이트웨이 Dockerfile에 `ARG MINT_VERSION`을 두고 `release.build_info()`에 `version`을 더하고 ② 콘솔 하단은 `/api/readiness`의 `build.console.version`을 라벨 없이 `v0.9.0`으로 보이고 ③ 키트 묶음(`agent_service`가 `/endpoint-kit`에서 만드는 ZIP)에 `VERSION`을 넣어 `mcpgw-status`가 「키트 0.9.0 · 게이트웨이 0.9.0」과 불일치 경고를 보인다. 판본 비교는 같은 문자열 일치만 쓰고 해시(`pc_kit_sha256`)는 그대로 둔다(같은 판본 안의 핫픽스 구분).
- 검사: `deploy/check.py`(VERSION 형식, CHANGELOG 첫 판본 = VERSION)를 CI 정적 검사에 넣었다.

## D-240 운영 배포 묶음은 `deploy/` 하나, 실습 스택과 같은 이름·코드를 쓰고 게시는 한 주소의 443·3128 (2026-10-25)

  1. `deploy/compose.yaml`은 독립 파일이다. 서비스 11개(db·opa·presidio 2·gateway·agent-service·intake-worker·runtime-worker·corp-git·caddy·model-proxy, 선택 siem-worker). 실습용·Jaeger·GreenMail·LLM·SSE 진입점(gateway-sse, Caddy 경로가 없어 밖에서 닿지 않음)은 뺀다. 서비스·망 이름은 랩과 같게 둔다 — 실행기가 compose 서비스 `gateway`와 `<프로젝트>_edge` 망을, Caddyfile이 `corp-git`·`agent-service`를 이름으로 찾기 때문이다. Caddyfile·OPA 정책·레지스트리·키트·빌드 문맥은 `../full_stack_lab`·`../endpoint-agent`를 그대로 마운트해 정본을 하나로 둔다.

## D-249 LiteLLM 애드온: 경로 선택 하나, deploy 설치 연결, 완료 상태 재조회, 대상 단위 실패 격리, 1.105 고정 (2026-10-25)

- 배경(astra 10-25 검토, 판정 「수정 필요」): 동기화는 원래 upstream 주소를 LiteLLM에 등록하는데 standalone은 LiteLLM 출구를 MINT로만 열어 등록과 호출이 따로 놀았다. `deploy/`에는 매핑·키·CA 연결이 없었고, `verified` 뒤에는 외부 변경을 다시 보지 않았으며, 키 하나의 오류가 서버를 지워 다른 직원까지 멈췄다. 정상 호출은 대역으로만 확인돼 있었다.
- 결정:
  1. **경로는 `MINT_LITELLM_ROUTE` 하나로 정한다.** `mint`(기본, A 경유): LiteLLM MCP 서버 주소 = `GATEWAY_PUBLIC_MCP_URL`(또는 `MINT_LITELLM_MINT_MCP_URL`)`/<서버>/`, `auth_type=oauth_delegate` — LiteLLM은 직원이 보낸 `x-mcp-<서버>-authorization`(본인 MINT 토큰)을 그대로 넘기고 보관하지 않는다. upstream 자격·URL 속 자격은 MINT 안에만 있으므로 A에서는 등록을 막지 않는다(장치 실행 서버만 제외). `direct`(B): 원래 주소, `auth_type=none`, 호출 직전 가드레일이 판정 API를 부른다. A에서 B로 바꿀 때 우리가 넣은 `oauth_delegate`를 물려받지 않고 `none`으로 바꾼다(직원 토큰이 upstream으로 가지 않게). 경로 값은 동기화 지문에 들어가 바꾸면 다시 전파된다. standalone(출구가 MINT뿐)은 A 전용 묶음으로 명시한다.
  2. **설치 연결**: `./mint.sh litellm enable --url --bindings [--ca] [--route]`(관리 키는 표준 입력) → 매핑을 `deploy/litellm/`에, 관리 키를 게이트웨이 이미지 안에서 `0400`·소유 10001 파일로 쓰고 → `python -m app.litellm_sync check`(매핑·키·`require_key_mcp_access_defined`·워커 연결, 쓰기 없음)가 통과할 때만 게이트웨이를 다시 만든다. `rotate-key`는 재기동 없이 키 파일만 바꾸고 점검한다(키는 요청마다 다시 읽음). 관리 origin 전용 사설 CA(`MINT_LITELLM_SYNC_CA_FILE`)는 다른 외부 TLS의 시스템 저장소를 바꾸지 않는다. 매핑·CA는 백업에 들어가고 관리 키는 비밀 저장소가 정본이라 복구 뒤 `rotate-key`로 넣는다.
  3. **재조회**: `verified`도 `MINT_LITELLM_SYNC_RECHECK_SECONDS`(기본 300초, 최소 30초)마다 읽기 전용으로 서버·키·팀을 다시 읽는다(`observe`). 일치하면 원장에 아무것도 쓰지 않고 시각만 갱신, 다르면 `drift` 관측과 함께 다시 전파해 되돌리고 그때만 `litellm-sync` 사건을 남긴다(5분마다 원장이 늘지 않게).
  4. **실패 격리**: 키·팀 하나의 소유자 불일치·권한 재조회 불일치·관리 API 오류는 그 대상만 실패로 두고(`partial` 관측에 대상 해시) 서버와 다른 대상의 권한은 유지한다. 서버 자체 재조회 불일치(`server-readback-mismatch`·워커 불일치)일 때만 서버를 지운다. 서버는 `allow_all_keys=false`이고 키 권한이 명시돼야 쓰이므로(`require_key_mcp_access_defined`) 실패 대상이 남은 서버로 권한을 얻지 않는다.
  5. **판본·위생**: 지원 판본은 LiteLLM 1.105.0(digest 고정, standalone·CI 동일). 프롬프트·응답 지출 로그 저장은 기본 끔. 가드레일은 `recorded:false`도 경고로 남긴다. `deploy/check.py`가 `addons/litellm`·`llm/standalone`·`integrations/litellm`도 위생 검사한다.
  6. **명시적 키 접근 설정(1.105 정정)**: D-208은 서버를 만들기 전에 `require_key_mcp_access_defined=true`를 관리 API(`/config/field/info`)로 다시 읽도록 했으나, 실제 1.105 이미지(CI)는 이 필드를 `/config/field/*`에서 400으로 거절한다(설정 파일 전용). 1.105 소스(`user_api_key_auth_mcp.py`)상 이 값은 자기 MCP 목록이 없는 키가 **팀** 권한을 물려받는지만 정한다. 그래서 매핑에 팀이 없으면(MINT가 키에만 명시적으로 부여) 점검을 건너뛰고(`team-ceiling: no-team-grants`), 팀 매핑이 있으면 API로 읽히거나 운영자가 설정 파일 값을 `MINT_LITELLM_KEY_ACCESS_CONFIRMED=1`로 확인했을 때만 서버를 만든다. 근거는 사건의 `team-ceiling` 관측에 남는다.

## D-250 중앙 AI 게이트웨이 전용 직원은 관리형 PC 없이 자기 MCP 토큰을 받는다 (2026-10-25)

- 배경: 필드 모드는 기동 때마다 관리자가 아닌 모든 계정을 「관리형 PC 필수」로 되돌린다(`bootstrap_field_accounts`). LiteLLM 등 중앙 AI 게이트웨이로만 MCP를 쓰는 직원은 PC 키트가 없어 비밀번호 인증으로 MCP 토큰을 받을 수 없었고, 애드온 시험은 승인 대상이 아닌 root로만 할 수 있었다.
- 결정: `principals.ai_gateway_only`(기본 false)를 두고, 이 계정은 기동 때 관리형 PC 요구를 되살리지 않는다. `./mint.sh add-account <아이디> --role 직원 --ai-gateway`로만 만든다(관리자에는 쓰지 않음). 신원은 여전히 그 직원의 전송 토큰이고, 승인 사용 대상·정책 판정·원장 귀속은 다른 직원과 같다. 이 직원이 나중에 키트를 설치하면 장치 등록이 관리형 요구를 다시 켠다(기존 동작).
- 근거: 소유자 지시(10-25) 「보안은 타 솔루션이 받친다는 전제에서 편의 우선」. 엔드포인트 통제를 중앙 게이트웨이 경로가 대신하며, 직원 PC의 다른 경로(하네스 직접 연결)는 엔드포인트 통제 범위 밖으로 남는다.
- 한계: 콘솔은 이 계정을 따로 표시하지 않는다(통제 범위 화면의 `observed_only` 구분은 후속). 비밀번호 인증 토큰은 장치에 결속되지 않은 bearer 토큰이다.
