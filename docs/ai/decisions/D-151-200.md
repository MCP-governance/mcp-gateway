# 설계 결정 번호 151~200

## D-151 Windows 관리 계정 환경의 CODEX_HOME·CLAUDE_CONFIG_DIR를 준수 실패로 보고한다 (2026-10-20, DEV-42)

- 문제: D-148의 `user_command_helpers` 검사는 등록 프로필의 기본 위치(`.claude\settings*.json`, `.codex\config.toml`·`*.config.toml`)만 읽는다. Windows 관리 계정의 사용자 환경(`HKEY_USERS\<SID>\Environment`)에 `CODEX_HOME` 또는 `CLAUDE_CONFIG_DIR`를 두면 하네스가 검사하지 않는 다른 설정 폴더를 읽어 `apiKeyHelper`·`notify` 같은 명령 헬퍼를 시작할 수 있다(적대 검토 S6-03). Linux는 래퍼가 환경을 비우므로 해당 없다.
- 결정: Windows `checks`가 같은 레지스트리 키(`set_user_environment`가 쓰는 곳)에서 두 변수의 존재만 읽는다. 값이 비어 있어도 있으면 `user_command_helpers`를 false로 하고 고정 표기 `env:CODEX_HOME`·`env:CLAUDE_CONFIG_DIR`(키 목록 없음)를 발견 항목에 더한다. 값은 읽어 쓰지 않으며 보고·DB·감사 사건에 남지 않는다. 키·하이브가 없으면(로그아웃 계정 포함) 변수 없음, 그 밖의 레지스트리 오류(권한·I/O)와 `winreg` 가져오기 실패는 실패로 보고하고 고정 표기 `env`를 쓴다. 게이트웨이 입력 모델 `UserCommandSetting.file`의 고정 표기 목록에 이 세 값만 추가했고 임의 문자열은 계속 거부한다. 새 준수 항목·라우트·DB 변경·의존성은 없다.
- 근거: [Codex 구성 설명](https://learn.chatgpt.com/docs/config-file/config-basic)의 `CODEX_HOME`, [Claude Code 환경 변수](https://code.claude.com/docs/ko/env-vars)의 `CLAUDE_CONFIG_DIR`, D-148/S6-03 분석. 표준 라이브러리 `winreg`와 기존 `set_user_environment`의 키 경로를 재사용했다. 사용자 임의 폴더를 SYSTEM이 재귀 탐색하는 방식은 읽기 범위를 늘려 택하지 않았다(S6-03 수정안의 "지원 경로를 열거해 검사" 대신 "변수 존재를 실패로" 선택).
- 검증: 새 `tests/windows_config_env_check.py` 8건(변수 없음·`CODEX_HOME`·빈 `CLAUDE_CONFIG_DIR`·키 없음·레지스트리 오류·`winreg` 부재·값 비누출·입력 모델 허용/거부)과 기존 `user_command_settings_check.py`가 통과한다. 기존 시험은 기대값을 바꾸지 않았고, Windows `checks`가 `winreg`를 읽으므로 비Windows 실행용 가짜 `winreg` 한 줄만 더했다. 실제 레지스트리·PJ1 하네스 음성 시험은 미실행이다.
- 한계: 검사 대상은 관리 계정의 사용자 환경 두 변수뿐이다. 프로필 아래 다른 위치(프로젝트 폴더, `--settings`·`-c/--config` 인자, 이미 올라간 세션의 프로세스 환경)와 시스템 환경 변수(`HKLM`, 관리자 권한 경계)는 범위 밖이다. 계정이 로그아웃이라 하이브가 올라와 있지 않으면 읽지 못하며(그동안 하네스도 실행되지 않음) 로그인 후 첫 heartbeat에서 잡힌다. 60초 간격 스냅샷이라 확인 사이 변수를 넣었다 빼는 경쟁은 막지 못한다. 관리 계정이 쓰는 정당한 `CODEX_HOME` 설정은 없으므로 오탐 비용은 낮지만, 있었다면 격리된다. 재설치하지 않은 구형 장치는 D-148의 전환 규칙대로 검사를 받지 않는다. [작업 보고](../../research/llm-wiki/status/reports/2026-10-20-windows-config-env.md).

### D-151 적대 검증 정정·기존 시험 대역 B 판정 (2026-10-20, Codex sol)

- 문제: 하이브 전체의 확인 불능을 변수 없음으로 정상 인증한다. 로그아웃 중 정상 heartbeat 뒤 로그인해 이전 환경을 상속한 하네스가 다음 검사 전에 시작할 수 있어, 위의 「그동안 하네스도 실행되지 않음」은 실행 전 차단의 근거가 되지 않는다. 또한 HEAD의 기존 시험 winreg 대역은 Windows Python 3.10의 observer import 중 `platform.system()`이 호출하는 `OpenKeyEx`를 제공하지 않아 오류가 난다.
- 결정: 기존 시험 대역 7줄은 **B(수정 후 채택)**다. 기존 파일·기대값은 보존했다. SID 하이브와 환경 키/값 부재를 구분하는 제품 수정에는 기존 D-151 정상 기대값과 D-148 대역 변경이 필요하므로 소유자의 「기존 시험 변경 필요」 규칙에 따라 제품 수정은 중단했다. 새 `tests/windows_config_env_review_check.py`는 14건 중 12통과·1실패·1오류로 결함을 숨기지 않는다. 커밋·배포 없음.
- 근거: [적대 검증 정본](../../research/llm-wiki/analysis/review-1020/d151-windows-config-env.md)의 공식 Microsoft 환경 상속·레지스트리 의미와 CPython 문서, 현재 `checks`·`serve_pipe`·`harness_launchers`·D-148 전환 코드를 대조했다. REG_EXPAND_SZ·대소문자 이름은 검출 대상이고, import/권한/I/O 실패는 고정 `env`로 닫힌다. `QueryValueEx`는 값을 메모리에 읽지만 보고/DB 사건에는 고정 표기만 사용한다는 것이 정확하다. 기존 「값은 읽지 않는다」 표현을 이 설명으로 정정한다. 새 의존성·정책 ID·DB 변경 없음.
- 한계/전환 정정: 휘발성·시스템·현재 프로세스 환경은 미조회다. 휘발성 임의 값의 실제 하네스 상속은 실기기 미검증이다. D-148만 설치된 에이전트도 같은 `user_command_helpers`를 보고할 수 있으므로 보고 표식은 D-151 설치/실행을 증명하지 않는다. 캐시 최대 120초·검사 루프 sleep 60초는 로그인 이벤트나 실행 시점 잠금이 아니다. 실제 Windows/기기/PJ1·입력 모델 실행은 미검증이며 기존 기록은 이력으로 보존한다. [실행 출력](../../research/llm-wiki/analysis/review-1020/d151-windows-config-env-evidence.json), [작업 보고](../../research/llm-wiki/status/reports/2026-10-20-d151-windows-config-env-review.md).
- 적대 검증(SR4, Codex sol) 판정 반영(Claude): W151-01(하이브 미탑재를 '확인 불가=실패'로) 거부 — 하이브가 올라오지 않은 계정의 사용자 환경 값은 어떤 프로세스에도 적용되지 않고(프로필 없이 실행되는 프로세스도 그 값을 받지 않음), 실패로 보면 로그아웃할 때마다 장치가 격리돼 관리자 재활성화가 필요하다. 로그인 뒤 첫 heartbeat(60초)까지의 틈은 한계로 남긴다. W151-12(기존 시험 winreg 대역이 Python 3.10의 platform 조회와 충돌)는 Windows 에이전트가 고정 CPython 3.13을 쓰고 기기 Linux·로컬 3.12에서 통과해 채택한다. 휘발성·시스템 환경·실행 중 프로세스 환경(W151-05~07)은 범위 밖 한계다. ## D-153 MCP 인입은 audience·mcp scope·수명·서명을 검증하고 철회 토큰을 거부한다 (2026-10-20, DEV-05)

- 문제: `authenticate()`는 IdP 서명·issuer·audience·시간 클레임을 확인하고, `authenticated_user()`는 철회 목록과 계정을 확인한다. 그러나 `require_mcp=True`는 `mcp` scope를 요구하지 않아 `console` scope 토큰도 MCP facade `_caller()`를 통과할 수 있었다.
- 결정: `authenticated_user(..., require_mcp=True)`는 토큰의 scope 집합에 `mcp`가 없으면 403으로 거부한다. 새 PostgreSQL 실험은 제품 IdP 발급 정상군과 다른 audience·scope·만료·철회 jti·다른 EdDSA 키·`none`·HS256 입력을 제품 MCP facade `_caller()`에 넣고 각 거부 후 발신자별 dispatch intent가 0인지 확인한다. 폐기 서명 목록은 `restore_residual_pg_check.py`처럼 격리 임시 디렉터리와 시험용 Ed25519 키로 초기화한다.
- 기존 시험 변경 필요: `tests/token_revocation_pg_check.py`는 제품 경로 변경 대상이 아니다. 이 시험을 고치는 diff만 제안하며 적용하지 않는다. `termination_lab_support` import에 `isolated_disposal`을 추가하고, `main()`에서 `for case in (...)` 전체를 `with isolated_disposal():` 안으로 들인다. D-123 이후 필수인 서명 폐기 원장 genesis를 먼저 만들고 시험별 폐기 기록을 임시 디렉터리에 가두기 위한 최소 fixture다.
- 근거: `docs/ai/DECISIONS.md` D-10의 OAuth 발급·철회 계약, `agent_contract.authenticate()`의 고정 ALGORITHM/AUDIENCE/ISSUER 검증, `mcp_facade._caller()` 및 Gateway `RequireBearer`의 전송 토큰 경계. scope 보강은 새 권한을 주지 않고 토큰의 발급 목적을 MCP 경계에서 강제한다. 새 의존성·정책 ID·DB 변경·mock MCP는 없다.
- 검증: Python 구문 컴파일과 diff 공백 검사를 수행한다. PostgreSQL 실험은 이 PC에서 실행하지 않는다. 솔루션 기기 명령은 `cd full_stack_lab && tests/termination_dispatch_lab.sh run oauth_negative_pg_check.py`이며, 실험실을 먼저 `up`해야 한다. 기존 토큰 폐기 시험도 기기에서 실행한다.
- 한계: `_caller()` 인증 거부와 intent 0은 외부 MCP 연결 없이 확인하도록 설계했으며 upstream 독립 효과 시험은 아니다. 실제 시험·Gateway 이미지·배포·PJ1 하네스 검증은 미실행이다. 다른 audience/서명 알고리즘은 서명 검증 단계에서 막히고, 만료·scope·철회는 각 해당 검증 단계에서 막힌다. `idp.token()`의 password grant 경로는 격리 DB에서 호출한다.
- 보고: [DEV-05 작업 보고](../../research/llm-wiki/status/reports/2026-10-20-oauth-negative.md).

## D-154 갱신 토큰 회전의 서명 폐기 기록은 커밋 뒤에 남긴다 (2026-10-20, DEV-16·DEV-63)

- 문제: D-123 이후 `idp.token`(refresh 회전)은 서명 폐기 목록에 옛 갱신 토큰을 먼저 기록하고 DB를 갱신했다. 발급이 실패해 DB가 되돌려지면 목록만 남아, DB가 여전히 유효하다고 보는 갱신 토큰이 거부되고 다음 사용이 재사용으로 판정돼 계열 전체가 폐기됐다. 기존 실험실 시험 `token_revocation_pg_check.py`는 서명 목록을 초기화하지 않아 D-123 이후 실행되지 못해 이 회귀가 가려졌다.
- 결정: 회전은 DB 커밋 뒤 목록에 기록한다. 계정·장치 폐기(G07.04)는 철회 방향이라 커밋 전 기록(초과 차단)을 유지한다.
- 근거: 실험실 PostgreSQL에서 `issuance_rolls_back`("실패한 발급 뒤 갱신 토큰이 계속 동작") 재현·수정 후 통과. 시험은 `isolated_disposal()`로 목록을 초기화하고, 장치 폐기 뒤 거부 상태를 401(서명 목록)·403(장치 상태) 모두 허용한다.
- 한계: 커밋과 목록 기록 사이에 프로세스가 죽고, 그 뒤 DB를 회전 전 백업으로 되돌리면 옛 갱신 토큰이 한 번 더 쓰일 수 있다(재사용 판정으로 계열이 폐기되는 기존 방어는 남음).

## D-152 승인 실행 시 요청자 토큰 현재 유효성 재검증(구현) + 요청자 재시도 모델(미구현·결정 필요) (2026-10-20, DEV-17)

- 문제: `main.approve`는 승인자를 인증하고 `core.approve_request`가 저장된 요청자 transport_claims로 즉시 실행한다. 현재 PAC의 철회 테이블·만료 검사와 managed_failure·D-140의 주체 활성 검사는 있지만, 이 승인 실행 경로는 authenticated_user의 서명 폐기 목록 검사를 거치지 않는다. 복원 뒤 철회 테이블이 과거 상태라면 파일에만 남은 폐기를 놓칠 수 있다.
- 결정(구현): 소유자의 범위 축소 지시에 따라 `approve_request → execute_call` 즉시 실행 UX와 기존 시험 기대값을 유지한다. `_call_upstream`에서 도구 탐색·승인 상태 재확인 뒤, 실제 tools/call과 intent 생성 전에 저장된 원 요청자 jti로 `disposal.blocked`와 `agent_revoked_tokens`를 다시 조회한다. authenticated_user가 쓰는 기존 함수·SQL을 그대로 사용한다. 폐기/철회 또는 서명 목록의 무결성·읽기 실패로 blocked가 true면 기존 `P-INPUT-001`, 예상 밖 조회 예외는 `P-CONTROL-FAIL-CLOSED`로 차단한다. 기존 DispatchRejected → execute_call → _decision_payload 경로가 차단을 원장에 추가하고 승인 상태를 NOT_EXECUTED로 마무리한다. 원 승인 payload·감사 기록은 덮어쓰지 않는다.
- 기존 검사 재사용: 이어지는 managed_failure가 저장 device_id의 현재 소유자·활성/관리 상태·epoch·정책·heartbeat를 검사한다. PAC 재생성의 `nbf <= now < exp`와 주체·발급자·대상·철회 검사를 유지하며 OPA가 만료를 거부한다. execute_call의 활성 주체 확인과 D-140 dispatch.record의 잠금·활성 상태 확인은 재사용만 한다. 관리형 토큰 5분이 승인 TTL 10분보다 먼저 끝나면 그대로 차단한다. 새 의존성·정책 ID·OPA·DB·라우트·콘솔 변경은 없다.
- 근거: 이전 초안은 요청자 재시도 모델과 기존 high_impact_check·acceptance·dispatch_effect_lab의 즉시 실행 기대 충돌 때문에 중단했다. 이번 결정은 그 중단 결정을 **저장 토큰의 현재 유효성 재검증에 한해 대체**한다. 기존 공개 OSS/인증 비교와 라이브러리를 재사용하는 작은 연동 보강이며 외부 SDK나 스크립트를 도입하지 않았다. 로컬 ponytail 스킬(MIT)은 최소 변경 검토에만 적용했다. [요구사항·호출 경로·이전 중단 이력](../../research/llm-wiki/analysis/fresh-requester-d152/README.md).
- 다음 단계·결정 필요(미구현): 승인 API를 승인 기록만 남기는 흐름으로 바꾸고 요청자가 새 transport 토큰으로 재시도하는 모델은 UX 변경이므로 이번에 구현하지 않는다. 새 jti와 원 PAC digest의 분리, 같은 주체·장치·인자·승인 TTL 결속, 재사용·동시 소비 및 기존 시험 기대값을 별도 결정해야 한다. 이번 구현은 새 로그인/재인증이나 요청자 재시도를 증명하지 않는다.

## D-156 발급자 비활성과 자원 서버 재접근을 분리하고 토큰 대상의 수락 증거를 빠뜨리지 않는다 (2026-10-20, DEV-08)

- 근거: [RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)의 캐시/철회 공백, [원자 요구사항·출처·코드 지문](../../research/llm-wiki/analysis/resource-residual/README.md), [로컬 13건 시험](../../full_stack_lab/tests/resource_residual_check.py)·[격리 PostgreSQL 시험](../../full_stack_lab/tests/resource_residual_pg_check.py). 현재 발급자 introspection 캐시는 없고 TTL 0, HTTP 응답은 기존 `no-store`다. 업스트림 풀·세션 폐기와 실행기의 종료 상태 재검사는 이미 있어 재구현하지 않았다. 공개 GitHub 스킬·기존 PyJWT/SDK를 조사했고 기존 의존성과 표준 라이브러리만 재사용했다. 새 의존성·정책 ID·DB 구조·권한·콘솔 변경은 없다.

D-154의 회전 커밋과 서명 append 사이 장애/과거 DB 복원 공백은 변경하지 않는다. [작업 보고](../../research/llm-wiki/status/reports/2026-10-20-resource-server-residual.md).

## D-157 SIEM 전송 UID를 원장 행과 사슬 해시에 묶고 전송 시도는 로그로 남긴다 (2026-10-20, DEV-61)

- 문제: 수신 확인 뒤 큐 커밋이 실패하거나 워커가 종료되면 같은 사건이 다시 전송된다. 재전송 시 UID가 안정적으로 유지되도록 묶여 있지 않았고, 전송 시도 기록은 DB 큐의 `attempts`에만 있어 커밋이 롤백되면 함께 사라졌다. D-128은 `metadata.uid`와 `Idempotency-Key`를 고정했지만 판정 UID는 원장 행 ID·사슬 해시에 결속되지 않은 상태였다.
- 결정: 판정 사건의 UID는 `mint:decisions:<원장 행 ID>:<entry_sha256>`로 재구성한다. 사슬이 없는 과거 판정·승인 감사·경보는 소스, 행 ID, UTC로 정규화한 기록 시각의 SHA-256 해시를 쓴다. 사슬 해시가 유효하지 않으면 시각 기반 UID로 조용히 대체하지 않고 전송 실패로 남긴다. `metadata.uid`와 `Idempotency-Key`는 같은 값을 쓴다. 워커는 전송 직전·응답·큐 커밋마다 UID를 표준 오류 INFO 로그에 남기며, 본문·사유·토큰·주소·원격 응답 본문은 로그에 넣지 않는다. 원장은 수정하거나 삭제하지 않는다.
- 근거: 로컬 시험(Windows Python 3.12.14, 2026-10-20)에서 새 UID·로그·TLS 시험 7건이 통과했다. 실제 로컬 CA 검증과 호스트명 불일치 거부, SQLite `PRIMARY KEY(uid)` 중복 제거를 포함하지만 PostgreSQL 시험은 아니다. 기존 SIEM 회귀 14건도 통과했다. 요구사항은 [분석 README](../../research/llm-wiki/analysis/siem-dedup/README.md)의 SIEM-UID-01~03, SIEM-LOG-01, SIEM-TLS-01 표를 따르며, UID 의미는 [OCSF 1.4.0 Metadata](https://raw.githubusercontent.com/ocsf/ocsf-schema/1.4.0/objects/metadata.json)를, 커밋 경계는 [Psycopg 트랜잭션 문서](https://www.psycopg.org/psycopg3/docs/basic/transactions.html)를 참고했다. 실제 PostgreSQL 격리 시험 [siem_queue_pg_check.py](../../full_stack_lab/tests/siem_queue_pg_check.py)는 트리거 기록, 503 재시도, 수신 200 뒤 큐 커밋 직전 SIGKILL, 재시작, `SKIP LOCKED` 병행을 검사하도록 작성했다. 새 의존성과 DB 스키마 변경은 없다. 고정 판본은 cryptography 50.0.1, psycopg 3.3.5, psycopg-pool 3.3.1이다. [작업 보고](../../research/llm-wiki/status/reports/2026-10-20-siem-dedup.md).
- 한계: 실제 PostgreSQL 시험은 **미실행**이다. 트리거·잠금·SIGKILL 후 재시작·누락 0은 확인되지 않았고, "3개 사건·5회 시도·4회 커밋"은 예상값이며 관측 결과가 아니다. 로컬 TLS·UID 시험은 DB 통합 증거가 아니다. 고정 게이트웨이 이미지의 의존성 검증과 CI pyflakes는 미검증이다. 전달은 최소 한 번 방식이며 중복 제거는 수신 측 UID 유일 키와 내구 저장에 의존한다. 정확히 한 번 전달, 순서 보장, 전체 HTTP 시간 제한은 없다. D-128로 보낸 판정과 비-UTC 세션 사건은 UID가 달라질 수 있어 구 워커 정지 후 수신 측 별칭 연결이 필요하며, 자동 전환은 구현하지 않았다. 로그의 시도 수는 전송 직전 행 수이고 로그 유실·회전은 범위 밖이다. 실제 SIEM 저장·검색, 솔루션 배포, PJ1 시험은 하지 않았다.

## D-159 관리형 Linux 토큰 헬퍼 캐시를 정상 heartbeat 주기 안에 유지한다 (2026-10-20, Codex luna)

- 문제: 배포 직후 첫 MCP 호출이 401을 내고 다음 heartbeat 뒤 회복한다는 관찰이 있었다. 401은 `RequireBearer` 인증 실패 challenge와 맞는다. 정책 해시 불일치는 `managed_failure`에서 403, 세션 결속 실패는 `ServerPath`에서 404이므로 관찰된 401과 다르다.
- 결정: Linux 관리 에이전트의 헤더 토큰 캐시를 120초에서 180초로 늘린다. 토큰 뒤 순차 실행하는 관측기 둘은 각 최대 40초, 활성 loop 대기는 60초라 알려진 반복 구간은 140초다. 180초는 이 경계를 덮되 장치 토큰의 300초 수명과 heartbeat 신선도 180초를 넘지 않는다. 비준수 heartbeat·loop 예외의 즉시 캐시 삭제와 고정 거부 Bearer는 유지한다. 새 의존성·정책·DB·라우트 변경은 없다.
- 근거: `console.sh ensure_env`는 Ed25519 키를 `.env`에 없을 때만 만들며 agent-service에 개인 키, gateway에 공개 키를 준다. `device_token`은 5분 토큰을 발급한다. D-148 고정 Bearer는 게이트웨이에서 401을 받고 다음 정상 발급 전까지 이어질 수 있다. 새 `managed_token_cache_check.py`는 140초 이상·300초 미만 경계와 캐시 적용을 확인한다. [작업 보고](../../research/llm-wiki/status/reports/2026-10-20-post-deploy-401.md).
- 한계: 당시 런타임 로그가 없어 유력 원인이지 인과 확정은 아니다. 회귀는 소스 설정 검사이며 배포 재현과 PJ1 실제 하네스 호출이 남았다. 키 회전·폐기 기록·하네스 재시도는 당시 로그 없이 배제할 수 없다.

- 기록·표시: 위험 평가와 승인 사건에는 설정 모드(`solo_mode`)와 root가 그 모드로 승인했는지(`solo_operator`)를 각각 참/거짓으로 기록하고, 콘솔은 해당 판단의 승인 방식을 표시한다. 환경 설정 전환 자체의 원장 기록은 아래 보강을 본다. 설정 변경 이력은 배포·변경 관리 기록으로 남겨야 하며, 이를 제품 원장 증거라고 주장하지 않는다.
- 계정 추가: `field add-account`는 비밀번호를 숨긴 표준입력으로 받아 해시만 저장한다. 비밀번호는 명령 인자·환경 변수·설정 파일·stdout에 넣지 않는다. 계정 식별자는 principal로 DB에 저장된다.
- 근거: 소유자 지시(10-20)는 운영 편의를 우선하되 보안 통제를 약화하지 않는 범위로 한정한다. [D-175 반려 판단](../../research/llm-wiki/analysis/review-1020/d175-arbitration.md)은 이 결정과 무관하며 변경하지 않는다.
- 한계: 단독 운영 설정만으로 2인 통제를 대체하지 않는다. 독립 변경 관리 연동은 구현하지 않았다(기동 시 전환 기록은 아래 보강).
- 보강(2026-10-21): 콘솔 기동 때 `ROOT_SOLO_APPROVAL`의 참/거짓을 `approval_events`의 `solo-mode` 행으로 관측 기록한다. 직전 기록과 값이 같으면 쓰지 않고, 다르면 전환 행 하나를 추가한다(`review.record_solo_mode_observation`, 시험 `tests/solo_mode_ledger_check.py`). 환경 변수 원문은 쓰지 않는다. 기록이 실패하면 기동 로그에 오류를 남기고 기동은 계속한다. 값을 바꿔도 재기동 전에는 관측되지 않으며, 바꾸고 되돌리는 사이에 기동이 없었다면 그 전환은 원장에 보이지 않는다.
- 보강(2026-10-21): 한 화면 승인(`approve_and_register`)도 개별 승인과 같은 방식으로 `solo_mode`·`solo_operator`를 `intake-one-click` 사건 `scope`와 `risk_assessment`에 실제 값으로 남긴다. 표식은 기록값일 뿐 승인자 수 계산에는 쓰지 않는다(시험 `tests/oneclick_markers_provenance_check.py`).
## D-189 위험 등급의 승인 방식: 높음은 관리자 2명, 매우 높음은 관리자 2명과 위험 수용 사유 (2026-10-21)

대체: D-143 ③과 D-187의 승인 방식 부분. 두 결정의 점수표·최소 등급·기존 서버 30일 유예·치명적 발견 수용 분리는 유지한다.

- 문제: D-143은 높음에 "관리자 2명 또는 위험 수용 사유(1명으로 가능)", 매우 높음에 "2명과 사유"를 두었고, D-187은 둘 다 "2명 필수, 사유는 치명적 발견에만"으로 바꿨다. 두 결정이 한 변경으로 사람 수와 사유 의무를 함께 다뤄 시험 2건이 충돌했다.
- 결정: 낮음·보통은 관리자 1명(변경 없음). 높음은 서로 다른 관리자 2명이 필수이며 "1명 + 서면 사유" 대안은 폐지한다. 매우 높음은 서로 다른 관리자 2명과 서면 위험 수용 사유(10자 이상)가 모두 필요하다. `risk_tier.APPROVAL`은 `high: {approvers: 2, reason: "none"}`, `very_high: {approvers: 2, reason: "required"}`다. 사유는 승인 클릭마다 받고 사람 수를 대신하지 못하며, 사람 수도 사유를 대신하지 못한다. `package`의 승인 방식 표시(매우 높음은 「관리자 2명 및 위험 수용 사유」)는 같은 표에서 만든다.
- 결정: 세 경로가 같은 표를 쓴다. 개별 승인(`risk_tier_gate`)과 한 화면 승인(`approve_and_register`)은 `risk_tier.decide`로 판정하고, 등록(`core.register_server`)은 승인 증거의 서로 다른 승인자 수와 매우 높음의 기록된 사유(`risk_assessment.written_reason`)를 다시 확인한다. 한 화면 승인은 매우 높음에서만 위험 수용 사유를 입력받으며 승인자별 사유를 `one_click_pending.risk_reasons`와 `risk_assessment.reasons`에 남긴다. `intake-cosign`(개별 승인)과 `intake-one-click`(한 화면 승인)이 1차 승인을, `risk_assessment.approvers`가 최종 승인자를 잇는다.
- 결정: 치명적 발견 수용은 `review.accept_risk`의 별도 절차로 남고 위험 등급 승인이 이를 대체하지 않는다. `PAC-13`·`P-X-APPROVAL-001`·`MCP-CATALOG-001`·`P-APPROVAL-EXPIRY-001`은 바꾸지 않았고 새 정책 ID는 없다.
- 근거: 사유는 사람을 대체할 수 없다. 한 사람이 글을 써서 "다른 관리자 2명"을 충족한 것으로 기록하면 원장과 화면이 없었던 독립 2인 통제를 있었다고 말하게 되며, 같은 이유로 root 단독 운영(D-188)도 승인자 수를 부풀리지 않는다. 사유 의무와 2인 요건은 서로 다른 통제라서 한쪽을 올린다고 다른 쪽을 없앨 근거가 되지 않는다. MCP Tools 명세는 사람의 거부 가능성과 annotations 불신만 요구하고 등급별 승인자 수·사유 의무를 정하지 않으므로 이 수치는 MINT의 정책이며 표준의 필수 요구로 적지 않는다. 판단 문서는 [D-189 승인 방식](../../research/llm-wiki/analysis/review-1020/d189-approval-method.md)이다.
- 한계: 높음 이상 도입에는 두 번째 관리자 계정이 반드시 필요하다. 한 사람이 운영하는 현장은 `./console.sh field add-account`로 관리자를 추가해 승인하며, 한 사람을 두 명으로 기록하는 경로는 복원하지 않는다. 같은 사람의 별도 토큰은 한 명으로 센다. 매우 높음의 사유는 사용자가 쓴 글이라 내용의 타당성은 확인하지 않는다. 기기 배포·실제 DB 경로(PostgreSQL) 시험은 이 변경에서 하지 않았다.

## D-182 관리형 엔드포인트 OS 관측은 제한된 디스크 버퍼로 재전송한다 (2026-10-21)

- 문제: 관리형 Linux/Windows OS 관측기는 게이트웨이 전송이 실패하면 원천 커서를 유지해 재시도하지만, 오프라인 동안 재연결 전에 프로세스가 재시작되거나 관측 주기가 지나면 안전한 내구 큐가 없다. 하트비트 공백은 별도 일시 격리(180초 후 거부)로 처리해야 한다.
- 결정: OS 거부 이벤트만 기존 보호 설정 경로에 표준 라이브러리 JSONL 버퍼로 내구 저장한다. 원천 커서와 버퍼 커서를 분리하고 버퍼 fsync 뒤 수집 커서만 전진시킨다. 게이트웨이 ACK 뒤 전달 커서를 맞춘다. 재전송은 기존 `raw_sha256` 7일 중복 규칙과 `(endpoint_id,event_id)` 유일 키를 따른다. 정제 이벤트와 해시만 저장하며 원문 로그/XML·토큰·자격은 저장하지 않는다.
- 상한: 8 MiB, 10,000건, 7일. 한도에 닿으면 해당 원천 커서를 전진시키지 않아 추가 수집을 멈춘다. 한도 초과로 버퍼에 들어가지 못한 이벤트 수와 보존 만료 폐기는 재연결 시 고정 UID·건수·사유를 `endpoint_buffer_events`에 append-only 적재한다. 용량 초과 기록은 수집 중단을 뜻하며 OS 원천의 영구 유실을 뜻하지 않는다. 해당 표가 필요한 이유는 기존 `endpoint_agents.detail.observation` 상태가 마지막 값으로 덮어써져 폐기 이력을 보존하지 않기 때문이다.
- 건수 의미: 값은 보고 한 번(같은 보고 uid) 안에서 「용량 초과로 버퍼에 넣지 못한 고유 건수 + 보존 기간(7일) 만료로 버퍼에서 지운 건수」의 합이며, 둘이 섞이면 사유는 mixed다. 같은 uid 안에서만 단조 증가하고, 보고가 성공하면 카운터가 0이 되어 다음 건수는 새 uid로 보고된다. 용량 초과로 거부된 줄이 나중에 적재돼도 이미 보고된 값에서 빼지 않는다. 콘솔·관리자 조회 API에는 이 값을 읽는 경로가 없고(쓰기 경로만 있음), 사람이 읽는 문구는 422 응답과 ValueError 두 곳뿐이며 라벨은 「미적재·만료 건수」다.
- 정책 경계: 버퍼는 관측 전달 보장만 보강한다. 오프라인 중 게이트웨이 heartbeat가 끊기면 기존 일시 격리(180초 만료 후 거부)는 그대로 적용한다. D-159의 180초 Linux 토큰 캐시는 heartbeat/정책 통신 공백을 처리하며 관측 버퍼나 격리 완화가 아니다.
- 근거·시험·한계: [원자 요구사항과 근거](../../research/llm-wiki/analysis/endpoint-offline-buffer/README.md), [작업 보고](../../research/llm-wiki/status/reports/2026-10-21-endpoint-offline-buffer.md). 로컬 단위·구문 시험만 수행했다. 실제 PostgreSQL/게이트웨이 중복 판정, 장치 파일 ACL, OS journal/event log 재시작·경합, 배포와 PJ1은 미실행이다.
## D-176 반복된 보안 정책 위반은 직원·서버 조합을 설정 기간 자동 중지한다 (2026-10-21, DEV-74)

- 문제: 여러 차례 보안 위반 판정이 누적돼도 운영자 감시 전까지 같은 직원이 재시도할 수 있고, 전체 차단을 위반으로 세면 승인·동의·구성 문제의 정상 거부가 자동 중지로 이어진다.
- 결정: 관측 단위는 직원×서버다. 판정 원장의 실제 `decision='Block'` 중 `MCP-EGRESS-002`, `MCP-DATA-EGRESS-001`, `P-DLP-001`, `P-CHAIN-001`, `P-FLOW-001`만 위반으로 집계한다. 미승인 서버 경로(`MCP-EGRESS-001`), PAC 실행 범위(`PAC-09`~`PAC-12`), 분류·카탈로그·등록 상태, 계정·엔드포인트 상태, 호출 상한, 정책·저장소 장애, 관리자 중지, 그리고 승인 대기·동의(`P-CONSENT-001`) 거부는 세지 않는다. PAC 실행 범위는 승인·자산 설정 누락과 사용자 행위를 판정 ID만으로 가를 수 없어 제외한다. 이 목록은 `core.AUTO_SUSPEND_POLICIES`에 고정한다.
- 설정: `AUTO_SUSPEND_THRESHOLD=5`, `AUTO_SUSPEND_WINDOW_SECONDS=600`, `AUTO_SUSPEND_DURATION_SECONDS=900`이 기본값이며 Compose 환경변수로 조정한다. 위반을 남긴 결정과 자동 중지 상태·`approval_events` 원장 사건은 한 트랜잭션에서 커밋한다. 원장 사건은 행위자 `automatic`, 정책 목록, 직원·서버, 임계, 집계 건수, 관측 창, 해제 예정 시각을 포함한다.
- 집행·복구: D-181 `user_server_suspensions` 부분 유일 인덱스, `P-SUSPEND-001`, 최종 dispatch 확인, 관리자 재개 경로를 그대로 쓴다. 자동 상태는 `expires_at`으로 만료하며, 다음 호출에서 만료를 원장에 기록하고 정상 호출을 허용한다. 해제 전 다음 호출은 기존 직원·서버 상태와 정책 ID로 차단한다. 집계 상태 조회가 실패하면 `P-CONTROL-FAIL-CLOSED`로 차단하며 그 실패는 위반 집계에 넣지 않는다.
- 경합·한계: 자동 중지 삽입은 D-181과 같은 직원 advisory lock과 기존 부분 유일 인덱스로 직렬화한다. 임계에 도달한 호출은 이미 차단 판정된 호출이다. 그 시각 전에 전송 transaction을 통과한 호출은 취소할 수 없고 기록만 남는다. 관측 창은 서버별이며 다른 서버의 위반은 합산하지 않는다.
- 정정(2026-10-21, 브랜치 `10/21-d176-record-path`): 집계 SELECT가 실패해도 Block 판정 행과 체인 갱신은 롤백되지 않는다. 자동 중지 검사는 그 뒤 SAVEPOINT에서 실행하고, 실패는 오류 로그로 남기며 판정은 Block 그대로다. 다음 호출이 집계를 다시 하므로 실패한 행도 임계 집계에 든다. 실패 표식은 판정 행에 붙이지 않았다(원장 행 수정 금지, 기존 JSON 필드마다 소비자가 있음). 상세는 [감사 보고 8-A](../../research/llm-wiki/status/reports/2026-10-21-criteria-audit.md).
- 보강(2026-10-21, 브랜치 `10/21-d176-followup`): 집계 실패는 로그만으로 두지 않고 `approval_events`에 사건 `auto-suspend-count-failed`(outcome `recorded`, 판정 행 id·직원·서버·정책 id만, 예외 원문 없음)로 append한다. 이 사건 기록이 실패해도 판정 행은 별도 SAVEPOINT 덕분에 유지되고 로그만 남는다. `AUTO_SUSPEND_THRESHOLD`·`WINDOW_SECONDS`·`DURATION_SECONDS`가 1 미만이거나 정책 목록이 비면 게이트웨이 기동을 거부한다(기본값 5·600·900은 통과, 현재 배포 설정 불변).
- 근거: [방향 갱신 10-20](../../research/llm-wiki/analysis/direction-1020/README.md) §3 DEV-74, [GB/T 45654—2025 6.5 a)](../../research/llm-wiki/papers/LIB-M32.md), D-181. GB/T는 위법·불량 정보의 입력 검출과 반복 기준을 공시하라는 권고성 표준이며, 위 정책 목록은 MINT의 호출 판정 정책에 한정한 구현 기준이다.

## D-177 미사용 도구는 원장 근거와 유예를 확인해 되돌릴 수 있게 비활성한다 (2026-10-21, DEV-75)

- 문제: 범위를 승인한 도구가 장기간 호출되지 않아도 `tools/list`와 직접 호출에 계속 노출된다. 원장 보존기간보다 긴 공백은 미사용인지 자료가 없는지 구분할 수 없다.
- 결정: 사람의 도구 범위 심사 시각이 있는 Console 도입 도구에 설정 `TOOL_SUNSET_IDLE_DAYS=90`, `TOOL_SUNSET_OBSERVATION_DAYS=30`, `TOOL_SUNSET_GRACE_DAYS=30`을 적용한다. 도구별 마지막 실제 실행 시각은 append-only `decisions`의 `upstream_executed=true`에서 조회하고, 만료 시각은 마지막 사용 또는 심사 시각에 유휴 기한과 30일 유예를 더한다. 설정된 원장 보존기간이 판정 구간보다 짧거나 원장 봉인 구간과 관측 구간이 겹치면 자료 없음으로 남기고 비활성하지 않는다.
- 집행·복구: 자동 비활성 사건은 기존 `approval_events`에 `automatic` 행위자, 서버·도구·마지막 사용·관측 창·유휴기한·유예·만료시각을 append한다. `tools/list`에서는 제외하고 직접 호출은 기존 `P-APPROVAL-EXPIRY-001`로 차단한다. 다른 관리자의 도구 범위 재심사·재승인은 새 사건으로 기존 자동 비활성을 해제한다. 자동 연장은 관측 창 안 실제 사용이 있는 경우에만 기존 서버 승인기한을 늘리고, 범위는 확장하지 않으며 사용 이력·창·기한을 원장에 기록한다.
- 이유: 집계 장애·자료 공백을 미사용으로 간주하면 정상 도구를 잘못 비활성할 수 있다. 따라서 실패 사건을 기록하고 새 비활성 사건을 만들지 않는다. 도구별 집계 테이블은 만들지 않는다.
- 목록 시 상태 조회에 실패한 도구는 오류로 기록하고 그 도구만 숨긴다. 직접 호출도 상태를 확인하지 못하면 기존 `P-CONTROL-FAIL-CLOSED`로 차단한다.
- 근거·한계: [DEV-75 분석](../../research/llm-wiki/analysis/tool-sunset/README.md), [방향 갱신 10-20](../../research/llm-wiki/analysis/direction-1020/README.md) §3 DEV-75, TC260 4.2.1(b). 2026-10-17 확인한 LIB-M31 2.0은 비구속 권고 프레임워크이며 3.0 발표 이후 최신판이 아니다. 코드 구현·로컬 격리 시험만 수행했다. 기기·PJ1은 미실행이다.

## D-181 직원별 MCP 서버 이용 중지·재개는 계정을 두고 그 조합만 막는다 (2026-10-21, DEV-79)

- 문제: 사고 대응에서 사람이 한 직원의 한 서버 이용만 즉시 멈출 수단이 없었다. 계정 중지(`set_account_status`)는 콘솔과 모든 서버를 끊고, D-122 서버 중지는 모든 직원을 끊는다.

- 근거: [방향 갱신 10-20](../../research/llm-wiki/analysis/direction-1020/README.md) 3장 DEV-79, [통제 검토](../../research/llm-wiki/analysis/direction-1020/control-review.md) 105행(근거 M05 **제2항**·TC260 4.2.3(b)-(c), README의 제3항은 정정), [원자 요구사항·근거](../../research/llm-wiki/analysis/user-server-suspend/README.md).
- 한계: 이미 전송된 호출은 취소하지 않는다(기록만). `tools/list`는 그대로 보이고 호출만 거부한다. 재개에 독립 승인은 요구하지 않는다(관리자 1명 운영). DEV-74 자동 중지는 아래 D-176에서 같은 상태를 재사용한다. 기기 배포·PJ1 실제 하네스 시험은 미실행이다.

## D-179 출처 증명은 신뢰 키로 검증하고 미제공만 통과시킨다 (2026-10-21, DEV-77)

- 문제: DEV-73 F3에서 이미지 서명·출처 증명은 DEV-77로 분리했다. 기존 소스 해시·라이선스·SBOM 분석은 누가 무엇을 빌드했는지 서명으로 증명하지 않으며, D-114 실행기는 내부 미러 commit·고정 레시피를 별도로 보장한다.

## D-180 실행기 이전 승인 판본으로 되돌릴 때 세대·계약을 함께 전환한다 (2026-10-21, DEV-78)

- 문제: D-114 실행기는 승인된 커밋을 실행·재조정하지만, 새 실행에 문제가 생겼을 때 과거 승인 이미지와 D-149 계약을 같은 전환에서 복구하는 경로가 없다.
- 결정: `runtime-active` 승인 이벤트에 당시 사람 승인 계약의 서버·도구별 설명/입력/출력 해시·서버 판본, 계약 SHA-256, 승인자·시각을 append-only로 보존한다. 관리자는 그 이력이 있는 과거 세대만 고른다. `registry/contracts.lock.json`은 설치/기준 잠금이고 서버별 변경 이력은 아니므로 되돌리기의 이력 원본으로 사용하지 않는다. 출력 해시 NULL도 미고정 상태로 재해석하지 않고 당시 값 그대로 저장한다.
- 전환: API는 관리자 권한·한 줄 사유·현재 운영 상태·대상 이력/철회 상태를 확인하고 현재 ACTIVE 세대를 STOPPING으로 바꾸며 요청 사건을 같은 DB 트랜잭션에서 append한다. worker는 기존 컨테이너·망을 제거한 뒤, 하나의 DB 트랜잭션에서 철회·종료·공급망 중지와 계약 해시를 재검사하고 승인 해시를 과거 스냅샷으로 되돌린 다음 과거 이미지의 새 세대를 QUEUED로 만든다. 기존 부분 유일 색인이 동시 ACTIVE를 막고 기존 전송 직전 D-149 계약 재확인이 호출을 판정한다. 되돌리기 실행 이벤트는 이력 세대의 계약 스냅샷을 그대로 이어받는다.
- 근거: [DEV-78 설계·검증 기록](../../research/llm-wiki/analysis/runtime-rollback/README.md), D-114 실행기 보고, D-144의 같은 상태/원장 트랜잭션·append-only 규칙, D-149 판본별 출력 해시, D-154의 실패 순서 구분.
- 한계: 새 스냅샷 기록 전의 과거 세대는 증거를 추정하지 않으므로 선택할 수 없다. 이전 이미지가 로컬 엔진에 남아 있어야 하며 레시피 판본이 현재 고정 설정과 다르면 실행을 거부한다. PostgreSQL 다중 작업자 경합·실제 이미지 재기동·MCP 호출 판정·실기기/PJ1은 별도 검증 전까지 미실행이다.
- 정정 (2026-10-21, 결함 처리 [판단 문서](../../research/llm-wiki/analysis/runtime-rollback/defects-1021.md)): **이 결정이 말하는 「철회·종료·공급망 중지 판본 거부」 중 `runtime-revoked`·`runtime-terminated`·`runtime-supply-chain-stop` 사건을 읽는 가드(`runtime_rollback_options`·요청 API·worker `approval_problem`·reconcile, 4곳)는 현재 동작하지 않는다.** 이 사건을 기록하는 코드가 저장소 어디에도 없어 가드가 찾을 행이 생기지 않는다(시험에서 사건을 직접 넣을 때만 막는다). 실제 차단은 서버 상태 검사(`DISABLED`·`BLOCKED_SUPPLY_CHAIN`, 수명주기 `TERMINATING`·`TERMINATED`·`RETIRED`, 열린 중지, 종료·종료 중인 이용 관계)가 한다. 사건 기록은 판정 경로를 바꾸므로 이 정정에서 추가하지 않고 별도 작업으로 둔다. 같은 처리에서 실행기 `import uuid` 누락, 되돌림 세대의 소스 지문 읽기(없으면 `Refused`), 거부·차단으로 멈춘 되돌림 세대의 재큐잉 금지(`stop_refused` 표식, 중단은 기존대로 복구), `runtime-rollback-queued` 사건의 세대 행 ID, 요청 쪽 거부의 원장 기록(`runtime-rollback-request-refused`)을 고쳤다. 기기 재배포와 되돌리기 1회 실행을 확인하기 전까지 「기기 확인」으로 올리지 않는다.

- **2026-10-28 정정 — D-299 2차 대체:** 이 결정의 솔루션 소스 실행·이미지 운영 검사·출구 프록시·실행 판본 전환 부분은 제거하고 엔드포인트 실행 재승인으로 전환한다. 당시 본문·측정·감사 이력은 보존한다.

## D-183 관리형 Linux 헤더 브로커를 AppArmor 신원에 결속하며 정상군 확인 전에는 경고 단계를 유지한다 (2026-10-21, DEV-81 F1)

- **검증·되돌릴 조건**: [재작업 보고](../../research/llm-wiki/status/reports/2026-10-21-dev73-rework.md). 기존 시험 기대값·AST는 보존했다. 실제 DB 잠금/경합·Linux 반복 교체·엔진 매핑/정지·OSS MCP 검증이 실패하면 지원 엔진/실행 경로를 열지 않는다. 메시지별 컨테이너의 상태 있는 MCP 호환성은 검증 후 별도 결정한다.

## D-191 외부 AI 게이트웨이(LiteLLM 등)는 업스트림 방식을 주력으로, 호출 직전 판정 API를 애드온으로 둔다 (2026-10-22)

- 문제: 기업이 LiteLLM 같은 AI 게이트웨이로 MCP를 중앙 연결하면 직원 PC의 하네스가 MINT를 거치지 않는다. 평가에서 「LiteLLM 쪽에서 MCP를 연동하는 경우는 커버되지 않느냐」는 지적이 있었고, 애드온만으로 방어할 수 있다는 방향이 주어졌다.
- 결정 A(주력): AI 게이트웨이의 MCP 서버가 MINT `/mcp/<서버>/`를 업스트림으로 가리키고 직원이 자기 MINT 토큰을 서버별 헤더로 보낸다. MINT의 판정·전송 직전 재검사·승인·출력 통제가 그대로 적용된다. `addons/litellm/gen_mcp_servers.py`가 운영 중인 서버 목록으로 LiteLLM `mcp_servers`(`oauth_delegate`)를 만든다. 공유 서비스 키를 쓰지 않는다.
- 결정 B·C: MCP를 게이트웨이에 직접 등록한 경우를 위해 `POST /api/addon/v1/mcp-decision`(호출 직전 판정)과 `/mcp-result`(사후 기록)를 둔다. 판정은 `core.execute_call`의 기존 경로에 `_decide_only`를 주어 upstream 전송만 건너뛴다. 신원은 직원 MCP 토큰에서만 정하고 게이트웨이가 주장하는 사용자는 기록만 한다. 라우트는 `Depends(caller)`이고 `mcp` scope를 요구한다. LiteLLM용 가드레일은 `addons/litellm/mint_guardrail.py`, 다른 게이트웨이는 [HTTP 계약](AI_GATEWAY_ADDON.md)을 쓴다.
- 결정: 승인 대기 건은 이 경로에서 만들지 않는다(승인되면 MINT가 같은 호출을 직접 한 번 더 보내 이중 실행된다). 사후 기록은 `approval_events`에 덧붙이고 판정 행을 고치지 않는다. MINT가 답하지 못하거나 허용이 아니면 호출자는 차단한다.
- 이유: B 방식은 판정과 전송 사이를 MINT가 쥐지 못해 A보다 보장이 약하다. 그래서 A를 권하고 B는 이미 직접 등록된 MCP를 위한 보완으로 둔다. 새 의존성·새 테이블 없이 기존 판정 함수와 원장을 재사용한다.
- 앞단 변경: `field/Caddyfile`의 HTTPS 사이트에 `/api/addon/v1/*`를 추가했고(적용에는 스택 재기동 필요), `llm/standalone/Caddyfile` 출구에 같은 경로를 허용했다.
- 되돌릴 조건: 평가자가 B를 요구하지 않거나 모든 대상 게이트웨이가 A를 쓸 수 있으면 B 라우트와 `_decide_only`를 제거한다. B로 사람 승인·출력 통제까지 요구받으면 A만 권고한다.
- 근거·시험·한계: [연동 문서](AI_GATEWAY_ADDON.md), [작업 보고](../../research/llm-wiki/status/reports/2026-10-22-ai-gateway-addon.md), [분석](../../research/llm-wiki/analysis/litellm-mint-opportunities-20261022.md). 판정 API는 제품 스택에 배포되지 않아 실제 MINT와의 B 연동은 미실행이다.

## D-192 로컬 MCP(PC 격리 실행)를 원클릭 승인 안에서 쓸 수 있게 한다 (2026-10-22)
- 문제(10-22 기기 실측): DEV-73 실행 경로는 배포돼 있었지만 로컬 신청·작업이 0건이었다. ① 매니페스트를 오프라인 키로 손 서명하고 기기 환경변수(`LOCAL_MANIFEST_PUBKEY`·`LOCAL_IMAGE_MIRRORS`·`LOCAL_ENGINE_SETTINGS`)를 손으로 넣어야 했고, ② 엔진 종류·**정확한 판본**을 기기 값 하나로 모든 PC에 강제해 PC마다 다른 docker 판본이 전부 거부됐으며, ③ 이미지를 PC에 미리 반입해야 했고(`--pull=never`), ④ 콘솔에 신청·승인 화면이 없었다. 저장소형 stdio 서버는 기기 내부 레시피(MarkItDown 하나)가 없으면 어떤 경로로도 실행되지 않았다.

- 남은 한계: docker에 userns-remap이 없으면 격리 구성이 「탈출 시 호스트 root」로 표시되고 키트가 그 위험 수용을 기본값으로 싣는다(승인 화면의 격리 구성에 표시). 비밀이 필요한 로컬 서버는 범위 밖. 이미지 서명(DEV-77)은 `확인 안 됨`.

- 후속(10-22): ① 승인 화면 「격리 구성」을 기기 환경변수 `LOCAL_ENGINE_SETTINGS`가 아니라 관찰 PC 실행기가 보고해 `local_job_events.evidence->'isolation'`에 남긴 최신 값(엔진·판본·사용자 매핑 범위, `engine` 항목 추가)으로 표시한다. 측정이 없을 때만 「확인 안 됨」. ② 마운트 대상을 관리 계정 홈 절대경로에서 컨테이너 안 고정 경로 `/workspace/<상대경로>`로 바꿨다(podman idmap `--mount`·docker `-v` 둘 다; docker는 원천만 고정한 홈 경로). 같은 서버의 실행 인자(`/workspace/mcp-docs`)가 PC 계정 이름과 무관해져 여러 직원 PC에서 한 서버를 쓴다. 호스트 쪽 검사(홈 아래 상대 경로·점 시작 거부·심볼릭 링크 거부·inode 재확인)는 그대로다.

## D-194 ID는 정의 정본 하나를 두고, 번호는 `--next`로만 받으며, CI가 정의·참조를 검사한다 (2026-10-22, WIKI-04)

- 같이 한 정리: D-175 둘째 정의를 D-193으로 옮기고 10-21 재작업 보고에 정정을 덧붙였다. `full_stack_lab/llm/standalone/compose.yaml`의 D-190은 D-191이다. 장부에 없는 정책 ID를 부르던 시험 두 곳은 실제 ID로, `lifecycle_tables.sql`의 위험 매핑은 폐기된 P-AUTHZ-DENY-001 대신 P-AUTHZ-ALLOW-001로 바꿨다(시드 문자열만 바뀌고 판정은 같다). 백로그 접두어 AIG·RM·OPS를 시트 ID 체계에 넣었다. 시트에는 모든 계열의 정의·참조·관련 ID를 담은 「추적」 탭(`sheet/tabs/47-trace.csv`)이 생긴다.
- 이유: 사람이 번호를 고르면 병렬 레인에서 반드시 겹친다. 겹침을 병합 뒤에 찾으면 이미 서로 다른 뜻으로 참조가 퍼진다. 정의가 하나뿐이어야 시트·문서·코드·룰셋 사이의 연결을 기계가 따라갈 수 있다.
- 한계: 원격에 올리지 않은 로컬 번호는 보지 못한다(받은 즉시 정의 줄을 쓰고 푸시하는 규칙으로 줄인다). 정의 정본이 JSON·표인 계열은 줄 위치만 알 뿐 의미를 비교하지 않는다. 열린 브랜치의 중복·정의 없는 참조는 병합 때까지 이 검사에 잡히지 않는다. 커밋 SHA와 규제 대장 번호(REQ-·RQ-·CAP-·CTL-·RSK-)는 범위 밖이다.

## D-173 국외 처리 심사를 등록별 현재 위치와 규칙에 결속한다 (2026-10-21, RM-03)

10-20 소유자 결정의 등록 시 1회 심사를 구현한다. `review_server_residency`의 기존 신청자와 승인자 독립성 검사를 통과한 공급자 호스팅 등록만 재사용 심사를 얻는다. 심사 해시는 서버 ID, 엔드포인트, 도입 신청 ID, 정규화한 처리국과 저장국, 처리자, 근거 참조, 이전 근거, 전체 관할 규칙 팩을 함께 덮는다. 심사 기록과 감사 사건에 같은 해시를 남긴다.

호출 시 현재 값으로 해시를 다시 계산하고 일치하는 경우에만 서버 대상에 `transfer_reviewed=true`를 넣는다. OPA의 예외는 내부 등급 국가 규칙의 `approval`에만 적용한다. 중요 등급의 `deny`, 미확인 위치, 도구 인자의 별도 외부 목적지, 기존 DLP와 PAC 차단은 풀지 않는다. 기존 심사 기록은 결속 해시가 없으므로 자동 승격하지 않고 위치 재심사 뒤 적용한다. 규칙 팩이 없거나 국외 이전 근거가 비면 위치 기록만 가능하고 반복 승인 면제는 없다.

새 의존성 없이 기존 OPA와 Python 표준 해시 구현을 재사용했다. 공식 [Rego 언어](https://www.openpolicyagent.org/docs/policy-language)와 [object.get](https://www.openpolicyagent.org/docs/policy-reference/builtins/object)의 누락 기본값 동작을 확인했다. 기존 122개 OPA 기대값은 변경하지 않고 8개 새 시험을 추가했다. 로컬 정책 시험과 DB 대역 경로 시험은 실기기 승인이나 실제 국외 전송 검증으로 세지 않는다. 구현과 검증 상세는 [작업 보고](../../research/llm-wiki/status/reports/2026-10-21-residency-transfer-review.md)에 둔다.

## D-196 macOS 키트는 기존 정책·브로커를 재사용하고 계정·pf·launchd만 어댑터로 연결한다 (2026-10-22, W5-KIT-MACOS)

- **문제**: 개인 키트가 Linux·Windows만 제공해 macOS 직원의 설치·활성화 경로가 없었다.
- **결정**: `managed-macos.py`가 dscl 관리 계정, Mach-O 공식 설치본 탐색, shim/셸 함수, pf 전용 하위 anchor와 launchd를
  구성한다. 전송·관리 설정·heartbeat·헤더 반환은 기존 Linux 코드를 재사용한다. 플랫폼별 점검을 별도로 보존해 Linux
  AppArmor/nft 항목을 macOS에서 참으로 보고하지 않는다. 공개 프로그램 디렉터리는 읽을 수 있도록 설치 umask022,
  장치 비밀은 명시700·mkstemp600으로 분리한다.
- **직원 흐름**: 콘솔에서 macOS 연결 파일을 받고 표시된 bash 명령 한 줄·관리자 암호 한 번으로 실행한다. 5분·1회용
  다운로드 자격은 인증 헤더용 파일에만 들어가고 URL·셸 기록·환경에 넣지 않는다. 원본 연결 파일과 임시 자격 파일을 지운다.
  기존 `/api/pc-kit` POST에서만 쓰도록 자격을 제한하고 DB의 원자 UPDATE로 소비한다. 등록 토큰과 해시 도메인을 분리한다.
- **런타임·제거**: 없으면 공식 PSF 서명 Python3.14.9 pkg를 같은 관리자 권한으로 설치한다. 공식 하네스 기설치는 D-71과 같다.
  재설치 전 rollback하며 제거는 launchd·shim·실행기·pf·설정·프로그램·계정 역순이다. 공유 Python은 유지한다.
- **한계**: PF는 Apple의 안정 API가 아니다. 관리 UID TCP/UDP 밖 프로토콜·같은 UID 헬퍼 호출·관리자 우회·프로세스 격리는
  보장하지 않는다. 실제 macOS 정상군·복구는 미실행이다. Linux·Windows 기존 시험 기대값은 변경하지 않았다.
- **근거·검증**: [분석](../../research/llm-wiki/analysis/kit-macos/README.md),
  [보고](../../research/llm-wiki/status/reports/2026-10-22-kit-macos.md). 새 오프라인11건·기존 콘솔15건 통과,
  구문/공개 엔드포인트 검사 통과. pyflakes는 도구 부재·네트워크 제약으로 미실행. 독립 검토의 판본·경로 fixture·umask 지적 수정.

## D-198 서버 추가만 있는 정책 변경은 장치가 가진 서버를 막지 않는다 (2026-10-23)

> 2026-10-25 D-238로 대체: 정책 판정은 통제 해시만 보고, 재렌더링 비교와 내려 준 정책 기억은 삭제했다.

- **문제**: 관리자가 서버 하나를 승인하면 관리형 정책 해시가 바뀌어(`endpoint_plane.managed_policy`가 서버 경로·허용 목록을
  해시에 넣는다), PC가 새 정책을 받는 최대 60초 동안 그 직원의 모든 MCP가 `ENDPOINT-MANAGED-001`로 끊겼다.
  `managed_failure`가 장치 보고 해시·토큰의 `device_policy`를 현재 해시와 통째로 비교하기 때문이다.
- **결정**: 장치가 설치한 서버 목록(heartbeat가 해시 일치 때 `detail.policy_servers`로 기록)으로 정책을 다시 렌더링해
  보고 해시와 같고, 그 목록이 현재 서버의 부분집합이면 "서버 추가만"으로 본다. 이때 이미 가진 서버는 통과하고 새 서버는
  `server` 인자로 막는다("PC가 새 정책을 적용하면 사용"). 재렌더링이 보고 해시와 다르면(방화벽 허용 목록·보호 설정·헤더 도우미·
  게이트웨이 주소 변경) 또는 제거된 서버가 있거나 기록이 없으면 지금처럼 전부 막는다(fail-closed). 토큰 발급(`mint`)은
  정확 일치만 허용한다. heartbeat도 같은 판정으로 구성 해시를 비교해 갱신 직전의 보고가 격리로 이어지지 않는다.
- **정정(10-23 오후)**: 서버 **제거**도 서버 목록만 다른 변경으로 본다. PJ1 실사용 중 원격 MCP 하나(deepwiki)가 상위 오류로
  ERROR가 되자 사용 목록에서 빠져, 그 PC의 모든 MCP가 키트가 새 정책을 받을 때까지 `ENDPOINT-MANAGED-001`로 끊겼다.
  제거된 서버는 게이트웨이가 호출마다 거절하므로(`server` 인자 → "사용할 수 없는 서버입니다.") 전체 차단으로 얻는 통제가 없다.
  재렌더링이 보고 해시와 같아야 한다는 조건은 그대로라 허용 목록·보호 설정·헤더 도우미 변경은 제거와 겹쳐도 계속 전부 막는다.
- **정정 2(10-23 오후)**: 로컬 작업(`local_jobs.validate_job`)도 같은 규칙을 쓴다(`endpoint_plane.policy_accepted`). 정확 일치만
  받던 탓에 서버 하나를 철회·승인하거나 원격 서버 하나가 ERROR가 되면 키트가 새 정책을 받을 때까지 그 PC의 로컬 작업이 모두
  `/control` 409로 컨테이너 전에 실패했다(PJ1 read_multiple_files·memory 관찰). 작업과 장치의 정책 해시는 계속 같아야 하며
  `/control`은 작업의 해시를 돌려준다.
- **범위 밖**: 키트의 60초 갱신 주기. 갱신 주기·즉시 갱신 신호는 키트 파일이라
  재설치로만 반영되며 이 변경에 넣지 않았다.
- **근거·시험**: `full_stack_lab/tests/managed_policy_gap_check.py` 4건(서버 추가 허용·새 서버 보류, 허용 목록·프록시·헬퍼 변경 차단,
  제거·기록 없음·낡은 토큰 차단, heartbeat). 기존 시험 기대값 불변,
  [보고](../../research/llm-wiki/status/reports/2026-10-23-policy-refresh-gap.md).

## D-199 원클릭 승인에서 관리자가 도구 분류를 제안값 이하로 낮출 수 있다 (2026-10-23)

- **문제**: 공식 `mcp/filesystem` 이미지는 도구에 `readOnlyHint`를 달지 않아 `read_file`·`list_directory`·`directory_tree` 같은
  읽기 도구가 쓰기(w)로 제안·등록됐다. 쓰기 중복 실행 방지(P-RATE-003)가 같은 인자로 다시 부른 읽기를 막아 PJ1 실사용이 멈췄다.
- **결정**: 승인 화면의 도구마다 분류를 고를 수 있다. 제안값보다 **낮추기만** 받는다(위험 등급은 제안 분류로 산정했으므로 올리면
  등급이 낮게 남는다). 바꾼 값만 `one_click_scope.actions`에 남겨 공동 승인 범위 비교와 감사 기록에 쓰고, 게이트웨이 등록 범위
  가드(`core.register_server`)도 같은 규칙으로 다시 확인한다. 기본 제안 규칙(`suggested_action`·`intake_proposal.action`)은 그대로다.
- **재신청**: 이미 등록된 서버의 분류를 고치려면 철회 후 새 신청이 필요하다(`core.register_server`가 승인 하나에 서버 하나만 허용).
  그런데 중복 신청 검사가 철회된(DISABLED) 서버의 승인 신청까지 진행 중으로 세어 재신청이 영구히 409였다. 철회된 등록은 대상을
  비운다. 새 신청은 검사·승인을 처음부터 다시 거친다.
- **범위 밖**: 주석 없는 도구를 입력 스키마·설명으로 읽기 후보로 추정해 표시하는 것. 확정은 사람이 한다는 원칙만 우선 반영했다.
- **시험**: `full_stack_lab/tests/intake_one_click_check.py`의 `test_admin_may_lower_tool_action_only_and_gateway_accepts_it`
  (게이트웨이 이미지에서 20건 통과). 이미지 없이 도는 `intake_one_click_ast_check.py`는 로컬 실행 승인 경로(D-192)가 쓰는
  `discovery`를 싣지 않아 9건이 실패하고 있었다. 함께 실어 12건 통과.

## D-200 로컬 MCP 이미지 준비 임대를 갱신하고 종료 진단을 전달한다 (2026-10-23, W14-LOCAL-RUNNER)

- 결정: 초기화의 이미지 준비에 최대 180초를 부여하고 기존 제어 조회에서 실행 전 수령 임대를 갱신한다. 실제 시작 후에는 20초 상한을 적용한다. 저장소 허용 목록·digest·서명·세대·철회 검사를 유지한다.
- 종료 코드와 제한된 표준 오류를 수집하고 비밀 검사 뒤 한국어 진단으로 전달한다. 실행 권한 거부 시 관리 UID를 유지하며 root로 재시도하지 않는다.
- 설치 선택지는 Docker 사용자 재매핑 또는 rootless Podman이다. 현재 root 서비스의 Podman 자동 사용자 공간은 rootless와 다르므로 설치만으로 rootless 지원을 주장하지 않는다. 전용 엔진 계정·마운트 매핑·회수 경로 검증이 필요하다.
- 근거·검증·한계: [작업 보고](../../research/llm-wiki/status/reports/2026-10-23-local-runner-usability.md). 기기·PJ1 접속 및 배포는 이번 범위에서 제외한다.

## D-197 Windows 키트의 UAC 승인과 보호 설치기 준비를 한 파일에 묶는다 (2026-10-23)

- **문제**: 10-22 Windows 실측은 IT 선행 배포·로그아웃·모델 로그인 안내 누락으로 D-71의 파일 하나/UAC 한 번 기준에 미달했다.
- **결정**: 기존 인증된 `/api/pc-kit`의 `packaging=oneclick`이 ZIP과 ASCII PowerShell 템플릿을 담은 `.cmd`를 만든다. UAC 한 번으로 승인한 전체 파일의 SHA-256과 읽기 잠금으로 같은 바이트를 사용하고, 파일 목록·해시 검증 뒤 기존 보호 경로·승인 JSON을 준비한다. 새 라우트·의존성·자동 장치 활성화는 없다.
- **신뢰 경계**: 기존 `Get-EndpointApprovedKit`·작업자의 경로/ACL/해시 검증은 유지한다. 기존 승인물이 있으면 정확히 일치해야 하고 손상·다른 버전을 덮어쓰지 않는다. 최초 신뢰는 콘솔에서 받은 파일에 대한 관리자의 명시적 UAC 승인이다. SHA-256은 발행자 서명이 아니며 코드 서명 인증서는 추가하지 않는다. `AllSigned`는 거부하고 IT 서명 경로를 유지한다. 자식 작업자만 프로세스 범위 `RemoteSigned`로 실행하며 시스템·그룹 정책은 변경하지 않는다.
- **계정**: 새 경로는 표준 직원에게도 별도 비관리자 계정을 사용한다. `CreateProfile`로 프로필을 만들고 직원 프로필에서 하네스를 복사한다. 기존 관리 계정의 실행 중 프로세스 거부·SID 방화벽·보호 설정·SYSTEM 헤더 도우미·로그온 트레이 작업은 그대로다. 설치 종료는 조직 활성화 대기이고, 실제 하네스 사용과 모델 로그인은 관리 계정에서 한다.
- **안내**: 설치 결과에 관리 계정과 `claude auth login`, `codex login --device-auth`만 표시한다. 모델 자격 수집·전달·로그 기록을 추가하지 않는다.
- **검증/한계**: 기존 Windows 16개와 새 오프라인 9개 시험 통과. 실제 UAC·프로필 생성·Windows 실설치·장치 활성화·모델 로그인은 미실행이며 리더의 pj3 검수가 남는다. 공식 하네스 사전 설치와 신뢰된 콘솔 다운로드는 필요하다. 초기 실패로 남은 보호 설치물·기존 승인판 갱신·재설치는 자동 덮어쓰기하지 않는다. [분석](../../research/llm-wiki/analysis/windows-oneclick-2026-10-23.md) · [보고](../../research/llm-wiki/status/reports/2026-10-23-windows-oneclick.md).
