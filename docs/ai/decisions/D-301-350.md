# 설계 결정 번호 301~350

## D-301 Codex 허용 목록은 비어 있어도 표를 두고, 모든 MCP 호출은 관리형 훅으로 중앙에 남긴다 (2026-10-31)

- 증상: pj3(Windows 11)에서 Codex가 미등록 Ghidra MCP(pyghidra-mcp)를 켜 도구 4개를 호출했지만 중앙에는 인벤토리 `shadow` 행만 남았다. 호출 기록·경보·감사가 없었다.
- 원인 1: Codex `requirements.toml`의 `[mcp_servers]` 표가 없으면 제한하지 않고, 있으나 비면 전부 끈다(learn.chatgpt.com managed configuration). 승인 서버가 0개인 장치에는 표가 빠졌다.
- 원인 2: 경보는 게이트웨이 호출 판정에서만 만들었다. 로컬 MCP·커넥터 호출은 게이트웨이를 거치지 않는다.
- 결정: 엔드포인트 정책·실기기 키트·실습 워크스테이션 렌더러가 빈 `[mcp_servers]` 표를 항상 둔다. Claude Code `managed-settings.json`과 Codex `requirements.toml`에 `PostToolUse` 훅(`mcp__*`)을 넣는다. 훅은 키트 `agent.py hook`이 직원 홈 `.mcpgw/tool-events.jsonl`에 서버·도구 이름, 인자 크기·SHA-256, 결과 크기, 실패만 남기고 서비스가 `/api/endpoint/tool-events`로 보낸다. 중앙 `endpoint_tool_events`는 경로(게이트웨이·커넥터·로컬)를 붙인다. 로컬 경로 첫 호출, 엔드포인트가 보고한 미등록 설정·확인된 수신기는 `unapproved-endpoint-mcp` 경보(SIEM 큐 포함).
- 셸: Windows Codex는 훅을 PowerShell로 실행해 `&` 호출 연산자가 필요하고, Claude Code는 `command`+`args`로 둔다.
- 대안: stdio 중계(설정 재작성)는 레퍼런스(Obot Sentry·Runlayer·Endor·Mintive)가 관리형 훅을 쓰는 것과 달리 설정 충돌과 우회 재작성이 생겨 보조로 미뤘다.
- 검증: pj3 — 빈 표 뒤 `ghidra … disabled: requirements`, Codex ChatGPT 앱 호출 → `hook: PostToolUse Completed` → 콘솔 「엔드포인트 호출」. 실제 PostgreSQL 랩 경보 시험.
- 한계: 기록 파일은 직원이 지울 수 있다. Claude Code 훅의 Windows 실행은 미확인. PreToolUse 차단 모드 미구현. 설계서 [OVERHAUL_2026-10-31](../OVERHAUL_2026-10-31.md).

## D-302 엔드포인트 사용자 기능은 한 명령 표를 CLI와 로컬 화면이 같이 쓴다 (2026-10-31)

- 결정: `mint servers·logs·request·login·ui`. 표는 `kit_access.py` 하나이고 Windows `mint.cmd`·Linux `mint`가 하위 명령을 넘긴다. 직원 계정은 서비스의 기존 로컬 통로(파이프 DACL·소켓 SO_PEERCRED)에 더한 `self`·`request` 동작으로 `/api/endpoint/self`·`/api/endpoint/self/requests`만 부른다. `mint ui`는 127.0.0.1 임시 포트·경로 토큰·스크립트 없는 화면, 30분 유휴 시 종료.
- 도입 요청은 `endpoint_mcp_requests`에 쌓이고 관리자가 콘솔 「도입 신청 > 엔드포인트 요청」에서 미리 채운 신청서로 잇거나 닫는다. 엔드포인트가 스스로 등록하지 않는다.
- Codex 앱 내장 런타임(`cua_repl`·`node_repl`)은 벤더 설치 경로면 인벤토리에서 뺀다. BOM이 붙은 하네스 설정도 읽는다.
- 참고: `tailscale web`(localhost 화면), NetBird(CLI·앱 같은 상태).
- 검증: pj3 실기기 `mint servers`·`logs`·`request`·`ui`(네 화면), 콘솔 요청·신청서 미리 채움, 실제 PostgreSQL 랩 8/8.
- 한계: Windows 관리형 장치는 하네스 커넥터·기능 보고를 아직 보내지 않는다. 자가 복구 명령 미구현.

## D-303 커넥터는 기본 승인·발견 시 목록·중앙 차단, 하네스 기본 기능은 커넥터에서 분리한다 (2026-10-31)

- 결정: `/api/integrations`에서 하네스 기능(`kind=feature`)을 빼고, 「MCP 서버 > 커넥터」에는 커넥터만, 「정책 > 하네스 기능」에 기능 켬·차단을 둔다. 기본 승인 커넥터는 「관찰만」 경고 대신 「기본 승인 · 벤더 경유」. 미등록 MCP는 이름별 한 항목.
- 근거: Claude 조직 설정(Capabilities와 Connectors), ChatGPT(설정과 Connectors 탭), Codex(`[features]`와 `[mcp_servers]`)가 모두 둘을 나눈다.

## D-306 root 단독 모드에서 root는 강제 집행하는 최고 관리자, 현장 기본 관리자 admin1~3 (2026-10-31)

- 소유자 지시: root는 다른 관리자와 무관하게 강제 집행할 수 있는 최고 관리자, 기본 관리자 계정 admin1~3.
- 결정: `ROOT_SOLO_APPROVAL=1`(현장 기본 켬, 운영 배포 기본 끔)일 때 root는 본인 신청 건 승인(`require_independent`)과 높은 등급의 서로 다른 관리자 2명 조건을 혼자 충족한다. 원장에는 독립 승인이 아니라 `outcome=forced`·「root 강제 집행」과 승인 기록의 `solo_operator`로 남는다. 매우 높음의 서면 사유는 그대로 요구한다. D-188·D-189의 "root 단독 모드에서도 신청자≠승인자, 높음은 두 번째 관리자" 부분을 대체한다.
- 현장 모드는 기동 때 `admin1~3`(비밀번호 = 아이디)을 만든다. 운영 배포 `mint.sh`는 공개 전에 비밀번호가 기본값인 admin1~3을 중지한다(user와 같음).
- 같은 날: 엔드포인트 요청으로 쓴 신청서는 요청한 직원 명의(`endpoint_request_id`)로 기록하고 그 요청을 닫는다. 실사용 시험에서 관리자가 신청자로 남아 같은 관리자가 승인할 수 없었다.
- 시험: `tests/nested_tx_refactor_check.py`(강제 집행은 호출자 트랜잭션 안에서 forced 기록, 모드가 꺼지면 거부), `event_kind_labels_check.py`.

## D-307 콘솔 결과 축·근거 링크·상세 탐색은 읽기 모델로 제공한다 (2026-11-01)

- 호출의 경로·정책 판정·도구 실행·업무 결과를 별도 표시한다. 저장된 결과 스냅숏을 읽고 원장은 수정하지 않는다. 경보·제한 판정은 허용과 구별하며 출력 크기나 전송 성공으로 업무 성공을 추정하지 않는다.
- 엔드포인트 호출은 기존 주체·서버·도구·시간 창에 장치 일치 조건을 더한다. 후보가 하나일 때만 보조 연결로 표시하고 복수 후보는 판정 연결 없음으로 둔다. 시간 연결은 정확한 호출 식별자가 아니다. `self_summary`와 키트의 함수 본문은 변경하지 않는다.
- 경보 조회는 시간대 있는 시작·종료 또는 시간 수와 페이지 위치를 받는다. 대시보드의 24시간 집계에 사용한 시작·종료를 링크에 담는다. 묶음의 건수·최초·최근은 표시된 원본 범위이며 전체 조회 건수·다음 페이지를 따로 표시한다. 읽음은 사용자별 브라우저에 실제 표시한 ID 범위를 저장하고 서버의 전체 미열람 수로 센다. 삭제·자동 종결은 없다.
- 미등록 MCP 경보는 출처·원본 ID를 조회 시 설정/수신기 상세로 연결한다. 엔드포인트 필터는 재고·수신기·차단의 행과 전체 건수에 함께 적용한다. 사용자·호스트·PC 계정을 분리한다.
- 상세 첫 진입은 `pushState`, 상세 전환·탭은 `replaceState`, 진입 표식이 있는 닫기는 `back`이다. 직접 링크는 URL에서 상세 식별자를 제거한다. 호출 필터·페이지, 재고 커서 이력, 상세 탭도 URL에 둔다. 일회용 키·변경 확인창은 공유 가능한 기록 상세로 저장하지 않는다.
- 신청은 필드별 접근성 오류와 입력을 보존한다. 주소·유형·연결 방식 변경은 이전 도구 선택과 진행 중 결과를 무효화한다. 동의는 본인의 기존 API만 쓰며 일괄 확인창에서 표시된 도구 ID 집합·수·목적지·등급을 확인한다.
- 근거: [History API](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState), [WAI 폼 알림](https://www.w3.org/WAI/tutorials/forms/notifications/), 기존 D-301·D-304. OSS·스킬 판본과 실제 적용 범위는 [작업 보고](../../../research/llm-wiki/status/reports/2026-11-01-console-ux-2.md)에 기록한다. 통제 권한·인가·종료 판정 규칙은 변경하지 않는다.

## D-308 정책 정의와 집행 증거를 분리해 조회한다 (2026-10-31)

- 이유: 관리대장에 운영으로 등록된 정책과 실제 실행 경로에서 집행되는 정책은 같은 사실이 아니다. 원본 오류 시 이전 캐시로 목록을 만들면 현재 로드 상태를 오해할 수 있다.
- 결정: 관리대장 API는 현재 OPA 문서를 직접 조회하고 조회 상태와 시각, 실행 규칙과 정책 데이터의 배포 대조, 최근 24시간 최종 판정 집계를 반환한다. 조직 단위 원장 집계가 추가되므로 관리자 인증을 요구한다. 집행 자체와 원장은 변경하지 않는다.
- 화면: 정책 목록의 집행 주체, 관리 상태, 정의된 결과, 원장 근거, 관련 POL을 분리한다. 상세에는 정의와 집행 근거 및 명시적 연결을 두며 감사 화면으로 이동한다. 서버 권한과 호출 원문을 중복 표시하지 않는다.
- 경계: 배포 해시 일치와 원장 기록은 현재 집행 경로 및 독립 효과의 검증이 아니다. pol_ids가 없는 정책은 POL 연결 미확인이다. 정책 충돌에서 선택되지 않은 규칙과 무효 표시된 기록의 유효성 판정은 집계에 포함하지 않으며, 집계는 최종 policy_id 원장 행 수만 의미한다.
- 검증: UI 93개, 격리 API 시험 6개 및 인증과 제품 문구 정적 검사. 실제 OPA 및 DB 연동, 솔루션 배포와 브라우저 검수는 미실행이다.
- 보고: research/llm-wiki/status/reports/2026-10-31-policy-evidence-ui.md

## D-309 조직 보안 정책 카탈로그는 실행 정책 및 적용 증거와 분리한다 (2026-10-31)

- 이유: 조직의 POL 전체 목록은 구현 규칙 목록과 다른 정보다. 별도 PaC 코드의 존재를 현재 게이트웨이에서 적용 중이라는 표시로 바꾸면 안 된다.
- 결정: 정책 원본과 구현 분류 및 Rego 판정 줄과 시험 정의에서 읽기 전용 제품 카탈로그를 재생성한다. 제품 이미지의 앱 디렉터리에 포함하고 기존 관리자 정책 API로만 제공한다. 원본이 없거나 잘못되면 조회 실패로 구분한다.
- 화면: 조직 보안 정책과 집행 규칙을 나눈다. 조직 정책은 대상, 적용 단계, 구현 방식, 코드 확인과 조직 적용 확인을 표시한다. 상세에는 본문과 통과 및 차단 요건, 시험 정의와 집행 규칙 검토 후보를 둔다.
- 경계: 과거 정적 분류의 구현 상태를 현재 적용 상태로 쓰지 않는다. 규칙 및 시험 정의는 실행 성공을 의미하지 않는다. 정적 검토의 후보 ID가 현재 관리대장에 있더라도 검토된 POL 매핑으로 승격하지 않는다. 원문 지시는 분석 데이터다.
- 검증: 원본 일치와 누락 및 손상된 카탈로그, 규칙 정의 추적 및 화면 이스케이프와 미확인 상태 시험. 기기 배포와 브라우저 검수는 미실행이다.
- 보고: research/llm-wiki/status/reports/2026-10-31-organization-policy-tab.md

## D-310 승인 작업은 처리 대상의 화면으로 이동한다 (2026-10-31)

- 이유: 단독 승인 대기 화면은 호출 승인, 실행 확인, 개인 이용 동의처럼 처리 주체와 목적이 다른 작업을 한곳에 섞는다.
- 결정: 호출 승인은 대시보드의 요약과 전체 목록 탭으로 옮긴다. 실행 확인과 승인 처리 이력은 호출 및 감사 기록으로 옮기고 본인의 이용 동의는 내 계정 메뉴 그룹에 둔다. 가입 승인과 엔드포인트 활성화 및 도입 신청은 기존 관리 화면에서 처리한다. 기존 승인 대기 주소는 새 화면으로 연결한다.
- 경계: 승인, 거부, 증빙 확인, 본인 요청 제한, 승인 번복 및 실행 확인 API는 유지한다. 개인 이용 동의를 관리자 대행 기능으로 확장하지 않는다. 감사 원장과 판정 규칙은 바꾸지 않는다.

- 표시: 480px 이하 로컬 메뉴는 2×2, 경로는 게이트웨이 파랑·커넥터 청록·로컬 노랑, 호출 전체 수는 중립이다. 기존 차단 표 안에 짧은 한국어 사유를 표시한다. 경보는 대상 이름·서버/도구·최근 시각을 먼저 보이고 원본 식별자는 상세에 둔다. 같은 관측의 기록 번호만 제외하고 나머지 근거와 출처가 다르면 별도 묶음을 유지한다.
- 터미널: 요청 시작 때 화면을 비우고 빈 서버 이름 또는 Ctrl+C로 원래 화면으로 돌아간다. 도움말은 명령·역할·예를 명령별 한 줄로 표시한다.
- 한계: 시간 기반 연결은 정확한 요청 식별자가 아니며, 장치 키가 없는 과거 기록과 복수 후보를 임의 연결하지 않는다. 로컬 단위·정적·합성 UI 배치 검사와 실제 원장·하네스 재검증은 구분한다.
- 보고: research/llm-wiki/status/reports/2026-11-01-ui-review-fix.md

## D-331 Windows 로컬 MCP 프로세스에 직원 프로필 위치 변수를 준다 (2026-11-01)
- 문제: PC 실행기는 승인 매니페스트의 환경 변수와 고정 PATH·SystemRoot만 넘겼다. Windows에서는 USERPROFILE·APPDATA·LOCALAPPDATA·TEMP가 없어 Java·Python 서버가 설정·임시 폴더를 정하지 못한다(pj3에서 Ghidra 12.2가 `getDefaultUserSettingsDir`에서 종료).
- 결정: 직원 로그온 토큰으로 `CreateEnvironmentBlock`을 읽어 프로필·시스템 위치 변수(USERPROFILE, APPDATA, LOCALAPPDATA, TEMP, TMP, HOMEDRIVE, HOMEPATH, ProgramData, ProgramFiles 계열, windir 등)만 넣고, 승인 매니페스트 값이 같은 이름(대소문자 무시)을 덮는다. 환경 블록은 대소문자 무시 순서로 정렬한다.
- 넣지 않는 것: PATH, PYTHON*, JAVA_TOOL_OPTIONS, NODE_OPTIONS 등 직원이 바꿀 수 있는 실행 경로·옵션. 승인한 코드 밖을 실행하게 만들기 때문이다.
- 한계: Linux 실행기는 HOME을 주지 않는다(Python·Java는 passwd로 홈을 찾는다). 위치 값 자체는 직원 레지스트리에서 바뀔 수 있으나 실행 코드를 바꾸지는 않는다.

## D-332 Windows에서도 소스(프로세스) 실행 로컬 MCP를 관리형 정책에 싣고, 사전 준비가 소스 설치를 한다 (2026-11-01)
- 문제 1: 관리형 정책이 Windows 장치에서 `deployment=local` 서버를 모두 뺐다(「Windows에는 PC 격리 실행기가 없다」). Windows 키트는 이미 직원 토큰으로 승인 소스를 실행하는 프로세스 실행기(`stdio_windows`·`source_seal`)를 갖고 있어, 승인한 소스형 서버가 Windows 하네스에 나타나지 않았다(Ghidra, pj3).
- 결정 1: `runs_on(windows, server)`로 Windows에서는 컨테이너 실행(이미지) 로컬 서버만 뺀다. 소스 실행 서버는 싣고 `mint`에도 「사용 가능」으로 표시한다.
- 문제 2: 승인 직후 사전 준비(`prepare_once`)가 매니페스트 종류와 무관하게 이미지 준비를 불러 소스 실행 서버는 늘 「내부 미러 이미지가 아닙니다」로 실패했다(pj1). 첫 호출은 소스 준비로 갈라져 동작했지만 잠금 wheel 설치가 첫 호출 기한 안에 들어가야 했다.
- 결정 2: 사전 준비도 첫 호출과 같은 분기로 `stdio_source.prepare`를 긴 기한(`PREFETCH_SECONDS`)으로 부른다. 화면 안내는 「설치 중」.
- 한계: 같은 매니페스트를 여러 OS가 쓰므로 경로 인자·환경 값은 OS 공통 문자열이어야 한다(Windows는 `/opt/...`를 현재 드라이브 기준 `C:\opt\...`로 푼다). OS별 매니페스트는 범위 밖.

## D-333 로컬 MCP 한 호출의 실행 상한을 20초에서 60초로 올린다 (2026-11-01)
- 문제: 로컬 실행은 호출마다 프로세스를 새로 띄우고, 기동·initialize·도구 실행을 게이트웨이 `RUN_SECONDS`·실행기 `READ_SECONDS` 20초 안에 끝내야 했다. Ghidra(pyghidra-mcp)는 JVM 기동만 11~14초라 pj1에서 목록은 겨우 들어가고 디컴파일은 시간 초과, pj3(Windows VM)에서는 목록도 넘쳤다. 게이트웨이의 호출 기한(`UPSTREAM_TIMEOUT_SECONDS`, 기본 90초)이 있는데 로컬만 20초로 다시 잘렸다.
- 결정: 두 상한을 60초로 맞춘다.
- 이유: 철회·정지는 실행기 감시 스레드가 0.2초마다 `/control`을 확인해 세션을 끊으므로 상한은 정지 지연이 아니라 한 호출이 붙잡을 수 있는 최대 시간이다. `quiesce`의 대기 상한만 65초로 늘어난다.
- DB: `local_jobs.run_seconds` 검사 제약(≤20)과 기본값도 60으로 바꾼다. 설치된 DB는 기동 때 제약을 지웠다 다시 만든다.
- 한계: 호출마다 기동하는 구조라 무거운 서버는 매 호출 10초 이상이 든다. 새로 가져온 바이너리의 백그라운드 분석은 호출 사이에 이어지지 않는다(pyghidra-mcp는 `--wait-for-analysis`가 있어야 기동 중에 분석을 끝낸다). 세션 유지형 로컬 실행은 범위 밖.

## D-334 소스 실행 준비 폴더 이름을 해시 앞 16자로 줄인다 (2026-11-01)
- 문제: 준비 폴더를 매니페스트 해시 64자 이름으로 두자 `C:\Program Files\MCPGatewayManaged\sources\<SID>\<64자>\packages\...`의 가장 깊은 wheel 파일이 263자가 되어, 긴 경로가 꺼진 Windows(pj3 `LongPathsEnabled=0`)에서 열리지 않았다. 설치는 16자 `prepare-*` 임시 폴더에서 하므로 성공하고, 이름을 바꾼 뒤의 재검증(`.ready.json` 대조)·실행만 실패했다. 서비스가 다시 뜰 때마다 모든 호출이 「로컬 MCP 실행을 완료하지 못했습니다」로 끝났다.
- 결정: 폴더 이름을 해시 앞 16자(64비트)로 해 설치 때와 같은 길이로 둔다. 한 직원 폴더 안의 캐시 이름이라 충돌 위험은 무시할 수 있고, 내용은 `.ready.json`의 파일별 해시가 그대로 고정한다.
- 함께 고친 것: Windows 키트 파이프 스레드가 재시작 직후 이름 충돌(이전 서비스 파이프를 쥔 클라이언트)로 첫 인스턴스 생성에 실패하면 죽던 것을 1초 간격 재시도로 바꿨다(`FILE_FLAG_FIRST_PIPE_INSTANCE`는 유지).
- 함께 고친 것(2): 실행기는 `-I -S`로 띄워 site를 건너뛰므로 잠금 wheel의 `.pth`(pywin32의 pywintypes 경로)가 적용되지 않아 pj3에서 서버가 시작하자마자 종료했다. 부트스트랩이 패키지 폴더에 `site.addsitedir`를 불러 `.pth`를 읽는다. `.pth`의 import 줄도 해시로 고정한 wheel의 것이라 일반 설치와 같은 신뢰 범위다.
- 한계: 기존 64자 폴더는 남는다(다음 준비가 16자 폴더를 새로 만든다).

## D-335 실행기가 검증을 통과한 소스 폴더의 지문을 기억해 호출마다 전체 검증을 반복하지 않는다 (2026-11-01)
- 문제: 소스 실행 서버는 호출마다 준비 폴더 전체를 보호 상태(ACL)·내용(SHA-256)으로 다시 검증했다. Windows에서는 PowerShell ACL 조회가 파일 8천여 개를 훑어 1분 가까이 걸려, 서버를 띄우기도 전에 한 호출의 상한(D-333)을 다 썼다(pj3 Ghidra: 작업 수령→시작 55초, 「로컬 MCP 실행을 완료하지 못했습니다」).
- 결정: 실행기 프로세스가 전체 검증(또는 설치)을 마친 폴더의 지문(경로·크기·수정 시각·파일 번호의 SHA-256)을 기억한다. 다음 호출은 지문만 다시 재서 같으면 검증을 건너뛰고, 다르면 전체 검증으로 돌아가 바뀐 파일이면 거부한다. 재시작하면 기억이 비어 사전 준비(D-332)가 다시 검증한다.
- 이유: 폴더는 SYSTEM/root 소유로 직원이 쓸 수 없다. 내용을 바꾸면서 크기·수정 시각·파일 번호까지 맞출 수 있는 권한은 이미 기기를 가진 것이라 위협 모델 밖이다.
- 한계: ACL만 바뀐 경우는 지문이 그대로라 다음 재시작까지 모른다(ACL을 바꿀 권한도 관리자 권한이다).

## D-336 docstring 들여쓰기 차이는 로컬 도구 계약 변경으로 보지 않는다 (2026-11-01)
- 문제: 로컬 실행기는 호출마다 도구 설명·입력·출력 스키마의 해시를 승인값과 대조한다. Python 3.13은 컴파일 때 docstring의 공통 들여쓰기를 지우고 3.12는 남긴다. 승인 관찰을 3.12 PC(pj1)에서 하면, 같은 커밋을 3.13 키트로 돌리는 Windows PC(pj3)에서 여러 줄 설명을 가진 도구 5개(Ghidra `decompile_function` 등)가 늘 「계약 불일치」로 거부됐다. 거부 뒤 실행기가 프로세스를 끊어, 원장에는 원인 대신 「로컬 MCP가 종료되었습니다 · 종료 코드 1」만 남았다.
- 결정: 게이트웨이가 제어 응답의 도구 계약에 승인 설명의 `inspect.cleandoc` 해시(`description_clean_sha256`)를 함께 보낸다. 저장한 설명이 승인 해시와 일치할 때만 만든다. 실행기는 원문 해시 또는 정리본 해시가 맞으면 설명이 같다고 본다. 입력·출력 스키마는 그대로 원문 해시만 대조한다.
- 함께 고친 것: 실행기가 계약 불일치로 거부하면 진단 종류를 `contract`로 보내고, 게이트웨이는 「엔드포인트의 도구 계약이 승인값과 달라 실행하지 않았습니다」로 기록한다(종료 코드·시작 로그를 붙이지 않는다).
- 한계: 들여쓰기·앞뒤 빈 줄 외의 차이는 여전히 거부한다. 구 실행기는 정리본 해시를 무시하므로 3.13 PC는 실행기를 갱신해야 한다.

## D-337 팀 정책 시트 11-01판의 단계별 번호를 PaC에 그대로 쓰고, 바뀐 규칙만 다시 맞춘다 (2026-11-01)
- 문제: 팀 시트 「D3-1. MCP 보안 관리 정책」 11-01판이 정책 90개의 번호를 세 자리(`POL-001`~`090`)에서 단계별(`POL-I-01`~`11` 도입 검토, `POL-R-01`~`22` 등록 및 연결, `POL-E-01`~`29` 실행, `POL-O-01`~`19` 관리, `POL-D-01`~`09` 연결 해제 및 폐기)로 바꿨다. 위험·보안 요구사항 번호도 같은 방식(`RSK-I-01`, `SR-I-01` …)이 됐고 위험도는 다시 매겨졌다. 정책 문장·실행 규칙이 바뀐 것은 9건이다.
- 결정: 시트가 정본이므로 PaC·콘솔 정책 목록·시험 이름을 새 번호로 옮긴다. 시트 행 순서가 같아 옛 번호를 순서대로 새 번호에 대응하고(본문 동일 83건으로 확인), 대응표를 `policy/source/renumbering.json`에 둔다. 옛 번호를 적은 분석·결정 기록은 시점 보존으로 그대로 두고, 위키 추적 검사는 옛 번호를 이 대응표로 정의한다.
- 바뀐 규칙: POL-R-15(옛 026)는 OAuth scope에서 사용자·Agent에게 주는 Tool·자료 접근권한까지 넓어져 `connect` 단계에 `requested_access`⊆등록부 `approved_access` 대조를 더했다. POL-O-15(옛 077)는 「인증정보 사용 범위」로 넓어져 입력 `oauth_scopes`를 `credential_scopes`로 바꿨다. POL-D-09(옛 090)는 시트에 실행 규칙이 채워져 제외에서 PaC로 옮기고 `connect`에 `restore` 단계(복원된 주소·허용 Tool·접근권한이 현재 승인과 맞고 폐기·만료되지 않았는지)를 더했다. POL-R-07·09·10(옛 018·020·021)은 OAuth 전용 문장이 MCP 연결 일반으로 바뀌었고 솔루션 기능 분류는 그대로 두되 사유를 고쳤다. POL-R-08·O-07·O-08은 문구·참조 번호만 바뀌었다.
- 함께 고친 것: 카탈로그·추적표·콘솔 목록은 시트 순서(도입→폐기)로 낸다. 단계 이름은 시트대로 「실행」·「관리」다. 「통제 대상」 열이 분류명(MCP Server·Tool / Resource·Agent 등)으로 바뀌어 콘솔 「정책 대상」도 그 값을 보인다.
- 한계: 게이트웨이는 아직 이 패키지로 질의하지 않으므로(policy/README 「게이트웨이 연결」) 새 규칙도 코드·시험 수준이다. POL-D-09의 복원 설정 입력과 POL-R-15의 접근권한 입력을 만드는 기능은 없다. 새 규칙의 독립 반례 시험은 아직 없다.

## D-338 PC 설치 파일을 고정 실행 파일 뒤에 키트를 붙인 실행 파일로 내려준다 (2026-11-02)
- 문제: 콘솔의 설치 파일이 Windows는 `.cmd`, Linux는 ZIP과 `unzip … && install.sh` 명령이었다. 소유자 지시로 직원이 받는 것은 명령 파일이 아닌 실행 파일이어야 한다.
- 결정: 게이트웨이 이미지의 Go 빌드 단계에서 `native/setup`을 Windows(`windows-amd64.exe`, GUI 서브시스템)·Linux(`linux-amd64`, 정적) 실행 파일로 한 번 빌드해 `/opt/mcp-setup`에 둔다. 다운로드 때 직원 자격이 없는 기존 키트를 그 뒤에 붙인다. Windows exe는 붙은 줄(`:MCPGW_COMMAND`)의 PowerShell 명령을 창 없이 실행할 뿐이고, 그 명령·UAC 승인·파일 해시 재확인·메모리 안 ZIP 검증은 D-197의 `.cmd`와 같다. Linux 실행 파일은 붙은 ZIP을 `~/mcp-managed-kit`에 새로 풀고(평면 파일 목록만 허용) `install.sh`를 그대로 실행한다.
- 이유: 설치기 판단은 이미 검증된 PowerShell·설치 스크립트에 그대로 두고, 실행 파일은 그것을 찾아 띄우는 일만 한다. 실행 파일이 사람마다 같으므로 빌드는 이미지에서 한 번이고 다운로드마다 컴파일하지 않는다. 부트스트랩이 파일을 첫 `:MCPGW_PAYLOAD` 줄에서 나누므로 실행 파일 안에는 그 줄이 없어야 한다(시험이 확인).
- 한계: 코드 서명이 없어 Windows SmartScreen이 「알 수 없는 게시자」를 보일 수 있다(서명 인증서가 생기면 빌드 단계에서 서명). Linux 실행 파일은 x86-64만이며, 브라우저가 실행 권한을 주지 않아 `chmod +x` 뒤 터미널에서 실행한다(관리자 암호 입력이 필요). macOS는 그대로 `.command`다. 실행 파일이 없으면 원클릭 받기는 503이고 ZIP 받기(`packaging=zip`)는 그대로다.
