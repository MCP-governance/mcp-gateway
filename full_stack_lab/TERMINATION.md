# 전주기의 마지막: 종료·폐기와 그 판정

이 문서는 MCP 이용 관계를 **끝내는** 절차와, 끝났다고 말할 수 있는 근거를 정리합니다.

저장소의 나머지 부분은 들어오는 것에 촘촘합니다 — 도입 요청, 격리 검증, 승인,
catalog 고정, 공급망 증적. 나가는 것에 대해서는 v1.5까지 `status='DISABLED'` 한
칸뿐이었습니다. 그 한 칸은 "호출을 막았다"만 말하고 "회수했다"는 말하지 못합니다.
**둘은 다른 사실입니다.**

근거는 CISC-W'26 투고 논문
「원격 MCP 서비스 종료 시 권한 회수의 구조적 한계 및 종료 판정 기준 제안」입니다.
여기 구현된 C1~C4 기준과 T1~T3 등급은 그 논문의 5장을 실행 가능한 판정으로 옮긴
것입니다.

---

## 1. 왜 "껐다"가 "끝났다"가 아닌가

논문이 규격 조항으로 특정한 세 가지입니다.

| 사실 | 근거 |
| --- | --- |
| 세션 계층에는 원용할 종료 수단이 없다 | MCP 명세 2026-07-28이 프로토콜 수준 세션을 제거했다. 구 개정판에서도 서버가 종료 요청을 405로 거절할 수 있었다 |
| 폐기 성공 응답은 대상의 상태를 구별하지 않는다 | RFC 7009는 이미 무효인 토큰에도 200을 반환하도록 규정한다. 상태 비저장 접근 토큰은 폐기 뒤에도 만료까지 동작할 수 있다 |
| 서버가 하위 시스템에 보유한 자격은 회수 대상이 아니다 | MCP 인가 명세는 상위 토큰의 전달을 금지한다. 곧 하위 접근은 **별개 인가 영역**이며 회수 주체가 제공자다 |

실측에서도 같은 결과였습니다. 폐기 종단점을 공개한 호스트는 47.0%, 조사 종단점은
10.2%였고, 상위 자격을 완전히 폐기하고 조사 응답으로 확인한 뒤에도 서버 보유 자격을
통한 하위 접근이 5회 모두 성립했습니다.

그래서 종료는 **조치를 수행했다는 사실**이 아니라 **그 조치가 확인해 주는 대상의
범위**로 판단해야 합니다.

## 2. 네 기준과 세 등급

| 기준 | 확인 내용 | 이 저장소가 계산하는 방법 |
| --- | --- | --- |
| **C1 모집단** | 회수 대상을 빠짐없이 열거하고 조치 대상과 대조하였는가 | 회수 대상이 1건 이상 · `UNVERIFIABLE` 없음 · 원격이면 제공자 고지 있음 · 엔드포인트 잔존 0 |
| **C2 수행 권한** | 조치 권한이 있고 증거를 제출받을 수 있는가 | 모든 대상이 회수/만료됨 · `holder='provider'`인 대상은 제공자 증명 보유 |
| **C3 연속성** | 조치부터 전파 완료까지 공백 구간이 없는가 | 차단 시각 이후 실행된 호출 0건 · 원격이면 도달 확인 기록 존재하고 응답 없음 |
| **C4 증거 접근** | 증거가 대상·시점을 특정하며 열람 가능한가 | 모든 회수 대상이 대상·시점 특정 증거를 1건 이상 보유 |

C1과 C4는 **판정의 성립 요건**, C2와 C3은 **충족 정도**를 가릅니다.

| 등급 | 조건 | 의미 |
| --- | --- | --- |
| **T1 종료** | 네 기준 모두 충족 | 이 이용 관계의 종료를 진술할 수 있다 |
| **T2 부분 종료** | C1·C4 충족, C2 또는 C3 미충족 | 잔존 범위를 특정할 수 있어 위험의 상한을 설정할 수 있다 |
| **T3 판단 불가** | C1 또는 C4 미충족 | 잔존 범위를 산정할 수 없다. 추가 증거나 별도 승인이 필요하다 |

T2와 T3의 구별이 실무의 핵심입니다. **T3는 위험 수용 근거 없이 종결되지 않습니다.**
코드가 그것을 강제합니다(`close_case()`).

## 2.1 시작하기 전에 — 폐기 드릴

종료를 결정하기 전에 물어야 하는 것은 "끄면 무엇이 남는가"입니다.

```bash
curl -sS http://localhost:8000/api/termination/drill/github \
  -H "authorization: Bearer $TOKEN" | python3 -m json.tool
```

드릴이 답하는 것은 현재 등급이 아니라 **도달 가능한 최선 등급**입니다. 증거를
전부 모으고 회수를 전부 마쳐도 T1에 닿지 못하는 서버가 있습니다.

| 조건 | 최선 등급 | 왜 |
| --- | --- | --- |
| 로컬 stdio | **T1** | 이중 위임 계층이 없어 제공자 고지가 필요 없습니다 |
| 원격 + 자격 고지 조항 없음 | **T3** | C1의 천장이 이미 정해져 있습니다 |
| 원격 + 고지 있음, 폐기 기록 제출 없음 | **T2** | 제공자 보유 자격의 회수를 확인할 수단이 없습니다 |
| 원격 + 둘 다 있음 | **T1** | — |

함께 나오는 것: 이 서버를 실제로 호출한 주체와 횟수(업무 영향), 회수해야 할
자격의 수, 엔드포인트에 남아 있는 설정 수.

**드릴은 아무것도 바꾸지 않습니다.** 케이스를 만들지도, `lifecycle`을 건드리지도
않습니다. "계산해 봤더니 실행됐다"는 가장 나쁜 종류의 부작용입니다.

이 값을 도입 심사에서 보면 질문이 하나 늘어납니다 — "들일 수 있는가"가 아니라
**"끊을 수 있는가"**.

## 2.2 T3를 줄이는 유일한 자리는 도입 시점이다

논문 5.2는 종료 증거가 "개시 시점의 기록 체계와 계약 설계에 의존하므로 소급
확보가 어렵다"고 적습니다. 그러면 T3를 줄이는 자리는 종료 단계가 아닙니다.

`MCP 도입` 화면의 요청 양식에 종료 조건 세 개가 있습니다.

| 항목 | 없으면 |
| --- | --- |
| 제공자가 하위 위임 자격을 고지한다 | 종료 시 **반드시 T3** |
| 폐기 처리 결과를 대상·시점이 특정된 기록으로 제출한다 | 최선 등급 **T2** |
| 종료 후에도 합의 기간 동안 감사 기록에 접근할 수 있다 | C4의 증거원이 좁아집니다 |

체크박스를 켜고 끌 때마다 화면이 그 서버의 최선 등급을 그 자리에서 말합니다.
제출한 뒤에 알려주면 이미 고른 전송 방식과 계약 조건을 다시 볼 이유가 없습니다.

**여기 기록하는 것은 계약 조항의 존재이지 제공자가 실제로 고지했다는 사실이
아닙니다.** 둘을 같은 칸에 넣으면 조항만 체크해 두고 C1이 충족된 것처럼 보입니다.
조항은 "요청할 권리가 있다"까지이고, 고지는 별도 증거로 들어옵니다.

조직이 이 조건을 **필수**로 만들 준비가 되면 승인 게이트를 켭니다.

```dotenv
INTAKE_EXIT_TERMS_REQUIRED=1
```

켜면 원격 MCP는 제공자 자격 고지 조항 없이 `APPROVED`로 올라가지 않습니다.
기본값이 꺼짐인 이유는 이 실습의 기존 등록 서버들이 도입 심사 이전에 들어온
것들이라, 켜 둔 채로는 승인 시나리오가 통과하지 않기 때문입니다.

## 3. 운영 절차

Console의 `종료·폐기` 화면(관리자 전용) 또는 API로 수행합니다.

### 3.1 종료 절차 시작 — 차단이 먼저다

```bash
curl -sS -X POST http://localhost:8000/api/termination/cases \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"server_id":"github","reason":"계약 종료에 따른 이용 중단"}'
```

이 호출은 **즉시** 다음을 합니다.

1. `mcp_servers.lifecycle = 'TERMINATING'` — 이 순간부터 모든 호출이
   `MCP-DECOMM-001`로 차단됩니다.
2. `cutover_at` 고정 — C3의 기준점입니다.
3. 회수 대상 자동 수집 (3.2).

**순서가 중요합니다.** 회수를 먼저 하고 차단을 나중에 하면 그 사이에 호출이
성립하는 구간이 생기고, 그 구간이 바로 C3이 세는 대상입니다. 스스로 C3을
깨뜨리는 절차가 됩니다.

`MCP-DECOMM-001`은 `MCP-` 접두사라 **관찰 모드에서도 집행됩니다.** 관찰 모드는
권한 모델에 대한 의견일 뿐이고, 폐기는 의견이 아닙니다.

### 3.2 모집단 채우기 (C1)

케이스를 열면 조직이 자체 확보할 수 있는 몫은 자동으로 올라갑니다.

| 출처 | 무엇 | 자동 여부 |
| --- | --- | --- |
| `gateway-ledger` | 감사 기록에서 이 서버를 호출한 모든 주체 | 자동 |
| `endpoint-agent` | 엔드포인트 설정에 남아 있는 이 서버 항목 | 자동 (보고될 때마다 갱신) |
| `operator-manual` | 원격 제공자가 보유한 하위 위임 자격 자리 | 자동으로 `UNVERIFIABLE` 생성 |
| `provider-disclosure` | 제공자가 고지한 보유 자격 | **수동** |

세 번째 줄이 핵심입니다. 원격 서버에는 하위 위임 자격이 있을 개연성이 높은데,
제공자가 고지하지 않으면 **존재 여부조차 알 수 없습니다.** 그래서 자리만 만들고
`UNVERIFIABLE`로 둡니다. 이 한 행이 C1을 미충족으로 만들고 판정을 T3로 내립니다.

> 빈칸을 채워주는 것이 아니라 빈칸을 드러내는 것이 목적입니다.

로컬 stdio 서버에는 이 행을 만들지 않습니다. 이중 위임 계층이 구조적으로 없기
때문입니다. 요구 조건을 전송 방식과 무관하게 두면 로컬 서버가 영원히 T3가 되고,
그러면 아무도 이 판정을 쓰지 않게 됩니다.

### 3.3 회수 기록과 증거 (C2·C4)

대상마다 회수 여부를 기록하고 증거를 붙입니다.

```bash
# 회수 기록
curl -sS -X PUT http://localhost:8000/api/termination/targets/$TARGET_ID \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"status":"REVOKED","note":"인가 서버 콘솔에서 폐기"}'

# 증거 첨부 — 대상과 시점이 없는 증거는 받지 않는다
curl -sS -X POST http://localhost:8000/api/termination/cases/$CASE_ID/evidence \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"kind":"introspection","subject":"access_token jti=abc123",
       "source":"상위 인가 서버 /introspect","target_id":"'$TARGET_ID'",
       "detail":{"active":false}}'
```

증거 종류와 그것이 증명하는 것:

| 종류 | 증명하는 것 | 증명하지 못하는 것 |
| --- | --- | --- |
| `revocation-response` | 요청이 처리되었다 | 대상이 폐기 시점에 유효했는지 (RFC 7009) |
| `introspection` | 인가 서버가 판단하는 토큰의 활성 상태 | 자원 서버의 차단에 반영됐는지 |
| `provider-attestation` | 제공자가 하위 자격을 회수했다 | — (C2의 유일한 충족 수단) |
| `gateway-denial` | 이 조직의 강제 경로가 막았다 | 다른 경로의 접근 |
| `liveness-probe` | 그 주소의 도달 가능성 | 회수 실패 여부 (다른 고객에게 계속 서비스할 수 있음) |
| `endpoint-inventory` | 단말에서 설정이 사라졌다 | — |

`add_evidence()`는 `subject`와 `observed_at`을 필수로 받습니다. "폐기 요청을
보냈다"는 조치의 기록이지 대상 상태의 증거가 아니기 때문입니다.

### 3.4 도달 확인 (C3)

```bash
curl -sS -X POST http://localhost:8000/api/termination/cases/$CASE_ID/probe \
  -H "authorization: Bearer $TOKEN"
```

Gateway가 HTTP HEAD만 보냅니다. MCP 핸드셰이크는 하지 않습니다 — 폐기한 서버와
다시 대화를 시작하지는 않습니다. catalog 갱신도 이 상태에서는 건너뜁니다.

응답이 온다고 해서 곧 "회수 실패"는 아닙니다. 조직의 토큰이 폐기됐어도 그 주소는
다른 고객에게 계속 서비스합니다. 그래서 이 증거의 이름은 **도달 가능성**이고,
판정에서는 C3(전파 완료)의 반증으로만 씁니다. 증거가 말하는 것 이상을 말하지 않습니다.

AI-Infra-Guard의 동적 점검도 같은 시점에 자동으로 큐잉됩니다(§4.3).

### 3.5 판정과 종결

```bash
curl -sS -X POST http://localhost:8000/api/termination/cases/$CASE_ID/assess \
  -H "authorization: Bearer $TOKEN" | python3 -m json.tool
```

판정은 관리대장 행에서 계산됩니다. 같은 케이스를 두 사람이 봐도 같은 등급이
나오고, 등급이 달라졌으면 **어느 행이 바뀌어서 달라졌는지** 말할 수 있습니다.

근거가 바뀌면 판정은 즉시 낡습니다. 회수 대상이나 증거를 추가하면 케이스는
`ASSESSED`에서 `REVOKING`으로 돌아가고 등급이 지워집니다. 낡은 판정과 판정 없음
중 위험한 것은 낡은 판정입니다.

```bash
# T1/T2 종결
curl -sS -X POST http://localhost:8000/api/termination/cases/$CASE_ID/close \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"note":"회수 완료 확인"}'

# T3 종결 — 위험 수용 근거가 없으면 거절된다
curl -sS -X POST http://localhost:8000/api/termination/cases/$CASE_ID/close \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"note":"제공자 고지 미회신","risk_acceptance":"CISO 승인 2026-09-19, 잔존 위험 수용"}'
```

종결하면 `lifecycle='RETIRED'`가 되고 Registry에서 비활성으로 내려갑니다.

### 3.5.1 기한

케이스가 열린 채로 잊히면 "차단은 했으나 아무것도 회수되지 않은 상태"가 무기한
지속됩니다. 그 상태는 T2도 T3도 아니고 **판정 자체가 없는 상태**라 위험 보고에
잡히지도 않습니다. 그래서 기한을 세는 쪽은 판정이 아니라 요약입니다.

```dotenv
TERMINATION_SLA_DAYS=14
```

기한을 넘긴 케이스는 운영 현황 배너와 메뉴 배지에 빨간색으로 올라옵니다.
판정에는 영향을 주지 않습니다 — 늦었다는 것이 회수됐다는 뜻은 아니니까요.

### 3.6 제공자 고지 요청서

T3의 가장 흔한 원인은 제공자가 보유 자격을 고지하지 않는 것이고, 그 상태에서
조직이 할 수 있는 일은 **요청하는 것**뿐입니다. 그 요청을 매번 사람이 새로 쓰게
두면 하지 않게 됩니다.

```bash
curl -sS http://localhost:8000/api/termination/cases/$CASE_ID/disclosure-request \
  -H "authorization: Bearer $TOKEN" | python3 -c 'import json,sys; print(json.load(sys.stdin)["markdown"])'
```

문서에 들어가는 것: 이용 관계와 차단 시각, 현재 판정, **요청 근거**(도입 시 합의한
종료 조건이 있으면 그것을 인용하고, 없으면 그 사실을 적습니다), 요청 사항 세 가지,
그리고 왜 이 요청이 필요한지 — 규격상 조직이 회수할 수 없다는 설명.

Console의 `제공자 고지 요청서` 버튼이 같은 문서를 마크다운으로 내려받습니다.

### 3.7 재개

종결이 되돌릴 수 없으면 "닫지 않는 편이 안전하다"가 되고, 그러면 아무 케이스도
닫히지 않습니다. 새 증거나 잔존 발견이 있으면 사유와 함께 재개합니다.
재개해도 폐기했던 서버가 다시 살아나지는 않습니다 — 되살리는 것은 재개가 아니라
새 도입입니다.

## 4. 판정서

```bash
curl -sS http://localhost:8000/api/termination/cases/$CASE_ID/report \
  -H "authorization: Bearer $TOKEN" | python3 -m json.tool
```

Console의 `판정서 내려받기`와 같은 내용입니다. 감사에 그대로 제출할 수 있도록
네 기준의 충족 여부, 미충족 사유, 회수 대상 전체, 증거 전체, 게이트웨이가 실측한
차단 이후 활동을 한 문서에 담습니다.

## 5. 시연

`github` 서버는 인증 전이라 의도적으로 비활성이고 어떤 시나리오도 쓰지 않으므로,
폐기 시연 대상으로 안전합니다. (같은 흐름을 `./console.sh test`의
`termination-*` 항목이 자동 검증합니다.)

1. `종료·폐기` 화면에서 `GitHub MCP Server`를 골라 사유와 함께 시작합니다.
2. `MCP 실행` 화면에서 이 서버 호출이 `Block · MCP-DECOMM-001`이 되는지 봅니다.
3. 바로 `판정 실행`을 누릅니다 → **T3**. 이유는 "원격 제공자가 하위 위임 자격을
   고지하지 않아 회수 대상의 모집단을 열거할 수 없습니다"입니다.
4. `종결`을 눌러 봅니다 → 위험 수용 근거를 요구합니다.
5. 회수 대상을 회수로 기록하고 증거를 붙인 뒤 다시 판정하면 등급이 올라갑니다.

`./console.sh endpoint`를 함께 올렸다면 4번과 5번 사이에 하나가 더 생깁니다.
`.mcp.json`의 `github` 항목이 `retired-residue`로 바뀌고, 그것이 자동으로 이
케이스의 회수 대상에 추가되어 C1을 다시 미충족으로 만듭니다. **관리대장에서 지운
것과 사람들의 PC에서 사라진 것은 다른 사건입니다.**

## 6. 한계

- 회수 조치 자체는 **이 저장소가 수행하지 않습니다.** 인가 서버의 `/revoke` 호출,
  제공자 콘솔에서의 자격 삭제는 운영자가 하고, 여기에는 그 결과를 기록합니다.
  게이트웨이가 남의 인가 서버에 폐기를 요청하는 자격을 갖는 것은 별개의 위험입니다.
- `liveness-probe`는 HTTP 도달만 봅니다. 그 주소의 서비스가 이 조직의 자격을
  아직 유효하다고 보는지는 알 수 없습니다.
- 제공자 고지는 **계약 단계의 산출물**입니다. 논문 5.2가 적었듯 이들 증거는 개시
  시점의 기록 체계와 계약 설계에 의존하므로 소급 확보가 어렵습니다. 조달 문서에
  하위 자격 고지·폐기 기록 제출·감사 기록 접근권 존속 기간을 명시해야 합니다.
- 이용 관계의 식별자는 이 테스트베드에서 **Registry 서버 하나**입니다. 논문의
  정의(조직·목적·제공자·허용 자원)는 케이스를 열 때 스냅샷으로 굳히지만, 한
  서버를 여러 목적으로 쓰는 조직에서는 이용 관계가 서버보다 잘게 쪼개집니다.
- 종료 케이스의 승인자는 합성 관리자입니다. 4-eyes, 위임, 알림 채널은 미구현입니다.
