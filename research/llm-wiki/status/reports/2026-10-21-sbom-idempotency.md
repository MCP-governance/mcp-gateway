# 2026-10-21 SBOM 일괄 중지 중복 처리 보강

- 작업자: Codex
- 코드 기준: `2045799`에서 시작, 작업 브랜치 `10/21-sheet-runtime-completion`. 다른 작업자의 변경 파일은 건드리지 않았다.
- 시작 근거: DEV-76, D-178, [SBOM 영향 조회 분석](../../analysis/sbom-impact/README.md), [백로그](../backlog.md).
- 해결할 문제와 완료 조건: 기존 중지 서버를 `건너뜀`으로 보고하면서도 중지 사유와 실행기 상태를 덮어쓰던 경로를 없애고, SBOM과 실행 세대의 연결이 끊긴 경우 영향 서버로 판정하지 않는다.

## 결과

`ops_response.suspend()`가 이미 중지된 서버를 읽기 단계에서 거르고, 동시 중지 상황에서는 서버 행 잠금과 중지 행 삽입 결과를 다시 확인한다. 새 중지 행을 만든 경우에만 서버 상태, 실행기 상태, append-only 원장을 변경한다. `False`는 이번 호출에서 새 중지가 생성되지 않았다는 뜻이며 SBOM 일괄 API의 `skipped`에 해당한다. 이미 중지된 서버의 기존 사유와 실행기 오류값을 새 요청의 사유로 바꾸지 않는다.

SBOM 영향 조회는 검사 미완료, 실행 세대의 소스 커밋 불일치, 실행 세대 부재를 `자료 없음`으로 반환한다. 이 경우 저장된 구성요소가 취약 판본과 같아 보여도 해당 서버를 영향 중지 목록에 넣지 않는다. 합성 시험에서 세 분기를 각각 확인했다.

이 변경은 기존 D-178 구현 보완이다. 새로운 정책이나 중지 종류는 추가하지 않았다. 제품 코드와 로컬 대역 시험만 변경했으며 배포와 실제 PostgreSQL 검증은 하지 않았다.

## 실패와 남은 범위

동시 중지 시험은 DB 대역으로 `ON CONFLICT DO NOTHING` 반환을 재현한 것이다. 실제 PostgreSQL 경합과 로컬 실행 정지 수신 확인은 남아 있다. 선행 조회와 서버 행 잠금 사이에 다른 중지가 생기면 로컬 중지 요청은 중복될 수 있지만, 서버와 실행기 상태 및 원장은 두 번째 요청으로 변경되지 않는다. 저장된 SBOM 요약은 200개 제한이며, 원본 전체 목록 대조와 실제 이미지 SBOM 연결은 이번 변경 범위 밖이다.
