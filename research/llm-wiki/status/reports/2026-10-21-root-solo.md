## 결과

원본 클론에서 `10/20-root-solo`를 가져온 뒤 main 추적 스냅샷에서 새 브랜치를 만들었다. 원본 커밋의 부모에는 반려된 DEV-73 구현이 있지만 cherry-pick은 커밋 자체의 변경만 적용했다. 변경 파일은 D-188 결정, field compose/CLI, `review.py`, `agent_service.py`, 계정 검사 파일이다. `DECISIONS.md` 충돌은 main 내용을 보존하고 D-188만 다시 작성해 해결했다. D-175를 추가하거나 수정하지 않았다.

보안 검토 중 root solo 코드가 승인자 수를 등급 요구 인원까지 인위적으로 올리는 경로를 발견했다. 이 경로는 실제 두 번째 승인자 없이 높은 등급을 통과시킬 수 있었다. 이를 제거해 승인자 수를 실제 서로 다른 사람만 세도록 했다. `require_independent`는 root solo와 무관하게 신청자와 승인자가 같으면 거부 사건을 남기고 차단한다.

- 낮음·보통: 현재 등급 정책에 따라 한 명 승인.
- 높음: 기존 D-143 대안 그대로, 두 번째 승인자 또는 서면 위험 수용 사유가 필요하다.
- 매우 높음: 서면 사유와 서로 다른 두 번째 승인자가 모두 필요하다. root 한 명은 두 번째 승인자로 중복 계산되지 않고, 조건 미충족이면 대기 상태에 머문다.
- root solo 설정은 승인 정책의 승인자 수를 바꾸지 않는다. 사용한 설정(`solo_mode`)과 root가 그 설정으로 승인했는지(`solo_operator`)를 위험 평가와 승인 원장 범위에 참/거짓으로 기록한다. 등록 상세 콘솔은 승인 당시 설정을 `단독 운영`, `일반 운영`, 과거 기록이면 `—`로 표시한다.
- 설정값 변경 그 자체를 원장에 쓰는 처리는 없다. 전환 이벤트는 자동 추적되지 않는다. 배포·변경 관리 절차에서 전환을 기록해야 하며, 이를 제품 원장 증거라고 주장하지 않는다.

`field add-account`는 비밀번호를 숨겨 두 번 입력받아 표준입력으로 컨테이너에 전달하고, DB에는 bcrypt 해시를 쓴다. 비밀번호는 명령 인자·환경 변수·설정 파일·stdout에 포함되지 않는다. 명령 출력에는 계정 이름만 표시한다. DB의 `principals.token` 값은 기존 스키마의 principal 식별자(`아이디` 또는 `emp-아이디`)이며 발급 bearer token이 아니다. 로그인 후 발급되는 세션 토큰을 명령에서 만들거나 출력하지 않는다. CLI 도움말의 역할 라벨은 `관리자|직원`으로 표시하고 내부 별칭은 입력 호환용으로만 받는다.

D-188은 root 한 명을 복수 승인자로 간주하던 원본 결정에서 수정했다. 단독 운영 편의가 독립 승인 통제를 대체할 수 없다는 점, 남은 제한, 설정 전환 로그 공백을 결정 기록에 적었다.

## 실패·미완료·한계

- 공유 체크아웃의 `.git` 쓰기가 거부되어(`.git/FETCH_HEAD: Permission denied`) 그 위치에서 `git fetch origin main`과 브랜치 생성은 불가능했다. 작업은 쓰기 가능한 `worktrees/root-solo-main`에서 수행했다. 원격 GitHub로의 fetch도 네트워크 차단으로 실패했다. 따라서 `d3238dcc…`는 현재 로컬 `origin/main` 추적 ref와 원본 클론의 추적 ref가 가리키는 동일한 스냅샷이지, 이번 실행에서 GitHub 최신 HEAD를 재확인한 값은 아니다.
- 기존 `intake_risk_tier_check.py`의 13건은 환경 조건에 따라 건너뛰었다. 실제 PostgreSQL·현장 서비스 시험으로 세지 않는다.
- 설정 전환 자체는 자동 원장화되지 않는다. 외부 변경 기록과의 연결은 후속 과제다.
- 단독 운영자가 매우 높은 등급을 승인할 수 없다는 제한은 의도된 통제다. 추가 관리자 계정을 등록해 독립 승인자를 구성해야 한다.
- `field add-account`는 소스/정적 검사만 했다. DB 연결, 계정 로그인 및 비밀번호 회전은 실행하지 않았다.
