- 공식 MCP Python SDK 실제 호출(2·3차 배포): github `get_me` 실행, context7 실행(벤더 월 한도 응답), `list_commits`는 승인 인자 밖이라 PAC-01 차단, 반복 뒤 P-VOLUME-001 승인 대기. 2차 배포 호출 8건의 전송 의도가 모두 `resolved`.

## 실패·미완료·한계

- 하네스 자연어 E2E와 PJ1 키트 재설치 후 DEV-31·D-105 실기기 확인은 하지 않았다.
- **기기에 현장 모드 기본 계정이 그대로 활성**: 관리자 `root`·직원 `user`의 비밀번호가 계정 이름과 같다(`agent_service.bootstrap_field_accounts`가 첫 기동 때 심음, DB 해시로 확인·값 비노출). 테일넷에 닿는 누구나 관리자 로그인이 가능하다. 계정 자격 변경이라 에이전트가 바꾸지 않았다.
- C의 보호 자원 거부 확인은 조직이 제공자 토큰 사본을 가져야 한다. 제품 스택에는 사본이 없어 `provider_side=unverified`다.
- MCP 세션 재사용(DEV-29)을 하지 않아 지연의 대부분(업스트림 연결·목록)이 남는다. Bearer 장치 토큰은 발신자 결속(DPoP 등)이 없다.
- D의 한국어 표본은 규칙을 읽은 같은 작성자가 썼고, 코퍼스 오탐·미탐 수치는 D 브랜치 실행 결과다(병합 뒤 규칙 파일은 바뀌지 않았다).
- 팀원이 `feat/web-ui` 파일을 기기에 통째로 복사하는 방식이 계속되면 통합 기능이 다시 기기에서 빠진다.
