## 결과

현장 Caddy를 사설 CA HTTPS로 바꾸고 IP 바인딩을 유지했다. 자동 HTTP 리디렉션·시스템 신뢰 등록을 끄며
TLS 1.2/1.3, ECDHE/ECDSA AEAD, IP 기본 SNI를 설정했다. 선택 공개 이름은 별도 인증서 발급 대상과 명시적 MCP Host 허용값으로만 추가한다.
`field_caddy_data`에만 CA 개인 키를 보존하고 `field ca`는 공개 루트·DER SHA-256을 내보낸다.
공개 OAuth·MCP·Console·Git URL은 HTTPS다. 루트 디렉터리는 Console에 읽기 전용으로 제공한다.

Console ZIP의 루트·지문을 Linux 설치기가 네트워크 등록과 설치 변경 전에 검증한다. 직원 PC 키트도
`--ca-sha256` 또는 동봉 지문을 검증한다. Linux 하네스 실행기와 직원 PC 도구의 `harness` 명령은
Claude에 `NODE_EXTRA_CA_CERTS`, Codex에 `CODEX_CA_CERTIFICATE`를 해당 프로세스에만 준다.
에이전트의 공통 통신을 통해 `os-observer.py`도 인증서/호스트 검증을 적용한다. 원격 HTTP와 리디렉션은 거부한다.
기존 내부 격리 랩의 HTTP는 명시적 Dockerfile 빌드 인자로 유지하며 field 렌더링은 HTTPS다.

## 메인: 솔루션 기기에서 실행할 명령

이 절의 명령은 **미실행 인계**다. 변경을 통합한 솔루션 기기(`user@100.83.175.111`)의 저장소에서만 실행한다.
아래 검사는 키·토큰·개인 키를 출력하지 않는다. 기존 루트 볼륨은 지우지 않는다.

```bash
cd full_stack_lab
python3 tests/field_tls_check.py
python3 tests/field_kit_check.py
python3 tests/open_endpoints.py
bash -n console.sh
docker run --rm --network none \
  -e APPLIANCE_BIND=100.83.175.111 \
  -e FIELD_TLS_ADDRESSES='https://100.83.175.111:8080, https://mint.example.internal:8080' \
  -v "$PWD/field/Caddyfile:/etc/caddy/Caddyfile:ro" \
  caddy:2.11.4-alpine caddy adapt --config /etc/caddy/Caddyfile --adapter caddyfile --validate > /tmp/field-tls-d124-caddy.json
./console.sh field up
./console.sh field ca
./console.sh field status
openssl x509 -in field/ca/root.crt -noout -fingerprint -sha256
```

정적 검사 컨테이너는 포트를 게시하지 않고 배치와 별개의 임시 CA를 만든다. 출력의 `:8080` TLS 정책,
internal issuer, TLS 1.2/1.3·암호군·리디렉션 비활성화를 확인한다.
실제 공개 이름을 쓰면 `.env`에 `FIELD_PUBLIC_NAME=실제이름`을 지정한다. 예시 이름은 정적 검사용이다.
공개 IP 이외의 LAN/0.0.0.0 게시가 없는지 `docker compose -f compose.yaml -f compose.field.yaml config`와 호스트 리스닝도 확인한다.
직접 compose 명령에는 `APPLIANCE_BIND`와 `FIELD_TLS_ADDRESSES`를 위와 같이 지정해야 한다.

## 메인: PJ1에서 평문·TLS·키트·실제 하네스 확인

솔루션에서 꺼낸 공개 루트를 승인된 채널로 PJ1에 전달하고 운영자와 SHA-256을 대조한 뒤 진행한다.
`CA`에는 그 경로를 넣는다. 진짜 자격으로 평문 시험을 하지 않는다.

```bash
CA=/승인된경로/root.crt
TARGET=100.83.175.111
openssl x509 -in "$CA" -noout -fingerprint -sha256
curl --noproxy '*' --cacert "$CA" -fsS "https://$TARGET/api/health"
for version in -tls1_2 -tls1_3; do
  timeout 10 openssl s_client -connect "$TARGET:443" -noservername \
    -verify_ip "$TARGET" -CAfile "$CA" -verify_return_error "$version" -brief </dev/null
done
for version in -tls1 -tls1_1; do
  timeout 10 openssl s_client -connect "$TARGET:443" -cipher 'ALL:@SECLEVEL=0' \
    "$version" -brief </dev/null
done
curl --noproxy '*' --max-time 5 -sS -D /tmp/d124-http-headers \
  -o /tmp/d124-http-body "http://$TARGET:443/api/health"
curl --noproxy '*' --max-time 5 -sS -D /tmp/d124-port80-headers \
  -o /tmp/d124-port80-body "http://$TARGET/api/health"
```

TLS 1.2·1.3은 인증서 검증과 IP 이름 검사가 성공해야 한다. TLS 1.0·1.1은 서버의 protocol-version alert를 확인한다.
클라이언트의 지원 암호군 오류나 타임아웃만으로 서버 거부 통과를 선언하지 않는다.
443 평문은 연결 종료 또는 400/426만 허용하며 2xx·3xx·Location·JSON 건강 응답은 실패다. 80은 미게시/연결 거부가 기대값이다.
선택 공개 이름은 `-servername 실제이름 -verify_hostname 실제이름`으로도 검사한다.
다른 CA로 동일 HTTPS 검증이 실패하는지 확인하고 실패 전후 게이트웨이 판정 원장이 늘지 않는지 비교한다.

Console에서 **PJ1의 격리 시험 계정용 새 키트**를 받고 다음을 수행한다. 운영 계정·다른 작업자의 장치는 재설치하지 않는다.

```bash
unzip mcp-managed-kit-linux.zip -d d124-managed-kit
cd d124-managed-kit
openssl x509 -in root.crt -noout -fingerprint -sha256
./install.sh
```

설치 전에 사본의 `ca_sha256`을 바꾼 키트로 실패하고 등록 요청·계정/파일 변경이 없는지 검사한다.
정상 키트로 설치하고 Console에서 기존 독립 활성화 절차를 따른다. 관리 계정 실행기의 Claude·Codex로
**이미 승인된 실제 OSS MCP**의 읽기 도구를 각각 1회 호출하고 fresh 세션·transport 신원·원장의 `decision`과 `policy_id`·upstream 효과를 연결한다.
`managed_state=active`, 새 heartbeat와 inventory·OS 관측의 수신 시각을 확인한다. 설치나 도구 목록 조회만으로 호출 성공을 선언하지 않는다.

복수 클라이언트/동시 키트 발급의 CA 지문 동일성, Caddy 재기동 후 같은 지문·연결 복구,
격리 CA 교체 후 기존 CA 실패→새 키트 재설치 복구를 확인한다. CA 교체는 운영 볼륨에서 하지 않는다.
시스템 CA 저장소의 전후 차이가 없어야 하며 하네스 종료 후 새 CA 환경값이 전역에 남지 않아야 한다.

## 실패·미완료·통합 경계

- Caddy 실제 parser/validate·TLS handshake와 PJ1·운영 배포는 미실행이다. 로컬 소스 문자열 검사는 Caddy 자체 검사와 다르다.
- 위키 전체 검사는 `local-sources/compliance/*/provenance.json` 29개가 이 체크아웃에 없어 미통과다. 새 보고/분석 링크 오류와 코드 해시 불일치는 없다. 자료 원본을 새로 가져오거나 기존 증거 상태를 성공으로 바꾸지 않았다.
- Windows 키트 파일을 수정하지 않았다. 별도 작업은 `enrollment.json.ca_certificate`·`ca_sha256` 검증, 관측 설정의
  `ENDPOINT_CA_CERTIFICATE`·`ENDPOINT_CA_SHA256`, 하네스 환경값을 연결해야 한다. 통합 전 기존 Windows 키트로 사설 CA 성공을 주장하지 않는다.
- 직원 PC 도구는 `harness claude|codex` 경로를 써야 CA가 전달된다. 일반 CLI를 이미 실행한 프로세스에는 적용되지 않는다.
- 루트·지문을 함께 바꾼 악성 ZIP의 진위는 지문 일치만으로 확인할 수 없다. 인증된 배포와 별도 지문 대조가 전제다.
- 기존 HTTP 릴레이/실험 스크립트는 이번 PJ1 TLS 검증 수단으로 쓰지 않는다. 전체 실험 드라이버 이행은 별도 범위다.
