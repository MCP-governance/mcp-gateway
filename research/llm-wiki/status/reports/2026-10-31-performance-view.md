# 성능 화면 측정 기준 정리

- 기준: `feat/console-ui`, 시작 커밋 `56ace776`. 앞선 UI 작업의 미커밋 변경을 보존했다.
- 요청: 지연을 성능으로 변경하고 호출 처리 성능과 엔드포인트 통신 상태를 분리한다. 전체 처리, 구간별 표본, 오류 기준과 측정 상태를 명확히 한다.
- 호출: 게이트웨이 내부의 전체 처리 시간, 자체 처리, MCP 통신과 처리를 중앙값과 95백분위 및 각 표본 수로 표시한다. 상세 구간은 표로 바꿔 표본과 시간을 함께 확인한다. 서버는 95백분위가 높은 순으로 정렬한다. MCP 처리 오류는 기존 특정 미완료 판정 건수이며 실제 실행 여부와 구분한다.
- 집계: 기존 관리자 성능 API는 한 번 정한 시간 범위를 모든 읽기 쿼리에 사용하고 시각과 정렬 정보를 추가한다. 서버별 호출 기록 링크에도 같은 기간과 도구 호출 유형을 전달한다. 원장과 집행 규칙, 인증은 변경하지 않는다.
- 통신: `endpoint-agent/agent.py`의 measure_gateway와 summarise_samples를 확인했다. 시간은 성공한 TCP 연결 측정값이며 HTTP 상태 확인 응답 시간은 시간 표본에 넣지 않는다. 실패율은 연결 점검과 HTTP 상태 확인 요청을 합산한 점검 기준이다. 지터는 연속한 성공 측정 간 차이의 절댓값 평균이다. 이 기준을 라벨과 툴팁에 반영했다.
- 상태: 엔드포인트별 최근 측정과 시각 및 점검 수를 표시한다. 만료된 보고의 시간 값은 숨기고 만료 상태를 표시한다. 보고 없음, 최근 보고의 측정 실패, API 조회 실패를 구분한다. 실제 0ms와 0%는 유지한다. 엔드포인트 전체 백분위 요약은 제거하고 기존 API 필드는 유지한다. 콘솔 서버 TCP 측정 라벨은 실제 경로로 구체화했다.
- 검증: UI 및 번역 4개와 시간 표현 1개, 격리 API 함수 4개의 검사 통과. 기간 공통 적용과 관리자 DB 접근, 구간별 표본 수, 서버 정렬 및 오류 조건, 빈 값과 조회 실패, 최근 및 만료와 미측정, 실제 0과 실패율 100% 표시를 확인했다. JS 및 Python 구문 검사 통과.
- 한계: API 검사는 함수 AST와 DB 대역을 사용했다. 실제 PostgreSQL 백분위 및 정렬, 실기기 통신과 브라우저 및 배포 검수는 미실행이다. 위키와 전체 회귀 검사는 실행하지 않았다.
- 후속: 실행 PC에서 실제 지연 표본과 서버 순서, 만료 및 실패 측정과 새로고침, 기간 링크와 화면 폭에 따른 표 배치를 검수한다. 커밋과 푸시는 하지 않았다.

## 시스템 자원 위치 정리

- 엔드포인트 영역은 엔드포인트 → 게이트웨이 통신으로 명확히 하고 기기 이름을 우선 표시했다. 제목 옆에는 조회 시각만 남기고 행에는 최근 측정 시각을 표시한다. 연결 시간 95백분위와 점검 횟수 설명을 보완했으며 최근, 오래됨, 미측정, 측정 실패로 문구를 정리했다. 집계 기준 변경 없이 기존 테스트 기대값을 맞췄고 JS 구문 검사만 수행했다.

- 후속으로 성능 화면을 호출 처리 성능, MCP 서버별 통신 및 처리, 구간별 처리 시간, 엔드포인트 통신 상태, 시스템 자원 순서로 정렬했다. 순서만 변경하고 JS 구문 검사만 수행했다.

- 사용자 요청으로 시스템 자원을 요약에서 성능 탭 하단으로 이동했다. 기존 측정 영역 ID와 갱신 훅을 유지했다. 단순 배치 변경으로 JS 구문 검사와 변경 공백 검사만 수행했고 추가 테스트 및 위키 검사는 실행하지 않았다. 실제 화면 검수는 미실행이다.
