# 연구 자료를 구현으로 옮기는 방법

## 개발 단위

기능 이름 대신 실패 조건 하나를 개발 단위로 잡습니다. 예를 들어 “도구 계약이 승인 이후 바뀌면 실행 전에 차단한다”는 입력·관찰값·판정·효과를 모두 시험할 수 있습니다.

| 단계 | 작성할 것 | 이 솔루션에서 확인할 곳 |
| --- | --- | --- |
| 위협 선택 | 공격자 권한, 진입점, 자산, 직접·간접 경로 | [위협표](../threats/README.md), [통제 경계](../../../docs/ai/SECURITY_BOUNDARIES.md) |
| 근거 선택 | 원문 절·코드 커밋·독립 재현 여부 | [논문](../papers/README.md), [소스 분석](../solutions/README.md) |
| 사실 계약 | 신원 출처, 계약 해시, 정규화한 인자·자원·목적지 | `full_stack_lab/gateway/app/contract.py`, `classify.py`, `core.py` |
| 통제 구현 | 검사 실패의 결과, 실행 직전 재확인, 경쟁 조건 | `full_stack_lab/opa/pac15.rego`, `decision.rego`, `core.py` |
| 실험 | 허용 대조군, 공격군, 검사기 장애, 독립 효과 | [실험 목록](../experiments/README.md) |
| 보고 | 코드 기준, 확인 범위, 실패, 다음 작업 | [현황](../status/current.md), [양식](../templates/work-report.md) |

## 구현 전 체크

1. 이미 사용하는 FastAPI·OPA·PostgreSQL·Presidio·Gitleaks 등의 경로로 해결할 수 있는지 확인합니다.
2. 요청이 게이트웨이를 지나가는 경우와 엔드포인트에서 직접 연결하는 경우를 나눕니다.
3. 신원은 검증된 transport에서 가져옵니다. 사용자가 쓴 인자나 하네스 이름을 신원으로 승격하지 않습니다.
4. 도구 설명과 annotation은 공급자 주장입니다. 스키마·실제 인자·대상·효과 검증을 대체하지 않습니다.
5. 계약·분류·검사기·정책 엔진이 확인되지 않았을 때 결과를 먼저 정합니다.

## 최소 구현과 검증

공통 호출 경로에서 한 번 검사하고 관련 호출자와 정책 입력을 함께 고칩니다. 단순히 경고 문자열을 추가하는 대신 실제 전송 직전에 결과가 집행되는지 확인합니다. 실행 후 응답 마스킹은 실행 전 차단과 따로 기록합니다.

정적 검사 → 솔루션 기기 반영 → PJ1 실제 하네스 검증의 순서는 저장소 루트 규칙을 따릅니다. 연구 위키의 재생성은 로컬에서 해도 되며 솔루션 Compose를 실행할 이유가 되지 않습니다.

## 가져오기와 비교 기준

오픈소스는 해당 제품의 플러그인 구조·권한 필터·호출량 예약·실행 격리 등 필요한 부분을 검토합니다. 가져오려는 코드의 라이선스와 의존성, 검사 실패 동작을 확인합니다. 비교 실험은 같은 입력·같은 도구·같은 효과 판정을 사용합니다. UI 기능 표만으로 집행 성능이나 보안 우위를 주장하지 않습니다.

## 현황 보고

백로그는 연구 결과 → 설계 결정 → 코드 변경 → 시험 증거의 링크를 유지합니다. `완료`는 합의한 성공 조건이 만족될 때만 씁니다. `코드 확인`, `정적 검사 통과`, `실기기 미확인` 등 중간 상태를 명확히 씁니다.

사용자에게 필요한 자료는 대상을 구체화합니다. “키가 필요함” 대신 “공급자 A의 읽기 전용 테스트 프로젝트와 최소 scope OAuth 자격, 토큰 파일을 배치할 운영자”처럼 씁니다. 실제 자격 값은 보고서에 넣지 않습니다.
