# LiteLLM 중앙 MCP 관리에서 MINT가 추가할 수 있는 역할

확인일: 2026-10-22. 사용자 요청: 위키의 코드 분석과 LiteLLM 공식 기능을 실제로 대조하고 추가 가치의 가능성을 제시한다. 제품 설계 변경·배포 지시가 아니다.

## 판단

**우선 검토할 것은 고위험 도구 호출의 서버 측 승인·철회 집행과, 자체 배포 MCP의 공급망 검증·운영 대응이다.** 도구 등록·ACL·OAuth·입출력 검사·설명 고정·일반 로그는 LiteLLM이 이미 제공하므로 독립 차별점에서 제외한다. 실행 전 계약 불일치 차단과 종료 증거 관리는 보완 후보로 남긴다.

이것은 기존 제품에 없는 기능을 모두 찾아냈다는 주장도, MINT가 실제 중앙 연동을 완료했다는 주장도 아니다. 기존 기능을 활용한 개발 가능성과 고객에게 추가로 제공할 결과를 정리한 것이다. 고정 소스의 특정 결함을 영구적인 제품 차별점으로 삼지 않는다.

## 가능성 1 — 중앙에서 실행하는 고위험 호출의 승인과 철회 집행

**업무 예:** 사내 에이전트가 저장소 삭제·권한 변경·대외 발송 등 조직이 고위험으로 지정한 도구를 실행하려 한다. 도구 사용 권한이 있더라도 그 요청의 주체·대상·인자를 사람이 승인하기 전에는 실행하지 않고, 승인 뒤 인자가 바뀌거나 승인이 만료·철회되면 거부한다. 예시는 정책 대상이며 해당 업무 MCP를 이번에 연결한 것은 아니다.

- LiteLLM은 서버 등록 승인, 도구 ACL, 인자 규칙을 이미 제공한다. [OWASP 매핑 LLM03](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10)은 1.104.0 기준으로 호출별 서버 측 승인 단계를 제공하지 않으며 agent 측 HITL이 필요하다고 설명한다. 현재 전체 제품의 영구 부재로 단정하지 않는다.
- MINT에는 승인한 요청과 실제 전송 요청의 일치를 확인하는 코드가 있다. `dispatch.py:126–140`은 승인 payload의 주체·서버·도구·인자 fingerprint를 대조하고 만료/철회되지 않은 승인을 소비한다. `high_impact.py:45–52`는 검토 범위와 승인 근거를 결속한다. `core.py:1683–1759`는 승인 상태·정책·계정/서버 상태를 전송 전에 재확인한다.
- **추가할 제품 결과:** LiteLLM을 사용하는 여러 앱에서 승인 절차를 각각 구현하지 않고, 중앙에서 동일한 승인 조건·철회·처리 근거를 적용한다. LiteLLM의 기존 신원을 검증 가능한 방식으로 MINT 주체에 연결해야 한다.
- **접점:** 얇은 pre-MCP adapter로 미승인 요청을 거부하고 승인 절차로 보낼 수 있다. 그러나 adapter가 허용을 반환한 뒤 LiteLLM이 별도로 전송하면 검사와 전송 사이 경쟁이 다시 생긴다. 현재 MINT의 최종 전송 검사를 유지하려면 LiteLLM이 MINT의 MCP endpoint를 upstream으로 호출하는 구성이 우선 후보이다. plugin만으로 동일 보장을 내세우지 않는다.
- **검증:** 미승인·인자 변경·승인 만료·철회가 전송 기록의 경계보다 먼저 확정된 경우 upstream 효과 0, 승인한 요청은 한 번만 실행, 승인 후 응답 유실은 실행불명으로 남기는지 확인한다. 최종 intent 확정 뒤 이미 나간 호출을 소급 취소한다는 보장은 하지 않는다(`core.py:1738–1739`).
- **포기 조건:** 고객이 agent의 기존 승인 절차와 LiteLLM 정책으로 요구를 충족하고 중앙 승인 증거를 필요로 하지 않으면 별도 기능을 추가하지 않는다.

## 가능성 2 — 자체 배포 MCP의 공급망 검증과 취약 구성 대응

**업무 예:** 여러 팀이 운영하는 MCP 중 특정 의존 패키지의 취약 판본이 발견됐다. 영향을 받는 서버와 실행 세대를 찾고, 해당 서버를 중지하고, 재검토한 판본으로만 재개한다.

- 서버를 등록하고 승인하는 일과, 그 서버의 소스·구성요소·검증 결과·실행 세대를 대응하는 일은 다르다. LiteLLM 자체 이미지의 서명/보안과 LiteLLM에 연결한 제3자 MCP의 공급망 검증도 구분한다. 이번에 읽은 공식 MCP 관리 안내에서 후자의 전체 업무 흐름은 확인하지 못했다.
- MINT에는 `supply_chain/intake_worker.py`의 source checkout·Syft/Trivy/Semgrep/Gitleaks 검사, `runtime/worker.py`의 승인 재확인·실행 세대·image ID 관리, `gateway/app/sbom_impact.py:80–125`의 저장 SBOM→서버/실행 세대 조회와 기존 중지 경로 연계가 있다. [10-21 보고](../status/reports/2026-10-21-sbom-impact.md)는 시험 종류와 미확인 범위를 구분한다.
- **추가할 제품 결과:** LiteLLM에는 검증한 endpoint와 상태를 연결하고, MINT가 검사·승인·영향 조회·중지·재심사 근거를 제공한다. 초기에는 API로 승인/중지 상태를 연동할 수 있으므로 새로운 MCP 집계 엔진을 만들 필요는 없다.
- **한계:** 현재 Syft 자료는 source-tree SBOM이며 DB 요약은 200개 제한이다. 누락/잘림은 안전 판정으로 바꾸지 않는다. 실제 실행 이미지의 SBOM과 동일하다는 보장은 없고, 출처 증명도 미제공이면 허용되는 부분 구현이다. 원격 SaaS MCP 내부 소스·실행물을 강제로 검증할 수는 없다.
- **검증:** 실제 공개 OSS MCP 두 판본으로 정상·영향·자료 없음·200개 잘림을 구분하고, 중지 후 새 호출이 차단되는지 독립 효과와 확인한다. LiteLLM 다른 endpoint나 직접 credential이 남아 우회되지 않아야 한다.
- **포기 조건:** 원격 SaaS MCP만 사용하고 기존 기업 SCA/배포 시스템이 이 흐름을 충족하면, MINT는 해당 결과 연동에 한정하거나 도입 필요성을 낮게 본다.

## 가능성 3 — 고정본 노출을 넘어 실행 전 계약 불일치를 차단

**업무 예:** 기존 도구 이름은 같지만 제공자가 입력·출력 스키마를 바꿨다. 고정된 설명을 계속 보여주는 것만으로는 승인한 인터페이스와 실제 서버가 어긋날 수 있다.

- 최신 [pin 안내](https://docs.litellm.ai/docs/mcp_control#pin-a-servers-tool-list)는 변경된 설명·입력 스키마 대신 고정본을 계속 노출하고 알림을 낸다고 설명한다. annotations와 output schema는 pin 범위 밖이며 live로 노출한다. 이것은 SDK의 schema 검증이 전혀 없다는 뜻은 아니다.
- MINT의 `core.py:1650–1678`은 실행 직전 조회한 도구의 설명·입력·승인 출력 스키마 해시를 대조하고 불일치하면 `MCP-CATALOG-001`로 차단한다. 따라서 후보는 일반적인 pin이 아니라 **실행 전 live 계약 대조와 불일치 시 중지**이다.
- **한계:** `output_contract.py:60–76`에서 기존 `approved_output_schema_hash=NULL`인 항목은 출력 계약이 아직 고정되지 않은 채 호환 처리된다. 재승인 전 모든 도구의 출력 계약을 강제한다고 표현하면 틀린다. 계약 일치가 실제 동작의 안전성·소스 일치까지 증명하지도 않는다.
- **접점/검증:** 최신 LiteLLM의 discovery hook이 주는 metadata와 실행 시점의 live metadata는 다르므로 완전한 적용 경로를 확인한다. 설명·입력·출력 변경 각각에서 알림, 모델 노출, 실제 전송 여부를 LiteLLM 단독/연동으로 비교한다. 기존 공개 OSS MCP의 실제 다른 판본·승인 스냅샷을 사용하고 자체/mock MCP를 새로 만들지 않는다.
- **판단:** 가능성 1·2를 보강하는 엄격 운영 옵션으로 적합하다. upstream의 pin 확장으로 격차가 줄 수 있으므로 이것 하나를 제품의 유일한 차별점으로 삼지 않는다.

## 종료·증거와 실행불명은 어떻게 다룰까

별도의 네 번째 대형 제품보다는 위 세 흐름의 공통 기능으로 묶는다. `decommission.py:1–29`는 차단·권한·전파·대상 상태 증거를 구분하며 관리 API의 성공 응답만으로 회수 완료를 인정하지 않는다. `dispatch.py:18–30,66–86`은 전송 의도와 응답 없는 쓰기를 구분한다. 자격 삭제 뒤 provider에서도 무효인지, 진행 호출의 결과가 불명인지 확인하는 운영 가치를 검토할 수 있다.

단, LiteLLM의 세션 종료·저장 자격 철회가 없는 것처럼 설명하지 않는다. 외부 제공자의 회수 API·관리 권한·증거 접근이 없으면 MINT도 완료를 증명할 수 없다. 원장과 승인 화면만으로 독립 효과나 법적 준수를 보장하지 않는다.

## 중앙 연동과 제품 형태에 대한 결론

현재 우선 비교안은 **LiteLLM이 모델/키/예산/MCP 집계를 맡고, 고위험·관리 대상 MCP는 MINT의 서버별 endpoint를 통해 실행하는 구성**이다. 기존 MINT의 최종 전송 검사를 재사용할 수 있다. 불필요한 사용자/registry 화면 복제는 줄이고 관리 항목 ID·승인 상태를 대응한다.

얇은 plugin은 중앙 승인/검사 서비스의 접점으로 가능하지만, 코드 조각 하나로 공급망 워커·승인 저장소·종료 증거까지 없어지지는 않는다. 정책 검사 후 실제 전송 사이 경쟁, 모든 실행 입구의 적용, 장애 시 차단, 검증된 사용자 위임, 우회 경로를 각각 확인해야 한다. 공유 서비스 키로 모든 직원을 대체하지 않는다.

중앙 연동을 전혀 조사하지 않았던 것도 아니다. [10-20 보고](../status/reports/2026-10-20-litellm-compat.md)는 LiteLLM 1.105.0→MINT의 분리 자격·허용 경로 구성과 소량의 인증 음성 확인을 기록했다. 정상 도구 호출·두 사용자 귀속·조건별 반복 시험·전체 모델 경로는 미완료였다. 이번에 다시 실행한 증거가 아니다. 앞선 대화에서 이 기록을 놓치고 전혀 검토되지 않은 것처럼 설명한 부분을 정정한다.
