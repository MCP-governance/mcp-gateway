## 3. Falcon Guardian

| 구분 | 내용과 근거 |
| --- | --- |
| 가져올 수 있는 것 | ① **하네스 인벤토리**: 「어떤 에이전트가 누구 PC에서 도는가, 휴면 포함」. MINT는 호출마다 `harness{name,version,user_agent}`와 엔드포인트를 원장에 남긴다([ARCHITECTURE §호출 기록](../../../../docs/ai/ARCHITECTURE.md)). 이를 직원×엔드포인트×하네스 목록으로 모으는 화면은 제안 대상이다(현재 Console 메뉴에 해당 목록이 있는지는 CONSOLE_UI 표 기준 「사용자·엔드포인트」 안에 있을 수 있으나 하네스 단위 인벤토리 여부는 확인하지 못했다). ② **인과 사슬 조사 화면**: 프롬프트·신원·도구 호출을 한 줄기로 보는 조사. MINT는 호출 상세 5단계와 D-145 요청·판정·엔드포인트 이벤트 상관 조회가 있어 근접하다. 같은 주체·서버·자원으로 이어진 호출을 한 화면에 묶는 「영향 범위」 뷰가 부족한지 점검할 가치가 있다. ③ (채택 보류) **허용 에이전트 종류 목록**: Falcon은 센서가 확인한 프로세스를 기준으로 허용 종류를 정한다. MINT에서 같은 효과를 하네스 이름으로 내려면 클라이언트 신고값을 판정에 써야 하므로 저장소 불변식(「하네스 신원은 기록만, 판정에 쓰지 않음」)과 충돌한다. 아래 「가져오지 않을 것」 참조. |
| 이미 있는 것 | 실행 전 판정과 차단, 관찰 모드, 반복 위반 자동 중지(D-176·`ops` 자동 중지), 직원×서버 중지(D-181), SIEM 전달(OCSF), 오프라인 버퍼(D-182), 호출 순서 정책(`P-CHAIN-001`·`P-FLOW-001`), 지원 CLI의 관리형 설정 배포, 관리형 Linux의 AppArmor 프로세스 결속(D-183, 경고 단계·부분 구현) |
| 차별점 | Falcon은 OS 센서라 게이트웨이를 우회하는 셸·SDK 행위도 본다고 주장한다(검증 안 함). MINT는 MCP 호출 단위로 계약·목적·개인정보·정책을 판정하고 도입 심사·종료 수명주기까지 가진다. Falcon 공식 글에는 도구 호출 단위 판정 설명이 없다(미확인) |
| 가져오지 않을 것 | **하네스 이름 기반 허용·차단**(클라이언트 신고값은 위조 가능하며 불변식이 판정 사용을 금지; 필요하면 프로세스를 확인하는 엔드포인트 쪽 결속 D-183을 확장하는 문제로 따로 검토). OS 센서·MDR/OverWatch 서비스 모델, 「SIEM 비용 절감」 같은 공급자 주장, pre-beta AI Gateway 방향(MINT 자체가 게이트웨이). 지원 에이전트 범위 외 에이전트는 가시성 한계가 있다는 점을 공급자도 인정한다(「지원하는 에이전트」). Linux 지원 여부는 보도자료와 블로그가 달라 근거로 쓰지 않는다 |
| 연동 관점 | MINT의 셸·SDK 우회 한계는 이미 「조직의 MDM/EDR/egress 제품과 연결」로 문서화되어 있다([경계 §4](../../../../docs/ai/SECURITY_BOUNDARIES.md)). Falcon류 EDR이 있는 고객이라면 MINT 판정 사건(OCSF)을 그쪽 SIEM으로 보내는 경로가 현실적인 접점이다. 실제 연동은 시험하지 않았다 |

## 4. 젠아이랩스 — AI-native 개발 사례(GuardTrail 포함)

우리 협업 방식과 비교한다. MINT: Codex·Claude(·Gemini) 레인이 구현하고 메인이 판단·적대 검증·병합, [협업 콘솔](../../../collaboration-console/README.md)에 실제 공개 메시지·작업 상태·검증 결과를 남기며(읽기 전용 웹), 위키 규칙이 「증거 범위 구분·미실행은 미실행」을 요구한다.

| 구분 | 내용과 근거 |
| --- | --- |
| 가져올 수 있는 것 | ① **「0건 통과」 방지**: 사례 글은 검사 대상 0개로 통과한 규칙 테스트, 건너뛴 검사를 실패로 처리하는 규칙을 쓴다. MINT에서도 `__main__`이 없어 시험 0건이 종료 코드 0으로 끝난 사례가 있었다([10-21 현황](../../status/current.md)의 「시험 대역 회귀와 거짓 통과」). 시험 실행기가 「최소 실행 건수」를 단언하는지 점검할 만하다(현재 회귀 실행기의 분류 기준은 [10-21 시험 분류 보고](../../status/reports/2026-10-21-test-triage.md)를 확인). ② **「틀린 가설 기록」 형식**(가설·근거·반증·수정·교훈): MINT 위키는 「정정 이유를 남긴다」는 규칙은 있으나 **반증**(무엇을 보고 틀렸음을 알았나)을 필드로 강제하지 않는다. 결정·정정 기록에 반증 항목을 추가하는 안. ③ **막힌 순간용 짧은 규칙**: 600여 건 실수를 원인별로 묶어 긴 규칙을 11줄로 압축했다는 방식. 레인 프롬프트(작업 지시 양식)에 「값이 없으면 멈추고 보고, 지어내지 않는다, 확인 범위를 적는다」 같은 막힘 대응 줄을 두는 안. 이미 [작업 지시 양식](../../templates/task-prompt.md)·위키 규칙에 비슷한 항목이 있는지 비교한 뒤 중복은 넣지 않는다. 추가로 ④ **배포 성공 = 헬스 응답이 방금 배포한 커밋을 반환**: 기기 배포 확인 절차와 비교할 항목(MINT 헬스 응답에 커밋이 있는지는 미확인) |
| 이미 있는 것 | 사람 승인 지점(도입 위험 등급별 승인 D-189, root 단독 모드 D-188), 규칙 문서(AGENTS·CLAUDE)와 현황 분리(`docs/ai` 정본 vs `status/`), 세션 상호 검토(메인의 적대 검증, 독립 검토 레인), 「확인 범위를 적는다」(위키: 메타데이터 확인을 전문 읽기로 쓰지 않음), 실수에서 규칙·시험으로 전환(10-21 결함 처리가 시험으로 고정됨), 비밀값 비기록 규칙, 관찰 모드→집행 단계 도입 |
| 차별점 | 젠아이랩스는 단일 벤더(Claude Code) 병렬 세션과 공용 규약 저장소가 중심이고 사람은 한 명이다. MINT는 다중 벤더 레인, 증거 단계 구분(원문 확보·정적·단위·기기·독립 효과), 제3자에게 보여 줄 감사 원장이 있다. 반대로 젠아이랩스에는 저장소 40여 개에 같은 구조·같은 파이프라인을 강제하는 **표준 템플릿**이 있다. MINT는 단일 저장소라 필요성이 낮다 |
| 가져오지 않을 것 | 「체감 생산성 100배」·제품 10종 수치·테스트 약 19,800개 등 자체 기록 수치(외부 검증 없음, 회사도 한계로 명시). 「AI 세션 병렬 다수 + 사람 한 명」 규모 모델(MINT는 소유자 판단 기준 정확성 > 편의성 > 효율). 사례 글을 우리 위키의 근거로 인용할 때는 「회사 자체 기록」 표시를 유지 |
| GuardTrail 관련 | 자사 한 환경의 측정으로 도구 호출의 93.8%가 MCP를 거치지 않는 내장 도구라고 한다(Claude Code 세션 1,068개·호출 75,430건, 자체 측정, 일반화 불가). 이 수치가 맞다면 MCP 게이트웨이만으로 볼 수 있는 행위 비중이 작을 수 있다는 방향의 참고 자료일 뿐이며, MINT의 경계 문서가 이미 같은 한계를 밝힌다. 판정에 LLM을 쓰지 않는 점·2주 관찰 뒤 차단 전환·인자 원문 대신 가린 미리보기 보관은 MINT의 현재 방향(결정적 OPA·관찰 모드·본문 제외 감사)과 같다. 내장 도구(셸·파일)를 훅으로 판정하는 범위는 MINT 제품 범위 확장 여부이므로 **소유자 결정 사항**이다 |

## 5. GensOps

| 구분 | 내용과 근거 |
| --- | --- |
| 가져올 수 있는 것 | ① **「확인이 필요한 것을 맨 위로」 관제 뷰**: 서버·서비스·배포·비용을 한 화면에 모으고 이상 항목을 위로 올린다. MINT Console 대시보드에 「승인 대기·자동 중지·미등록 잔존·SIEM 대기」를 한 줄 상태로 올리는 우선 정렬이 있는지 점검(현재 대시보드는 요약/통제 적용 현황/호출 분석/지연 탭). 설명 문구 없이 라벨·값만 쓰는 [화면 원칙](../../../../docs/ai/CONSOLE_UI.md)을 지킨다. ② **전시용 풀스크린 관제 모드**: 대형 화면에 띄워 두는 읽기 전용 뷰(2D 한정, 키보드로 패널 확대·순회). 3D는 제외. ③ **조치의 4단계 표시 통일**(제안→승인→실행→기록): MINT의 종료·폐기 케이스 절차 막대, 자동 중지·복귀, 도입 승인 이력이 각각 따로 표시된다면 같은 4단계로 읽히게 하는 안 |
| 이미 있는 것 | 조치 기록: 감사 원장(append-only)과 승인 이력, 자동 중지·복귀 상태 기록, 승인 뒤에만 실행되는 도입·종료 경로, 상태·가동 지표(대시보드 지연 탭), 드릴다운(호출 상세 다이얼로그) |
| 차별점 | GensOps는 운영 상태 관측이 중심이고 정책 판정·계약·감사 증거를 갖지 않는다. MINT 관제는 판정 근거(정책 번호·사유)와 독립 효과 유무를 같이 보여 준다. GensOps는 AI 코딩 세션 현황과 CI·테스트 이력을 운영 화면에 합쳤고, MINT는 개발 협업 기록을 제품 Console이 아닌 **별도 협업 콘솔**에 둔다(위키 규칙). 이 분리는 유지가 맞다 |
| 가져오지 않을 것 | 3D 관제실(조작할 수 없는 장식, Console 원칙 5·「판매 가능한 UI」와 충돌), 비용·AI 모델 비용 패널(MINT 범위 밖, LiteLLM 영역), 서버 재시작류 인프라 조치(제품 범위 밖), 「8일 만에 운영」 같은 개발 속도 수치, 사내 전용·외부 비공개 제품이라 도입·연동 대상이 아님 |
| 협업 콘솔 시사점 | GensOps의 「프로젝트별 활동·마일스톤·이슈·CI 카드」는 우리 협업 콘솔 `#wbs`·`#작업`에 레인별 현황 카드를 더하는 참고가 된다. 우리는 이미 WBS 스냅샷과 통합 시트 연동이 있으므로 새 화면보다 기존 채널에 레인별 마지막 활동·열린 PR·CI 상태를 모으는 소규모 개선이 맞다 |

## 6. 방향 제안(구현 아님)

| 번호 | 제안 | 근거 | 효과 | 전제·위험 |
| --- | --- | --- | --- | --- |
| R-1 | 시험 실행기에 「실행 건수 ≥ 1」 단언과 건너뛴 검사를 통과로 세지 않는 규칙 점검 | 젠아이랩스 G3, MINT 10-21 거짓 통과 사례 | 거짓 통과 재발 방지 | 현재 실행기가 이미 막는지 먼저 확인. 중복 구현 금지 |
| R-2 | 결정·정정 기록에 「반증」 필드 추가 | G3의 틀린 가설 기록 | 같은 가정의 재발 방지 | 문서 양식만 바꾸며 코드 영향 없음. 기존 기록은 소급하지 않음 |
| R-3 | 하네스·엔드포인트 인벤토리 뷰(관측 전용) 존재 여부 점검 | C2의 발견·인벤토리 | 미승인 하네스 가시성 | 하네스 이름은 클라이언트 신고값이라 불변식에 따라 **판정에 쓰지 않고** 표시·조사에만 쓴다. 허용 목록 통제는 제안에서 제외 |
| R-4 | 대시보드 「확인 필요」 우선 정렬과 읽기 전용 풀스크린 뷰 검토 | G2·G5 | 운영자의 첫 화면 판단 속도 | Console 원칙(설명 없음·조작 가능한 것만) 준수. 사용자 검수 필요 |
| R-5 | 조치 4단계 표시 통일 여부 점검 | G2 | 화면 간 일관 | 용어 통일 원칙(CONSOLE_UI 6번)과 함께 검토 |
| R-6 | MINT 판정 사건을 EDR·SIEM 제품(예: Falcon Next-Gen SIEM)이 받는 경로 확인 | C2의 SIEM 연계, MINT OCSF 전달 | 셸·SDK 우회 한계의 현실적 보완 | 실제 고객 환경 시험 전에는 주장 금지 |
| R-7 | 내장 도구(셸·파일) 판정 범위 확장 여부는 소유자 결정 | G4 | 범위 논의 근거 | 제품 정의 변경이므로 이 문서는 결정하지 않음 |

## 7. 이 문서가 확인하지 않은 것

- 세 대상의 실제 제품 동작·성능·탐지율. 공급자·회사 주장이다.
- Falcon Guardian의 호출 단위 MCP 통제, 콘솔 화면, 지원 OS 범위(자료 간 불일치), AI Gateway 출시 여부. 2차 보도 중 일부는 Falcon Complete 출시 시점을 다르게 쓰나 본문을 보존하지 않았다.
- GensOps·GuardTrail 코드와 승인 흐름이 코드로 강제되는지.
- MINT의 Console 현재 화면 구성(문서 기준으로만 비교했고 화면을 새로 열어 보지 않았다).
- 제안 R-1~R-7의 필요성은 MINT 코드·기기에서 확인하기 전까지 가설이다.
