# 목표 기능 재검토 — OSS 심층 분석 반영 (2026-10-15)

[심층 분석 9건](README.md)과 Codex의 [통합본 검토](../review-2026-10-15/README.md)(RV-01~10)를 목표 G01~G10에 대조했다. 원칙(README의 "깨지지 않는 것" 7개)을 바꿀 근거는 나오지 않았다. 바뀌는 것은 **목표를 어떤 단위로 검수하느냐**와 **몇 개 기능의 경계**다.

## 요약: 무엇이 바뀌나

1. **"도입 승인"과 "실행"을 분리한다(G01·G07).** 승인은 소스까지, 실행은 별도 job(빌드→이미지 digest→실행 ID→내부 endpoint→계약 확인→활성화)으로 둔다. ToolHive를 런타임으로 들이지 않고 자체 최소 실행기로 시작한다(기본 허용 gate·경고 후 진행 검증이 승인 경계와 맞지 않음).
2. **목적지 통제는 두 층이다(G03·G04).** 인자 검사(자동 범위, D-108·D-111)만으로는 리디렉션·DNS·서버 자체의 외부 통신을 못 막는다. 솔루션이 실행하는 OSS MCP는 실행 위치에서 egress 허용목록을 강제해야 하고, 이것은 G01의 실행 job에 포함한다.
3. **계약의 범위가 넓어진다(G02).** 지금 계약은 도구 이름·설명·입력 스키마 해시다. 여기에 **목록 완결성(모든 페이지)**, **협상 판본**(D-110으로 실제 연결에 쓰임), **outputSchema**를 넣어야 한다. 판본이 바뀌면 재검토 대상이다.
4. **결과를 네 갈래로 기록한다(G06·G09).** 연결 정상 / 정책 판정 / 도구 업무 성공 / 독립 효과. 지금은 "정책이 막음"과 "검사기가 죽어서 막음"(P-CONTROL-FAIL-CLOSED), "제공자 할당량 실패"가 운영자 화면에서 같은 무게로 보인다. ContextForge·Cisco 스캐너·LiteLLM 모두 이 구분을 따로 둔다.
5. **종료는 차단·세션 종료·실행물 정지·자격 회수를 각각 증거로 본다(G07).** MS Gateway는 삭제가 세션을 안 닫고, ToolHive `rm` 성공은 회수가 아니다. MINT는 이미 차단 우선이지만 세션 재사용(DEV-29 2단계)을 넣는 순간 "세션 닫기"가 새 종료 증거가 된다.

## 바꾸지 않는 것

- 신원은 전송 토큰에서만, 직원 토큰 미전달, 판정 불가 시 차단, 사람 승인, 덧붙이기 전용 원장, 차단≠회수, 실제 OSS로 검증.
- ContextForge처럼 플러그인별로 오류 시 진행을 고르는 방식은 채택하지 않는다. 검사기 장애는 계속 차단이다. 대신 장애로 인한 차단을 구분해 보여 준다(위 4번).
