## 1. 얼마나 구현 가능한가

시트의 「정책 실행 규칙」 탭은 이미 PaC 사양에 가깝다. 열이 그대로 정책 코드의 부품이 된다.

| 시트 열 | PaC에서의 역할 |
| --- | --- |
| 검사 시점·집행 위치 | 어느 패키지(체크포인트)에서 평가하는가 |
| 판정에 필요한 값 | 입력 계약(JSON Schema) — 게이트웨이가 검증된 출처에서 채운다 |
| 자동 통과 조건 / 자동 차단·제한 조건 | Rego 규칙 본문과 시험(정책마다 통과 1·차단 1 이상, 값 누락·형식 오류 반례 포함) |
| 제한 허용·수동 판단·예외 심사 | `manual` 결과, 예외 데이터(정책 ID·대상·범위·종료일·승인 주체·상태) |
| 연결 위험 ID | 규칙 메타데이터(`custom.risk_id`) — 역추적 |

정책별로 판정을 누가 하느냐로 세 갈래로 나눴다([매핑표](policy-map.md)의 「구분」 열).

집행 시점으로 보면 호출 판정 44, 상태 점검(주기·이벤트) 23, 도입 게이트 9, 게이트웨이 밖 8, 절차 5개다.
**호출마다 평가할 정책은 절반이고, 나머지는 도입 심사나 운영 중 점검처럼 호출 경로 밖에서 돌아야 한다.** 지금 OPA는 호출 경로 하나에만 붙어 있다.

### 시트를 PaC로 옮길 때 막히는 곳(시트 보완 요청)

- **값의 정의가 없다**: 「승인된 업무 범위」(POL-002), 「자료 유형」 분류 체계(공개조회/내부조회/수정/삭제·공유·외부 전송), 「차단 패턴」(POL-049)의 형식이 정해지지 않았다.
- **한도 수치가 없다**: 결과 수·크기(POL-048), 시간창 조회량(049), 호출량·동시 실행(055), 제한 시간(056). 누가 정하는지(보안 관리자/자료 소유 부서)는 있지만 기본값이 없다.
- **결과 어휘가 섞여 있다**: 시트는 차단·거부·제한·지연·중단·수동 판단, 런타임은 허용·허용·경보·제한 실행·승인 대기·차단, OPA는 DENY·APPROVAL·ALERT다. 한 표로 맞춰야 한다.
- **정책 간 우선순위가 없다**: 같은 호출에 여러 정책이 걸릴 때의 순서. 런타임은 「더 제한적인 쪽」(priority 숫자) 규칙이 있다.
- **「확인 주체」가 정책마다 다르다**: 예외는 보안 관리자 또는 자료 소유 부서, 민감 작업 확인(052·053)은 요청 사용자 본인이다. 값을 채우는 주체(게이트웨이 관측/등록부/사람)도 열로 있어야 입력 계약을 쓸 수 있다.

## 3. 현재 솔루션은 어디까지 커버하는가

### 있는 것: PaC 구조는 이미 있다

- OPA 두 팩: `opa/policy.rego`(패키지 `mcp.authz`)와 `opa/pac15.rego`+`decision.rego`(PAC-01~15, `DENY > APPROVAL > ALERT > ALLOW` 집계). 정책 원장 68개 ID 중 51개가 OPA, 17개가 게이트웨이 코드가 집행한다. 이 68개를 POL-001~089의 충족 수로 바꿔 셀 수는 없다.
- 정책 원장에 정책마다 위험·요구사항·통제 ID·소유자·승인자·시험 ID 메타데이터, CI의 `opa test`, 과거 판정 재생 사례(`replay_cases*.json`).
- 판정 기록(`decisions` 테이블)에 `policy_version`·`policy_input`·`would_decision`(관찰 모드)·해시 체인. 다만 정책별 필수 증적(시험 결과·출력 범위·실제 권한 관측)과 연결한 표는 없고, 일부 조기 차단은 `policy_input`을 만들기 전에 일어난다.
- `POLICY_BUNDLE`은 팩 버전 문자열과 승인 기준의 정책 버전 문자열을 비교한다. 같은 버전 문자열로 내용만 바뀐 경우는 잡지 못한다.
- 관리 실행기의 실행 이미지 24시간 재검사, 치명 취약점 최초 발견 시각 유지, 7일 초과 시 비활성화(`runtime/image_scan.py`).

### 단계별 공백의 원인

- **도입 검토(구현 0)**: 등록은 관리자의 원클릭 승인(D-259)이고, 그 경로는 설명 위험 경고를 자동 확인한다(`agent_service.py:2586`). 「불분명 → 보안 관리자 판단 대기」 상태가 없고, 삭제·공유·전송 Tool을 자동 식별해 확인 대상 표시를 강제하지 않으며(주석 없는 Tool은 `w`로 기본 분류), 시험 호출 단계가 없다.
- **운영 및 변경**: 취약점은 관리 실행 이미지에 한해 치명 7일 규칙 하나다. 시트는 악용·노출 치명 48시간, 높음 14일, 보통 30일, 그 외 90일과 대체 통제를 요구한다. 업데이트 전후 권한 비교(074)·정기 권한 점검(075)은 없다.
- **전면 차단 5개**(007·042·064·065·066): 게이트웨이는 Resource·Prompt를 중개하지 않아(`mcp_facade.py`, MCP-METHOD-001) 모두 거부된다. 위반은 없지만 시트가 바라는 「승인본은 허용」 경로가 없다.
- **잘 된 곳**: 등록 및 연결(승인 목록·만료·토큰 대상·TLS·Origin·동의)과 폐기(종료 판정, 서명된 폐기 기록을 부팅 때와 60초마다 다시 적용해 복원 뒤에도 재활성화를 막음 — `disposal.py:212-273`).

## 5. PaC 구조 제안

- **체크포인트별 패키지**: `mcp.pol.intake`(도입) · `connect`(등록·연결) · `call`(호출, 기존 `mcp.authz`·`mcp.pac15`) · `ops`(운영 점검) · `decomm`(폐기). 각 패키지는 기존 `decision.rego`처럼 `{policy_id, effect}` 목록을 내고 집계 규칙 하나가 최종 결과를 만든다.
- **입력 계약을 먼저 고정한다**: 체크포인트마다 JSON Schema. 9월 팀원 PAC-15 Rego는 게이트웨이 계약과 입력·출력 형식이 달라 그대로 바꿔 끼우면 전부 차단됐다(`research/pac15-review`). 규칙을 쓰기 전에 계약부터 공유해야 같은 일이 반복되지 않는다.
- **규칙과 값을 나눈다**: 규칙(Rego)은 시트의 조건이고, 허용 목록·권한표·한도·예외는 데이터 번들이다. 값은 콘솔에서 바꾸고 코드 배포 없이 반영한다.
- **시트와 코드를 잇는다**: 규칙마다 `# METADATA custom.pol_id`를 달고 `opa inspect -a`로 「정책 ID → 규칙·시험」 표를 자동 생성해 시트의 별도 탭에 게시한다(예시에서 18개 ID 추출 확인). 메타데이터에 ID를 적었다고 그 정책의 조건이 구현된 것은 아니므로, 표에는 시험 수와 통과 여부를 같이 싣는다.
- **시험은 시트에서 나온다**: 「자동 통과 조건」·「자동 차단 조건」을 정책마다 통과 1·차단 1 이상으로 옮기고, **값 누락·형식 오류·범위 밖 예외·기한 경계** 반례를 꼭 넣는다. CI는 `opa check --strict`·`opa test --coverage`를 막는 조건으로 둔다.
- **관찰 모드로 켠다**: 새 정책은 `would_decision`만 기록하는 관찰 모드로 오탐을 재고 집행으로 바꾼다(런타임에 이미 있는 장치).

## 7. 추가 고민 사항

1. **「자동 승인」은 신규 계약의 최초 승인에서만 불변식과 충돌한다** — 시트의 판정 원칙은 「필수 검사 통과 + 사용자 동의면 보안 관리자 개별 승인 없이 자동 도입」이다. 저장소 불변식은 「첫 관찰값 자동 승인(TOFU) 금지」다. 처음 본 계약을 자동 승인하면 충돌하지만, 사람이 미리 승인한 계약·범위와 정확히 일치하는 신청의 자동 처리는 TOFU가 아니다(제품에도 조건부 자동 승인 연장이 있다, `core.py:1050-1095`). 시트의 자동 도입을 어느 쪽으로 읽을지 정해야 한다. 자동 판단의 근거가 될 시험 호출(006)은 아직 없다.
2. **민감 작업 확인의 주체** — 시트는 요청 사용자 본인의 확인을, 제품은 다른 관리자의 승인을 쓴다. 둘은 막는 위협이 다르다(사용자 확인은 에이전트의 무단 행위, 관리자 승인은 사용자 본인의 위험 행위). 시트에 둘 다 필요한지 정하자.
3. **번호 체계가 넷이다** — 이 시트 POL-001~089, 이전 시트 POL-01~50, 원본 PAC01~24, 런타임 PAC-01~15·P-*·MCP-*. 위험 ID도 시트 RSK-01~66과 정책 원장 RSK-01~32가 다른 체계다. 정본 하나를 정하고 정책 원장에 `pol_ids` 필드를 더해 연결하자.
4. **승인 주체 역할이 없다** — 시트는 보안 관리자와 자료 소유 부서를 나눈다. 콘솔은 관리자 단일 역할이라 자료 소유 부서 승인(002·003·033·040 등의 예외)을 받을 역할·화면이 없다.
5. **입력의 신뢰와 관측 시각** — Rego는 입력을 그대로 믿는다. 값마다 「누가 채우나」를 정하고, 사용자·하네스가 보낸 값으로 판정하지 않는다. 도입·운영 팩은 센서의 관측 시각과 승인 판본을 결속해 오래된 관측으로 실행하지 못하게 한다(제품은 호출 직전 계약·승인·상태를 다시 확인한다, `core.py:1698-1729`).
6. **Rego의 fail-open 함정** — 예시를 쓰며 실제로 두 번 걸렸다. ① `not f(x) > y`는 `f(x)`가 정의되지 않을 때 규칙 전체가 정의되지 않아 차단을 건너뛴다 → 보조 규칙으로 감싼다. ② `not is_number(obj.key)`도 키가 없으면 같은 일이 난다 → `object.get(obj, "key", null)`. 「모르면 차단」 정책이 대부분이라 시험에 값 누락 반례가 반드시 있어야 한다. `object.get(data, …)`처럼 `data` 전체를 읽으면 시험 패키지까지 끌어와 순환 오류가 난다.
7. **원자성은 Rego 밖이다** — 확인값 1회 사용(053), 동시 실행 상한(055), 중복 실행 방지(054)는 판정만으로 지킬 수 없다. 게이트웨이가 판정 전에 잠금·예약을 하고 Rego는 「이 호출에 예약됐는가」만 본다.
8. **시간 초과 ≠ 원격 작업 종료** — 게이트웨이가 기다리기를 멈춰도 원격 MCP의 작업은 계속될 수 있다. 056·057의 「중단」은 전송 여부·효과 미확인·종료 확인을 나눠 기록해야 한다(`core.py:2554-2559`).
9. **감사 재생과 최소 저장의 충돌** — `policy_input`에는 실제 인자가 들어가 재생에는 좋지만 비밀정보가 오래 남을 수 있다(060). 재생에 필요한 사실과 저장 금지 정보를 나눈 저장 계약이 필요하다.
10. **호출 경로 성능** — 호출마다 평가하는 규칙이 늘면 지연이 는다(10-25 진단: 호출 한 건에 DB 체크아웃 약 35회). 상태 점검 정책은 주기 실행기로 돌리고, 호출 시점에는 그 결과(서버 상태)만 읽는다.
11. **게이트웨이 밖 정책** — 038(우회, 간편 모드는 관측만)·044(컨텍스트)·082(설정 제거)는 엔드포인트 키트와 관리형 하네스 설정이 집행한다. PaC는 그 설정을 검사하는 형태(설정 파일 대상 정책 검사)로 쓸 수 있다.
12. **시트 ↔ 코드 동기화** — 시트를 고치면 Rego는 사람이 옮긴다. 자동 생성보다 「시트 변경 → 규칙·시험 PR → `opa inspect` 역추적표 재게시」 흐름이 현실적이다. 시트 행마다 판본 열이 있으면 어긋남을 찾기 쉽다.
