# 개발 방향 갱신 — MCP 공식 로컬 서버 보안 지침·중국 기술 통제 반영 (2026-10-20)

소유자 결정(10-20 대화)으로 정한 방향이다. 기능 구현 루프는 이 문서를 근거로 대기열을 고친다.
법·행정 절차(신고·등록·평가 제출)는 참고하지 않고 **MCP 기술 통제로 옮길 수 있는 조항만** 기술 목표로 쓴다.

## 0. 소유자 결정

| 질문 | 결정 |
| --- | --- |
| 중국 규제 반영 깊이 | 신고·행정 절차가 아니라 MCP 기술 통제 조항만 기술 목표로 사용 |
| 즉시 문제 항목 | Windows 계정 전체 방화벽, 오래된 보고 장치 영구 격리안(D-160 보류안), GitHub 잠정 '승인 필요' 규칙 — 삭제하고 대안으로 교체 |
| 유지 | 기본 계정 `root/root`·`user/user`(삭제 대상 아님, 기존처럼 운영자가 `field set-password`) |
| 에이전트 결정 권한 | 사용자 확인 단계 신설(중간 위험은 요청자 본인 확인, 고위험은 지금처럼 다른 관리자 승인) |
| 로컬 stdio MCP | 승인된 것만 관리 계정에서 격리 실행하는 경로 추가, 나머지는 계속 차단 |
| 우회 판단 | 일반적인 사내 솔루션이 막는 경로는 '우회'가 아니라 '조직 통제 의존'으로 관용 처리(§1) |

## 1. 관용 원칙 — 조직 통제 의존 경로

우리 통제 밖이지만 **일반적인 사내 보안 체계(MDM·EDR/앱 실행 통제·SSE/CASB·IdP 조건부 접근·조직 테넌트 정책)가 막는 경로**는
제품이 차단·경고하지 않고 `조직 통제 의존`으로 분류한다. 제품 기능 개발 대상에서 빼고, 통제 범위 문서와 콘솔 통제 범위 표시에만 남긴다.

| 경로 | 막는 사내 체계 | 처리 |
| --- | --- | --- |
| 같은 PC의 다른 로그인 계정, sudo·관리자 그룹 계정 | MDM 로컬 계정·권한 정책 | `bypass_possible` → `조직 통제 의존` 표시. 관리 계정 인증은 계속 유지(지금과 같음) |
| 승인 경로 밖에 복사한 하네스·임의 실행 파일(Windows) | AppLocker/WDAC(App Control) | 키트가 실행 통제를 만들지 않는다. Windows App Control 자체 설계 작업은 중단 |
| 하네스의 웹·Desktop·클라우드 커넥터 | 조직 테넌트 정책(Claude·ChatGPT 기업 관리자 설정) | 관리형 설정으로 끌 수 있는 것만 끄고 나머지는 조직 정책 의존 |
| 개인 토큰으로 SaaS API 직접 호출 | CASB·SaaS 테넌트 제한·IdP | 게이트웨이 범위 밖으로 표시 |
| Windows native 루프백·UWP 예외 | EDR·App Control | G05.02의 Windows 부분은 실측 대신 조직 통제 의존으로 정리 |
| 장치 하드웨어 증명 | MDM 준수 상태·조건부 접근 | 자체 증명 구현 없음. 연동 입력 자리만 둠 |

관용하지 않는 것(지금처럼 차단): 관리 계정 자신의 직접 외부 연결, 비인가 로컬 MCP 실행, 승인 계약과 다른 도구, 게이트웨이를 거치는 모든 판정 경로.
이 원칙으로 바꾸는 표시는 콘솔 제품 화면 규칙(설명 문구 금지)을 따른다.

## 2. 삭제와 대안

### RM-01 Windows 계정 전체 방화벽 → 하네스 프로그램 범위 규칙

- 문제: 계정 SID 범위 차단이라 그 계정의 브라우저·업무 프로그램까지 게이트웨이 밖으로 못 나간다. AI 전용 계정을 강제하는 셈이라 실사용이 막힌다.
- 대안: 승인 경로(`%ProgramFiles%` 보호 위치)의 하네스·`codex-code-mode-host`·헬퍼 실행 파일에만 프로그램 범위 차단 규칙을 건다(게이트웨이·모델 프록시만 허용).
  하네스가 셸 도구로 띄우는 자식 프로세스(powershell·curl·python 등)는 프로그램 규칙에 안 걸리므로, 관리형 설정으로 하네스 샌드박스의 네트워크를 끈다(Codex `requirements.toml`의 샌드박스·네트워크 제약, Claude 관리형 권한).
  그래도 남는 경로(하네스 복사본, 샌드박스 미지원 판본)는 §1 관용(App Control·SSE 의존)으로 분류한다.
- 여파: `managed-windows.py`의 규칙 3개·`firewall_enforcing` 점검·트레이 상태·`tests-windows`·README 표 변경. 이미 설치된 장치는 옛 규칙을 `이전 항목`으로 인정하고(D-148과 같은 단계 전환) 새 키트 재설치 시 새 규칙으로 바꾼다. 옛 규칙을 바로 실패로 만들지 않는다(D-149 장애 교훈).
  Linux UID 전체 규칙은 바꾸지 않는다(관리 계정이 AI 전용이라 문제 없음).

### RM-02 오래된 보고 장치 영구 격리안(D-160 보류) → 일시 격리 + 관리자 재활성화

- 영구 격리는 채택하지 않는다. 보고 중단은 지금처럼 일시 격리(180초 만료)로 두고, 장기간 미보고 장치는 콘솔에서 `재활성화 필요`로 표시해 독립 관리자 재활성화로만 돌아온다.
- 여파: D-160 결정 기록의 '결정 필요' 항목을 이 결정으로 닫는다. 자격 폐기는 관리자 조작으로만 한다.

### RM-03 GitHub 잠정 '승인 필요' 규칙 → 등록 시 1회 국외 처리 심사

- 문제: `residency.json`의 `nonimportant: {KR: allow, *: approval}`로 국외(US) 서버인 GitHub의 내부 등급 호출이 **매 호출 승인 대기**가 된다.
- 대안: 국외 처리 심사를 호출 시점에서 **등록 시점**으로 옮긴다. 신청자와 다른 관리자가 `transfer_basis`·`evidence_ref`를 검토해 `residency_review`를 승인하면(D-138 보강 API) 그 서버의 내부 등급 호출은 허용한다. 심사가 없거나 근거가 비어 있으면 지금처럼 승인 필요.
  중요 등급 `*: deny`, DLP·PAC-12·흐름 통제는 그대로다.
- 여파: OPA 규칙과 `policy_test.rego`의 기존 기대값(내부 등급 국외 = approval) 일부가 바뀐다 → 공통 규칙대로 기존 시험 변경은 적대 검증 후 적용. 우선순위 83 원장 항목 설명 갱신. 기기 GitHub 등록은 재심사 1회 필요.
