## Boundary findings

`GIT_BASE_DIR` is a supported path-validation root for most handlers, not an OS sandbox or one pinned repository. A second synthetic repo inside the base worked. Outside the base, `git_set_working_dir` succeeded and returned status/history metadata; subsequent implicit and explicit `git_status` calls were rejected with `Path traversal detected`. Separately, `git_clone` accepted an outside-base destination and cloned a task-local synthetic repository. The clone HEAD independently matched source HEAD. Source review shows both `git_set_working_dir` and `git_clone` opt out of common path resolution (`skipPathResolution:true`): the setter directly validates/stores its path and returns a repository snapshot; clone uses its supplied destination. Normal status handlers use the common GIT_BASE_DIR resolver. These are two different outside-root effects: setter metadata read and clone filesystem write. The clone destination was removed only after the MCP process exited and after verifying the task-owned path, exact origin, HEAD, and expected contents; evidence records `server_process_exited=true` and `clone_destination_removed=true`. The caller OS account's filesystem permissions remain the final boundary.

DBHub's default `execute_sql` can write. With per-tool `readonly=true`, a synthetic INSERT and `ATTACH DATABASE` were rejected as `READONLY_VIOLATION`, and no attached file was created. `SELECT load_extension(...)` was rejected as `not authorized` in this Node/SQLite build. Source review shows readonly SQL classification plus SQLite `PRAGMA query_only=ON` during execution. This is a SQL/tool restriction, not OS filesystem isolation; the process retains the current OS account's file permissions. The extension test referenced only a nonexistent synthetic DLL path.
