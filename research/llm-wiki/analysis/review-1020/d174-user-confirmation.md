## 발견

### F1 — 높음: 확인 화면 값과 실행 지문이 서로 다른 표현을 가리킬 수 있음

- 근거: 설계 §2.4·§6은 화면에 제한·마스킹 후 실제 전송할 인자를 보이고, 그 값의 지문을 대조한다고 한다. 현재 `core.py:2223-2235`의 `stored`/`request_fingerprint`는 원 호출의 `arguments`를 포함한 저장 payload 전체를 해시한다. `core.py:2243-2244`는 실행 직전 `classify.apply_restrictions(cls, outbound, ...)`로 전송값을 별도로 만든다.
- 반례: `secret`을 마스킹하거나 제한으로 길이를 줄이는 요청에서 확인 UI가 `outbound`를 보여도 제출 지문은 원본 `stored`의 해시다. 구현이 원본을 재구성해 실행할 때 그 해시만 비교하면, 화면에 렌더한 바이트가 실행값과 같다는 증명은 없다. 반대로 마스킹 출력만 저장하면 실행에 필요한 원본과의 결속이 사라진다.
- 수정안: 확인 스냅샷을 서버에서 생성해 제한·마스킹된 전송 인자, 서버·도구·계약 digest·정책/제한 버전, 요청자·만료를 정규화해 해시하고 저장한다. UI는 그 스냅샷 전부를 잘림 없이 렌더링하고 API는 클라이언트가 보낸 digest와 DB의 스냅샷 digest를 비교한다. 실행도 같은 스냅샷을 사용하거나, 재계산 결과가 digest와 다르면 차단한다. 민감 원본을 보존해야 한다면 별도 암호화·보존 규칙이 필요하다.

### F2 — 높음: `kind` 누락 기본값이 새 경로의 승인 종류 혼동을 숨길 수 있음

- 근거: 현재 `core.py:2163`은 OPA에 `approval.granted`와 `id`만 준다. 승인 종류는 전달되지 않는다. 설계 §2.3은 `object.get(input.approval, "kind", "independent")`로 누락 시 독립 승인을 가정한다. 기존 승인 규칙은 `policy.rego:421-440,617-626`처럼 `not input.approval.granted`에 의존한다. PAC 승인 facts는 `pac.py:314-323`에서 승인자 관리자 여부를 읽으며 행의 종류를 검사하지 않고, 중대 영향은 `high_impact.py:45-51`에서 승인 상태·지문·범위만 확인한다.
- 재현/반례: self 승인 행을 가져와 `approval_granted=True`로 재평가하되 OPA 입력에 `kind`를 빠뜨리면 기본값이 `independent`가 되어 기존 `P-X-APPROVAL-001`·`P-VOLUME-001`·`P-UNTRUSTED-CONTENT-001`의 재승인 요구를 통과할 수 있다. PAC·중대 영향 경로도 각각 승인자 관리자 또는 승인 범위 검증이 독립 승인을 증명한다고 오인할 수 있다. 누락 기본값은 구형 입력 호환에는 편하지만, 구현 누락을 fail-open 형태로 감춘다.
- 수정안: 새 실행 경로는 승인 ID에서 DB 행을 읽고 `kind`를 서버 측에서 반드시 가져온다. 승인된 행이 없거나 kind가 허용 집합에 없으면 차단한다. 구형 행의 독립 승인은 스키마 기본값으로 한 번 정규화한다. `kind` 누락과 self가 각 독립승인 정책·PAC-13·거주성·중대 영향 모두에서 거부되는 시험을 새 파일에 둔다. 다른 승인 행 ID를 대입해도 요청 fingerprint·요청자·호출 payload·approval row ID가 전부 같은 행에 결속돼야 한다.

### F3 — 높음: 확인 경합에서 관리자 거절이 확인 승리 후에는 효력이 없음

- 근거: 설계 §2.4는 확인에서 `PENDING → APPROVED` 조건부 UPDATE 후 실행하고, 관리자는 self 건을 거절할 수 있다고 한다. 현재 독립 승인도 `core.py:2348-2357`에서 조건부 UPDATE로 선점한 뒤 실행하지만, 자기 확인 경로와 관리자 거절 경로의 동시성 계약은 설계에 없다.
- 재현/반례: 관리자의 거절과 요청자의 확인이 동시에 도착하면, 확인 UPDATE가 먼저 성공한 경우 행은 `APPROVED`가 되고 실행 흐름이 시작된다. 뒤늦은 거절은 PENDING 행을 대상으로는 이길 수 없다. 이는 DB 단일 승자 규칙으로 일관되지만 “거절도 가능”이 실행 중 취소를 뜻한다면 보장하지 않는다.
- 수정안: 의도된 의미를 “PENDING 상태를 먼저 원자적으로 차지한 한 쪽이 이긴다”로 명시하고 결과를 원장에 남긴다. 관리자 거절이 선점 뒤에도 실행을 취소해야 한다면 별도 `CLAIMED` 상태 및 upstream dispatch 직전 취소/재검증을 설계해야 한다. 확인 2회 동시 요청은 조건부 UPDATE로 정확히 한 건만 성공하고 나머지는 실행·원장 승인 이벤트를 만들지 않는 계약을 둔다.

### F4 — 중간: 정책 우선순위는 이중 판정으로 제한·경보를 보존한다는 점을 시험으로 고정해야 함

- 근거: 설계 §2.2는 `P-CONFIRM-001` 우선순위 110이 제한(120)·경보(125·132)보다 먼저 선택될 수 있다고 적고, “확인 뒤 실행 때 다시 판정”을 전제한다. 현재 `core.py:2202-2209`는 기존 `Approval`이 아니라 Allow/Alert/Restrict일 때만 동의를 확인하고, 2211-2219행은 뒤에서 중대 영향 승인을 강제한다. Rego의 Restrict 예시는 `policy.rego:443-454`, Alert 예시는 629-637행이다.
- 반례: 최초 판정에서 P-CONFIRM이 제한·경보를 가리면, 승인 실행 재평가가 동일한 제한 인자와 경보를 다시 산출하지 못하는 구현(원본/마스킹 값 차이, 승인 표식이 잘못된 규칙까지 풀어줌)에서는 제한이 사라진다. 설계상 “재평가된다”는 설명만으로 결과 보존은 입증되지 않는다.
- 수정안: 신규 Rego 시험에서 confirm과 Restrict, confirm과 각 Alert, confirm과 Block, confirm과 다른 Approval의 동시 적중을 만들고, 1차는 대기·미실행, 확인 후에는 Restrict가 실제 적용되고 Alert가 원장에 남으며 Block/독립 Approval은 계속 대기·차단함을 확인한다. 시험 추가만 하고 기존 기대값은 바꾸지 않는다. 저장소의 우선순위 정렬 방향과 동률 규칙도 이 사례로 고정한다.

### F5 — 중간: 확인 미적용 등급과 완료 조건의 범위가 모순됨

- 근거: 방향 문서의 완료 조건은 “확인 없이 실행 0”이다. 설계 §2.2는 high·very_high에 새 확인 규칙을 만들지 않고, 등급 없는 이전 등록에는 도구 검토 `confirm`만 적용한다. 설계 §1은 등록 시 `risk_assessment.tier`를 언급하지만 현재 `v2_tables.sql:361-363`은 위험 입력을 저장하고 티어를 매번 산출한다고 설명한다.
- 반례: 기존 미등급 서버의 쓰기/실행이 도구 검토에 `confirm`이 없고 다른 규칙에도 걸리지 않으면 본인 확인 없이 실행될 수 있다. 이는 호출이 확인 대상일 때만 적용되는 완료 조건이라면 괜찮지만 문언 그대로는 실패다. high·very_high도 기존 정책이 승인하지 않는 행위까지 자동으로 독립 승인된다고 가정할 근거가 없다.
- 수정안: 완료 조건을 “DEV-72의 확인 또는 독립 승인 조건을 만족하는 모든 호출은 해당 승인 없이 실행 0”으로 범위화하고, 위험 티어별로 자동 허용/본인 확인/독립 승인/차단 표를 명시한다. 이전 등록은 등급 미확정 자체를 별도 재심사·차단·확인 중 무엇으로 둘지 명시하고, 아무 조치 없이 확인 면제되는 상태를 만들지 않는다.

### F6 — 낮음: MCP elicitation은 간편 입력에는 맞지만 확인 증거 대체로는 부적합

- 근거: 설계 §2.5는 elicitation을 확인 증거로 제외하고 실측 후 편의 경로만 고려한다. MCP의 공식 SDK 문서는 elicitation handler와 클라이언트가 수락한 입력을 처리하는 방식을 설명한다. 프로토콜은 입력 요청/응답을 전달하지만 콘솔 재인증, 사용자 identity, 실제 사람의 확인을 증명하지 않는다. [MCP Go SDK elicitation](https://go.sdk.modelcontextprotocol.io/client/), [MCP TypeScript SDK elicitation](https://ts.sdk.modelcontextprotocol.io/v2/servers/elicitation).
- 반례: 자동화된 elicitation handler가 `accept`를 반환할 수 있고, MCP 서버가 받은 응답만으로는 사람이 직접 봤는지 확인할 수 없다. URL mode도 별도 OAuth/브라우저 흐름에는 쓸 수 있지만 호출 자체에 대한 서명된 사용자 승인 증명이 되지는 않는다.
- 수정안: 설계의 “이번 범위 밖, 편의 경로만”을 유지한다. 향후 도입 시 확인 UI만 대체하고 서버가 발급한 nonce·요청 digest·재인증 결과를 게이트웨이에서 검증하는 구조가 아니라면 승인 효력이나 확인 지표에 포함하지 않는다.
