### 2. 낮음 입력은 기존 승인 시나리오를 우회하지 않는다

- `tests/intake_fixture.py:17–35`의 기본 입력은 점수 1·낮음이다. 실서비스 시험용 `impact_input('important')`도 점수 3·낮음이다. 실제 `risk_tier.assess`와 `decide`로 계산했으며 둘 다 관리자 1명으로 승인된다(`gateway/app/risk_tier.py:25–53,76–112`). 높은 데이터 등급 등록을 막는 별도 비교 때문에 실서비스 시험에 `important`를 준 것도 타당하다(`core.py:618–631`).
- 자기 승인은 위험 입력보다 먼저 거절된다. `agent_service.py:1394–1407`의 관리자·독립성 검사가 공급자 보증 검사(1408–1415행)와 위험 등급 검사(1417–1421행)보다 앞선다. 자기 승인용 신청에 위험 입력을 추가하지 않은 부분도 403 시나리오를 다른 오류로 대체하지 않는다.
- 출처 누락 시험의 본 신청은 정상 입력을 가지고, 계약 검토 뒤 `provenance`만 비운다(`intake_identity_pg_check.py:185–214`). 따라서 새 입력 누락 오류로 같은 409를 얻는 경우가 아니다. 제품은 위험 게이트를 통과한 후 `review.intake_gate`의 출처 차단 사유로 보류한다(`agent_service.py:1424–1436`).
- 소스 신청의 `risk_level='CRITICAL'`과 새 `risk_input`의 낮음은 서로 다른 축이다. 전자는 검사기가 발견한 취약점, 후자는 신고된 업무 영향이다. 기존 치명적 발견·독립 위험 수용·기한 만료 검사는 남는다(`intake_identity_pg_check.py:423–450,497–511,523–542`). 낮은 업무 영향 입력이 치명적 취약점을 없애지 않는다.
- 단위 시험의 새 `db.fetch_all=[]`은 위험 게이트가 조회하는 이전 공동 승인 이벤트가 없는 상태를 표현한다(`intake_validation_test.py:238–240,263`; `agent_service.py:1357–1366`). 낮음에는 공동 승인이 필요 없으므로 승인 함수를 대체하거나 승인 결과를 강제로 만드는 대역이 아니다.
- 보류 전 종료 조건을 확인하는 셸 시나리오는 아직 격리 검증 전이다. 위험 게이트는 `VALIDATED`·`REMOTE_REVIEWED`에만 적용되고(`agent_service.py:1417`), 기존 종료 조건·격리 검증 분기가 이어진다(1466–1474행). 여기에 위험 입력을 생략한 것이 기존 기대 사유를 가리는 변경은 아니다.

### 3. `acceptance.py` 상수 사본은 시험 코드의 입력이다

경로가 `gateway/app/`이고 이미지에 포함되는 것은 맞다(`gateway/Dockerfile:29`). 그러나 이 모듈은 기존부터 계정·주체·서버를 사용하는 인수 시험이며, 실행 진입점은 `python -m app.acceptance`다(`acceptance.py:1–18,632–635`; `console.sh:515`). 저장소 호출부 검색에서도 서비스 시작 시 이 상수를 제품 기본값으로 읽거나 브라우저 자산에 전달하는 경로는 발견하지 못했다. 기존 다른 시험도 이 모듈의 도우미를 가져다 쓴다(`tests/security_regression.sh:40`, `tests/reservation_effect_check.py:32`).

새 상수는 해당 인수 시험의 신청·승인 본문에서만 사용한다(`acceptance.py:44–51,475–489,506–507`). 실제로 AST에서 추출한 두 상수가 `intake_fixture.py`와 같은지도 확인했다. 따라서 **제품 승인 기본값에 합성 공급자 증빙을 주입하거나 제품 화면에 개발 주석을 추가한 변경으로 보지 않는다.** 시험을 실행하면 합성 값이 시험 신청·등록 증거에 저장되는 것은 사실이며, 실공급자 보증이나 실제 운영 도입의 증거로 재사용해서는 안 된다. 이미지에 시험 코드가 포함되는 기존 구조 자체를 이번 변경이 새로 만든 것은 아니다.

### 4. `intake_register.py` 필수 인자 추가는 운영 도구로 타당하다

`tests/intake_register.py:42–69,80–84,99–104`는 공급자 보증·영향 입력을 호출자/JSON 파일에서 필수로 받고 API로 전달한다. 합성 픽스처를 가져오거나 기본으로 채우지 않는다. 보증 필수화와 입력 누락 보류는 D-137·D-143의 제품 계약이다(`docs/ai/DECISIONS.md:1462–1467,1476–1481`). 기존 무입력 호출의 호환성을 유지하려고 증거를 자동 생성하는 것보다 필수 인자가 적절하다.

저장소의 Python 호출부 두 곳은 모두 새 인자를 전달한다(`real_mcp_gateway_check.py:61–68`, `real_warning_review_check.py:51–58`). CLI 예제와 설명도 갱신됐다(`intake_register.py:6–15`, `docs/ai/TESTING.md:62–65`). 메모리 HTTP 대역으로 신청에는 신청자 토큰과 전달받은 위험 입력, 승인에는 승인자 토큰과 전달받은 보증이 실리는지 확인했고, 인자 두 개를 각각 생략하면 `TypeError`로 거절됨을 확인했다.

도우미는 여전히 한 번의 관리자 승인만 수행한다. 매우 높음 등 공동 승인이 필요한 입력이면 승인 API의 보류 응답 이후 등록이 409로 거절될 수 있다(`agent_service.py:1418–1420,1648–1649`). 성공으로 위장하거나 등급을 낮춰 재시도하지 않는다. 공동 승인 진행을 지원하는 운영 UX까지 이 diff가 구현한 것은 아니다. 실서비스 시험의 공급자 보증·업무 영향 값도 합성 시험 전제이며 실제 공급자의 지원·개인정보 처리 사실을 증명하지 않는다.

## B. 세션 재사용 시험 대역 보완

### 1. 원인 재현과 제품 코드 대조

기존 시험의 AST 로더는 함수 본문을 읽고 시험의 전역 대역과 함께 실행한다(`tests/upstream_session_reuse_test.py:27–33,562–574`). 대역 `registry`에는 `tool_hashes`가 없다(563행). 제품은 승인 설명·스키마를 대조한 뒤 이 함수를 호출한다(`gateway/app/core.py:1371–1384`). 원본 실행은 **40건 중 실패 1·오류 8**이었다. 오류는 모두 `registry.tool_hashes` 누락이며, 철회 시험은 세 하위 사례가 여기서 멈춰 해제 횟수까지 `0 != 3`으로 실패한다.

`c002fbd`의 `_call_upstream`과 현재 체크아웃의 함수는 행 번호를 제외한 AST가 동일했다. 시험 파일도 두 판본 사이 차이가 없다. 따라서 이 재현에서 발견한 장애를 최근 공급자 보증·위험 등급 기능이나 세션 풀의 실행 결함으로 설명할 근거는 없다. 이것이 제품 전체에 다른 세션 결함이 없다는 증명은 아니다.

### 2. 승인 메타데이터 대역은 이 시험의 정상 입력으로 유효하다

실제 `registry.tool_hashes`는 설명·입력 스키마에 `canonical_hash`를 적용한 두 필드를 반환한다(`registry.py:266–268`). 기존 시험은 이미 `canonical_hash=lambda value: value`를 사용하고 관측 도구를 설명 `description`, 스키마 `{}`로 고정한다(`upstream_session_reuse_test.py:551–567`). Luna의 두 필드는 **이 기존 해시 대역을 전제로 한 결과와 일치**한다. 실제 SHA-256을 계산하는 대역이라는 뜻은 아니다.

제품은 승인된 `poisoning_review`가 같은 도구 해시일 때 메타데이터 경고 재검사를 생략하는 명시적인 분기를 갖고 있다(`core.py:1381–1384`). 실제 등록 코드도 승인된 경고 도구의 같은 해시 쌍을 보존한다(`core.py:649–650`). 제안은 이 승인 완료 상태를 픽스처에 주므로, 기존 시험이 다루려는 정책 재검사·철회·전송·해제 단계까지 도달한다. 제품의 `registry.tool_hashes`, 계약 대조, 정책 판정을 삭제하거나 대체하는 변경은 없다.

단, 상수 반환 대역이 일반적인 모든 도구 입력을 모델링하는 것은 아니다. T7은 `tool_view`의 설명을 바꾸며, 메타데이터 승인 분기보다 앞선 DB 계약 대조에서 차단됨을 계속 검사한다(`upstream_session_reuse_test.py:623–628`; `core.py:1375–1379`). 따라서 T7을 **메타데이터 승인 해시 불일치 자체**의 시험이라고 확대 해석하면 안 된다. 별도 실서비스 경고 검토 시험(`real_warning_review_check.py:62–73`)과 실제 SDK·MCP 시험은 여전히 따로 필요하다.

### 3. 거짓 통과 여부를 변이로 확인했다

파일은 바꾸지 않고 Luna 제안만 메모리에 적용해 같은 40건을 실행했을 때 모두 통과했다. 이어 같은 픽스처와 제품 함수의 메모리상 복사본에서 아래 각 기능만 독립적으로 무력화했다. 변이가 없는 `DispatchTests` 대조군 7건은 모두 통과했다.

| 메모리상 제품 함수 변이 | DispatchTests 결과 | 기존 시험이 탐지한 성질 |
| --- | --- | --- |
| `release_pool(..., 'dispatch-recheck')` 제거 | 실패 2·오류 0 | 철회 3회 해제, 계약 변경 후 해제 |
| 최종 `_policy` 호출을 허용 상수로 대체 | 실패 2·오류 0 | 호출마다 정책 재검사, 정책 장애 시 차단 |
| `dispatch.record`의 거부 결과 무시 | 실패 5·오류 0(하위 사례 포함) | 주체·종료·승인 철회 시 전송 금지, 세션 해제, 종료 정책 유지 |
| 설명·스키마 불일치의 `problem` 설정 무효화 | 실패 1·오류 0 | 변경된 계약은 전송하지 않음 |

따라서 보완 후 통과는 위 통제를 건너뛰었기 때문이 아니다. 보완 전에는 대역 오류 때문에 도달하지 못하던 기존 검사들이 실제로 실행된다.
