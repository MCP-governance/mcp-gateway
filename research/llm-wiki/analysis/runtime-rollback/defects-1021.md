# D-180 되돌리기 결함 6건 — 처리 판단 (2026-10-21)

- 판단자: 메인(통합 담당). 입력: `research/llm-wiki/status/reports/2026-10-21-criteria-audit.md` 6-B 절(시험 작성 중 발견).
- 상태: **D-180은 이미 main에 병합되고 기기에 배포(`848545f`)됐다.** 되돌리기를 실제로 요청하면 실행기가 죽는다.
- 판단 기준: 정확성 > 편의성 > 작업 효율성.

## 처리

| 결함 | 내용 | 처리 |
| --- | --- | --- |
| 1 | `worker.py`가 `uuid`를 import하지 않고 `uuid.uuid4()`를 쓴다 → 되돌림 큐잉이 `NameError`로 죽고 `main()`이 잡지 않아 **실행기 프로세스가 종료**된다. 세대는 STOPPING에 남고 재시작해도 같은 곳에서 죽는다. | **즉시 수정.** `import uuid` 추가. |
| 2 | 되돌림 분기가 `source = {}`로 두고 뒤에서 `source["source_archive_sha256"]`를 읽어 `KeyError`로 죽는다. | **즉시 수정.** 두 분기 공통으로 `evidence`에서 읽고, 이전 승인 판본의 소스 지문이 없으면 **차단**(`Refused`)한다. 조용히 비우지 않는다. |
| 3 | 되돌림으로 만든 세대가 **어떤 이유로든** 멈추면 같은 대상으로 다시 큐잉된다. 이어받은 증거의 출처 검증 실패(`MCP-SUPPLY-001`)로 멈춘 경우에도 새 세대가 QUEUED되어 **무한 되돌림 루프**가 된다. | **수정.** 멈춘 이유가 거부·차단이면 다시 큐잉하지 않고 STOPPED로 두고 그 사실을 기록한다. 자가 복구는 거부가 아닌 중단에만 적용한다. |
| 4 | `runtime-revoked`·`runtime-terminated`·`runtime-supply-chain-stop`을 **읽는 코드는 4곳인데 쓰는 코드가 없다.** 실제 차단은 서버 상태 검사가 하고 있다. | **문서로 정정.** 사건 기반 가드는 현재 동작하지 않는다 — 그 가드가 막는다고 주장하지 않는다. 실제 통제는 서버 상태 검사임을 D-180과 보고서에 적는다. 사건 기록 추가는 별도 작업으로 둔다(지금 넣으면 판정 경로가 바뀐다). |
| 5 | `runtime-rollback-queued` 사건의 `scope.runtime`이 새 세대가 아니라 멈춘 세대의 ID다. | **수정.** 같은 변경에서 고친다(증거 추적이 어긋난다). |
| 6 | 요청 쪽 거부(409)가 원장에 남지 않는다. 원장에 남는 거부는 실행기 쪽 `runtime-rollback-refused`뿐이다. | **수정.** 완료 조건이 「이력이 남음」이므로 요청 쪽 거부도 남긴다. 사유·요청자·대상 판본을 append-only로 추가하고 원장 수정 코드는 쓰지 않는다. |

## 메인의 책임 기록

결함 2의 `source = {}`와 그 뒤의 `source[...]` 접근은 D-180 구현에 함께 들어온 것이고, 메인이 `worker.py`의 병합 충돌(되돌림 분기 ↔ D-179 증명 검증)을 해결할 때 **그 조합을 그대로 보존**했다. 병합 당시 되돌림 분기를 실행하는 시험이 없어 정적 검사와 기존 회귀로는 드러나지 않았다. 완료 조건 대비 증거 감사를 돌린 뒤에야 발견됐다.

## 재검증 조건

수정 뒤 보류된 시험 5건(이전 이미지가 빌드 없이 QUEUED, 복원 뒤 계약 **바이트**·sha256이 직전 승인값과 같음, 전이 순서·사건 내용, 활성 전환 때 스냅샷 재기록, 다른 세대의 철회 표식은 막지 않음)을 새 파일로 옮긴다. 이 5건이 완료 조건의 「바이트 단위로 같다」와 「큐잉」을 덮는다.
수정 뒤 기기 재배포와 되돌리기 1회 실제 실행까지 확인한 다음에만 D-180을 「기기 확인」으로 올린다.
